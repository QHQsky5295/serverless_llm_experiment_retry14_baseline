## 一、为什么一直保留四张卡

到达窗1888次实际控制检查中，queue低条件满足1675次、active低条件满足
1881次，但TTFT低条件满足0次；all-low因此始终为false，48秒缩容等待从未
开始。1671次检查只有TTFT条件不满足。1888次是采样数，不是独立重复或
按时间加权的占比；真实资源仍由物理分配区间积分。

模型配置沿用D88开发值：TTFT lower=219.518056ms、upper=5000ms、窗口55秒。
本次控制窗口P95的最小/中位/P95分别1223.365/2200.958/3688.424ms。
不能把这个在线219.518ms控制下限混同D648按长度分组的最终SLO。

三次扩容发生在业务开始后10.556、12.606、14.704秒，三者当时queue均为0、
active分别0/0/1；触发分量均为已完成请求P95=7852.205ms，超过5000ms。
同一较慢的早期请求在55秒窗口内继续影响控制，这是当前代码的真实语义，
不是三个独立拥塞证据，也不能据此跳过或删掉旧样本。其后控制采样有1860次
四副本ready。由真实控制记录可以解释无缩容，但不能离线预测改阈值后的
SLO/U，也不直接提高下限、降低max实例数或套用7B配置。

## 二、短板主要不局限于启动期

自然扩容trigger→ready区间与到达→首token相交的19条请求仅1条联合违约；
无此交集的3981条中424条违约。该时间相关性不能把启动成本从请求中扣除，
但足以否定“只处理启动就已覆盖全部425条违约”的解释。

259条TTFT-only违约的平均TTFT2645.533ms，其顺序阶段均值如下：

| 阶段 | ms |
|---|---:|
| 计划到达→实际释放 | 381.626 |
| 释放→申请全局许可 | 105.562 |
| 申请许可→恢复执行 | 0.062 |
| runtime选择/来源保护 | 632.650 |
| runtime准入→原生引擎入口 | 1277.171 |
| 引擎入口→原生队列 | 118.911 |
| 原生队列→调度 | 9.696 |
| 原生prefill至首token | 119.854 |

runtime阶段包含路由、pending登记、所选来源确认及调度；不是纯槽容量排队。
准备阶段包含加载与协调；不是纯网络/磁盘/函数CPU时间。不能用减去某阶段
产生所谓修复后TTFT。当前全局许可等待不是7B D624中的秒级主导问题。
