# D815：Full 请求物化缺少文件容量回收路径的最小复现

2026-10-25。状态：因果反例已复现；生产实现尚未修改，没有新增性能运行。
对应主线为 D814 3B W2 失败的根因修正，不是新的 baseline 优化。

## 证据和历史

D814 在 `req_03285` 的 Remote→NVMe 物化预分配阶段失败：已收到远端
headers，客户端尚未接收 payload，本地报告 retained copies 加 incoming
transfer 超过 tier budget。随后主动准备提交同一失败 movement，错误向上
传播并终止回放。3289 条正常原生终态不等于完整 4000 条；截断 GPU-s 不进入
资源排名。原始证据和无损压缩身份均保留，未重复启动 D814。

核对历史发现：

- D277 是 GPU 引用/准备 lease 绑定问题，不是本轮文件容量问题。
- D449 / commit `48265b8c` 已明确记录：无准备 objective 的 demand 在满
  文件缓存中直接失败。该提交只给 ElasticLocality 实现普通文件 LRU，故
  Full 的 `planned_only` 路径仍存在这个缺口；不是本轮 max3 参数引入的新代码。
- 之后 D609/D627/D631/D680 的文件观察、发布及 HOST lease 修订没有补上
  请求物化的容量回收入口。已有默认 Full 测试甚至明确保留这一失败行为。
- 当前 `_ensure_local_async` 给 movement 标注 demand，但不提供文件回收
  objective；`_prepare_file_allocation` 仅处理主动 objective 或独立
  `demand_lru` 策略，剩余短缺直接报错。不能以关闭这个错误检查替代修正。
- GPU/HOST 主动准备所需的中间 NVMe 也可能没有最终文件候选 objective。
  这是同一容量协议的另一个入口，尚未通过本次反例验证其满缓存行为。

## 复用既有夹具的控制对照

复用 `FileObjectiveReplacement.make`、真实 LocalSourceReferences、文件
预分配/发布、既有 HTTP 响应夹具和真实 movement queue。调用真实
`_ensure_local_async`，没有 mock 掉容量或回收。合成小文件只用于正确性检查，
不是重建模型工件、真实远端实验或性能数据。

| 条件 | 请求驱动物化 | 既有主动 objective 路径 |
|---|---|---|
| NVMe 预算 | 24 KiB | 24 KiB |
| 旧 NVMe 副本 | 3 个，共 24 KiB | 相同布局及内容 |
| 可安全回收字节 | 24 KiB，3 个均 eligible | 相同 |
| 传入峰值 | 20 KiB（最终 payload 16 KiB） | 相同 |
| 旧副本 fallback | 已确认 HOST 副本 | 相同 |
| 结果 | 0 B payload 接收后容量错误；未回收任何副本 | 回收 24 KiB 后发布 16 KiB 新副本 |
| 后续同目标准备 | 保留失败，拒绝自动重试 | 正常完成 |

三个既有针对性测试通过：默认 Full 不静默变成 LRU；引用真实释放后才唤醒
延期替换；收益等于损失时不删除、不自旋。这些测试和上述两个夹具案例不是
性能重复样本，不计算 CI。

本次证明的是“存在安全可回收副本时，当前请求入口仍会失败”及其后续错误链。
它没有恢复 D814 失败瞬间每个实际副本的引用状态，不能断言当时所有 420 个
已下载副本都可回收。修复后的完整回放仍须检验实际可回收空间和等待行为。

## 论文语义与外部实现核查

IEEE 投稿文本的层级/引用、Eq.(4)–(7)及 replacement 段落要求主动计划
固定 h/d，按有效 fallback 的损失/可用字节选出覆盖短缺的最短前缀，且收益
大于总损失。最后一段同时明确请求驱动加载优先于主动准备、仍遵守物理限制。
论文没有要求“需要服务的请求因为不能作为有利的预取而永久失败”。

核对 [vLLM 0.30.0 官方 worker manager](https://raw.githubusercontent.com/vllm-project/vllm/v0.30.0/vllm/lora/worker_manager.py)
的 `LRUCacheWorkerLoRAManager.add_adapter`（263–296行）：请求驱动加载与
容量替换相连接；先验证加载再回收 CPU cache，允许短暂超过对象数量上限。
这支持区分“请求必需工作”和“可选准备”，但不能把其内存对象策略直接
说成文件层策略，尤其不能照搬临时超额来突破本项目物理文件预算。

## 下一项实现的约束（不是已完成修复）

继续同一个容量假设，不另开性能调参系列：

1. 在已有文件所有者和 movement queue 中明确请求必需物化与可选准备的
   分工，接入足额回收或可解除的容量等待；不增加第二套传输/缓存框架。
2. 保留主动选择的 h/d、收益/损失、源引用、pending 目标及物理容量合同。
   不把整个 Full 切成普通 LRU，不扩大 NVMe，也不把吞掉异常叫作恢复。
3. 中间 NVMe staging 必须有明确的容量处理；可选工作受阻时不得污染同键
   后续请求为永久 failed。真实 I/O/内容/所有权错误仍保持失败证据。
4. 请求与准备合并时，以仍然存活的请求意图决定必需性；请求撤销不得留下
   永久的高优先权。引用释放、计划结束等真实事件才触发重新检查。
5. 先用当前小文件反例验证成功，以及全部被引用、单次传输本就超额、合并、
   取消和中间 staging 的受影响语义；不重复无关 GPU/模型资格。通过后新建
   版本完整跑规定场景，保留 D812/D813/D814 的原身份。

当前尚未冻结具体需求回收策略，不能把上述边界描述为已经实现或验证的算法。
下一轮应直接选择并实现这条根因修正，不重复本次已证明的反例。
