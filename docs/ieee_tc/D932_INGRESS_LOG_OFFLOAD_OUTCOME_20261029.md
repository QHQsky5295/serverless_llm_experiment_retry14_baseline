# D932：7B W2 入口证据写盘 offload 结果

日期：2026-10-29  
执行键：`d932_7b_ingress_log_offload_w2`  
系统：PrimeLoRA（IEEE Full，vLLM 后端）  
身份：完整开发期观测；不是独立留出测试，也不替换 D917/D931。

## 结论

D932 完整完成了 4,000/4,000 请求，服务、回放器和看门狗返回码均为 0，所有
4,000 条请求具有原生 token 合同记录，物理 GPU 分配全部释放。它检验的是一个
明确的观测路径假设：服务事件循环中同步 `service_ingress.jsonl` 的逐请求
`write+flush` 是否污染请求接收时间。

该假设在局部阶段得到支持，但没有形成整体 PrimeLoRA 优化。D932 的最终入口
`server_received_s-client_submit_s` 均值为 133.11 ms、P95 为 810.42 ms；在
早期阶段曾显著低于 D930/D931，但随着回放进入高并发扩容阶段，入口延迟再次
累积。更重要的是，D932 的物理生命周期 GPU 时间和 Type-1 P95 TTFT 均劣于
当前旧 PrimeLoRA 参考，因此不封存为新性能参考，不开始绘图，也不据此改写
PrimeLoRA 的论文结论。

## 因果边界

D932 只把诊断日志写入从服务事件循环移到同一进程的专用 FIFO 写线程；它没有
改变回放时间戳、路由、adapter 选择、缓存、扩缩容、准入、远程传输或九个
IEEE 公式。日志错误仍会使运行失败，因而没有静默丢失证据。这个改变不能被
解释为“从 TTFT 中扣除了日志开销”，也不能把早期入口改善外推为整体系统改善。

完整结果显示主要尾延迟已经位于扩容准备、dispatch/admission 和远程工件交付
的组合路径。下一轮若继续 PrimeLoRA 优化，必须先用已有阶段字段提出一个新的、
可证伪的控制/准备路径假设；不能重复 D932，也不能叠加没有独立触发证据的守卫。

## 当前主线决定

1. D932 原始结果、失败/阴性解释和代码提交永久保留，不覆盖 D917、D930 或
   D931。
2. D932 不作为 7B G1/G2 正式参考，也不生成论文图表。
3. 由于 D932 的联合服务可行性已达到约 97.9%，且用户已授权“达到差不多效果
   后先完善基线”，下一步可以进行 ServerlessLLM 的同合同审计；该动作不是
   声称 PrimeLoRA 已最优，而是用正式论文基线揭示 G1/G2 的相对位置。
4. 若 ServerlessLLM 或后续基线显示 PrimeLoRA 在物理 GPU-s/request 或预算下
   W2 P95 TTFT 不占优，再回到 PrimeLoRA，依据配对阶段证据提出新候选；不通过
   选择性重跑、改变 SLO、隐藏 `n_correct` 未知或削弱基线来获得领先。

## 资源与交付边界

本轮没有修改推理机 150/100 GiB、内存、OOM 或 cgroup 规则，也没有删除唯一
工件。远端只读发布制品和请求触发的实际传输仍按
`REMOTE_DELIVERY_METRIC_POLICY_20261029.md` 计量；发布前压缩不进入请求
TTFT/E2E，不能事后从请求延迟扣除。制品传输节点的容量继续使用并发临时打包
峰值、日志增长和安全余量的独立门槛。
