# PrimeLoRA：当前资格、指标与实验主线裁决

日期：2026-10-20  
范围：D701/D702/D703、远端交付协议 v4、冻结指标 V1/V2  
用途：冻结后续 PrimeLoRA 与所有已发表 baseline 的实验解释口径；不修改历史

## 1. 先给出结论

1. **85%不是本项目的合格门槛。** 当前冻结协议没有 85% 这一主门槛。主档位是
   全部请求正确完成，并且联合 TTFT/TPOT 达成率至少 95%（4,000 请求中至少
   3,800 条同时满足两个限制）；G1 在此条件下比较生命周期物理 GPU-s/request，
   G2 另加共同资源预算 `U <= 0.75 U_ref` 后比较 W1/W2 P95 TTFT，并报告联合
   达成率差值。85%（3,400/4,000）最多只能作为原始结果的描述性切片，不能临时
   变成质量约束，也不能为了让某个系统进入排名而新增。
2. **不能强迫每个 baseline 达到 95%。** 95%是共同的资格档位，不是要求我们
   通过调参替所有已发表系统“制造”合格结果。某 baseline 未达到时，保留其完整
   正确性、SLO、尾延迟、资源和失败证据，并标记该冻结工作点不具备 G1/G2 的
   同条件排名资格；仍可在结果表中报告其 SLO 达成率及机制解释。只有出现明显
   适配错误时，才按预登记规则做必要适配，不能为胜负无限优化 baseline。
3. **D703 的服务质量已过主档位，但资格链还未闭合。** D703 为 4,000/4,000
   原生终态、3,995/4,000（99.875%）联合 SLO、P95 TTFT 1,784.727 ms、物理
   生命周期 GPU 时间 14,864.808 GPU-s；相对 D682，联合 SLO 提高 7.525 个
   百分点、P95 TTFT 降低 10.425%、物理 GPU 时间降低 6.489%。但是固定长度
   终态、HTTP 成功、adapter/content/lease 绑定和 token-id 计数不等于独立的
   数值 LoRA 正确性，D703 的 `n_correct=null` 必须保持未知。因此 D703 是完整
   运行与服务质量资格证据，不是 G1 排名点，也不允许进入 baseline 胜负表。
4. **当前停留点是数值正确性证据，而不是性能未达标。** 在继续 baseline 之前，
   需要使用既有权重、工件、canonical prompt 和固定生成合同建立独立、同后端或
   明确可信的参考路径，逐请求给出 adapter 数值/输出的可审计判定。不能由 D703
   的 99.875% SLO、目标长度或 HTTP 200 推造 `n_correct`。

## 2. 最终评价尺子（后续不得改写）

### G1：质量约束下的生命周期 GPU 效率

对每个请求 `r`，联合事件为：

\[
 I_r = z_r\,\mathbf 1[TTFT_r\le\theta^T_r]\,
       \mathbf 1[TPOT_r\le\theta^P_r],
 \qquad A_{joint}=N^{-1}\sum_r I_r .
\]

其中 `z_r` 表示独立证据支持的正确完成；失败请求仍在 4,000 个 offered 请求
分母中。主资格要求是全部请求正确完成且 `A_joint >= 0.95`。满足后比较：

\[
 U=\sum_d\int \mathbf 1\{\text{推理节点实际持有物理 GPU }d\}\,dt,
 \qquad R=U/N_{correct} .
\]

主结论只能写为“在该冻结工作点、共同质量约束下观测到更低的 `R`”，不能写成
全局最优或统计显著优胜。TPOT 单独退化不自动否决；联合事件和物理 GPU 账目
才是 G1 的判定条件。

### G2：预算约束下的扩容/churn 尾延迟

在全部正确、`A_joint >= 0.95`、共同资源包络和 `U <= 0.75 U_ref` 同时成立时，
比较 W1/W2 的 P95 TTFT，并同时报告 `A_joint`、P95 TPOT、fetch/miss、字节数、
驻留层级和生命周期 GPU 时间。75%是预先登记的资源节省档位，不是行业常数；
不能在看到结果后调整为 85%、95% 或其他有利数值。

CE、美元成本、平均延迟、吞吐、goodput、cost/token 和 Pareto 关系仅作补充：

\[
 CE=1/(L C),\qquad
 \ln(CE_P/CE_B)=\ln(L_B/L_P)+\ln(C_B/C_P).
\]

它们不能绕过正确完成、联合服务质量或物理 GPU 生命周期条件。

## 3. 85%问题的客观回答

85%并非“必须达标”，也不是为了 baseline 公平而应加入的中间门槛。若加入，
它会把失败/超时请求从主质量约束中隐藏，并使一个只有 85% 请求满足共同时延
的系统进入资源排名，改变已经批准的研究问题。正确的呈现方式是：

| 结果状态 | 能否进入 G1/G2 主排名 | 论文中如何使用 |
|---|---|---|
| 100% 正确，`A_joint >= 95%` | 可以（再检查资源/预算条件） | 主表与主结论 |
| 100% 正确，`85% <= A_joint < 95%` | 不可以 | 如实报告 SLO 达成率、尾延迟和资源，标注不满足主资格 |
| 100% 正确，`A_joint < 85%` | 不可以 | 诊断/失败证据，分析瓶颈，不删除结果 |
| `n_correct` 未知 | 不可以，无论 SLO 多高 | 保留服务质量观测，但等待独立正确性证据 |
| 请求失败或合同不完整 | 不可以 | 失败/不完整分类，不用低资源冒充优势 |

因此，baseline 的真实达成率可以低于 95%，但不能把低于 95% 的结果与合格的
PrimeLoRA 直接宣称“同条件 G1 优胜”。这不是惩罚 baseline，而是避免把不同质量
约束下的资源数字放在同一排名中。

## 4. 远端链路和请求延迟的最终边界

研究对象是推理节点在 adapter miss、分层驻留、churn、handoff、admission 和
扩缩容下的在线服务。部署前一次性生成只读压缩缓存、管理员打包、整池扫描、
日志备份、清理和其他后台运维不是研究对象。

### 必须计入 TTFT/E2E

- 请求引发的远端已发布对象读取与响应等待；
- 真实远端到推理节点的发送、接收、协议等待和共享链路竞争；
- 本地接收、写入、内容校验、必要 materialize 和必要解包；
- 由上述 miss/fetch 引起的 admission、排队和后端等待。

这些开销不能因为“所有系统都遇到”而从结果中删除。不同系统的 miss 次数、
字节数和并发本来就是机制差异；PrimeLoRA 通过减少 miss/fetch 或提高本地驻留
命中率来降低它们，正是合法的系统优势。

### 必须排除并单独记录

- 部署通知之前的统一只读缓存生成；
- 与请求无关的远端管理员打包、压缩测试、哈希扫描、日志/备份/清理；
- 正式运行期间任何不属于请求的后台任务。

若请求期间出现 `remote_pack_performed=true`，保留原始 TTFT/E2E，不进行
`E2E - pack_time` 的事后扣除；将运行标记为交付合同违规/外部干扰，不进入主
排名，修复统一预发布交付物后以新 execution key 重跑。这既不把外部运维错误
归因于 PrimeLoRA，也不通过扣时制造有利结果。

## 5. “100 Mbps 机房限制”的事实裁决

2026-10-20 只读复核得到：

- 本机 `eno1np0`：sysfs speed `1000`、duplex `full`、operstate `up`、carrier `1`；
- 远端 `eno1`：sysfs speed `1000`、duplex `full`、operstate `up`、carrier `1`，
  `ethtool` 同时显示 `Auto-negotiation: on`、`Link detected: yes`；
- 远端制品服务当前为 inactive，复核未改变服务配置或实验状态。

因此，不能确认机房永久只有 100 Mbps。历史 D77 的 100 Mbps 是旧时刻、旧协商
状态（当时对端只通告 10/100）的独立证据，可能与端口、线缆、自动协商、接口
状态或重启前后变化有关；现有证据不足以指认唯一物理原因。历史 100 Mbps 与
当前 1 Gbps 工作点不得池化为一个“平均带宽”，论文也不得声称测过 10/100 Gbps、
400 Gbps 或 H100。

当前结果应标明真实的 `1000_full` 链路。应用层限速敏感性可以作为单独工作点，
但不能冒称物理高速网络证据。传输延迟仍然计入在线请求时间线；链路较慢并不使
问题失效，因为它会在所有采用相同交付端点的系统中作为真实环境条件存在，而
PrimeLoRA 的缓存/驻留机制决定了每个系统实际承受多少次传输。

## 6. 为什么必须做 profile coverage/export 审计

此前的运行画像并未覆盖所有可达的 `(admission edge, output-length)` 类别。D698
离线审计发现 160 个预登记 service classes 中只有 130 个已有样本，缺失 30 个；
若直接继续运行，系统可能使用邻近类别、插值或默认值。这样得到的时延和资源
差异无法判断来自 PrimeLoRA 机制还是来自画像缺类，属于测量资格缺口，而不是
可以用平均值补齐的小问题。

D701 在同一 source-spec、trace、adapter 身份和运行合同下补齐了缺类，并严格
导出 160/160 service classes 与 96 个 measured preparation classes；导出器拒绝
插值、邻近类别和零值默认。D702 的 100-request smoke 验证了运行时可加载，D703
的 4,000-request 回放没有 profile fallback，且相对 D682 的改善可被审计为同一
生产父版本在完整画像下的观测变化。

这项审计不等于算法创新，也不把 D703 自动变成 G1；它的作用是先排除“测量画像
缺失”这一替代解释，使后续优化和 baseline 对比具有可比的证据基础。

## 7. 当前进度与尚未完成项（论文实验表述）

### 已完成

- 远端交付 v4 的计量边界已冻结：请求触发传输计入，部署/管理员打包隔离；
- D701 3B profile coverage/export：160/160 类别闭合，无插值/默认；
- D702 3B qualification smoke：100/100 原生合同通过；
- D703 3B full W0：4,000/4,000 终态，3,995/4,000 联合 SLO，远端 132 次
  预发布 gzip 传输、请求期打包为 0；
- D703 相比 D682 的 SLO、尾延迟和物理 GPU 时间改善已封存，原始数据未覆盖。

### 当前工作

建立独立的数值 LoRA 正确性证据，优先复用已有 7B/3B 权重、adapter、prompt、
trace 和固定生成合同；先做最小验证，再决定是否需要新的完整回放。任何参考
路径都必须记录模型/adapter 内容 SHA、后端版本、token-source、比较规则和失败
样本，不把 token 长度或 HTTP 成功当作 correctness。

### 尚未完成

- 3B PrimeLoRA 的 `n_correct` 独立资格及 G1 排名；
- 3B 的 W1/W2/G2；
- 按冻结顺序恢复的 ServerlessLLM、vLLM、S-LoRA、dLoRA（有限）、Loquetier、
  HydraServe 主比较；
- 同合同比较后的 PrimeLoRA 有证据优化、核心消融、churn/带宽/预算敏感性和
  最终论文图表。

在数值正确性证据闭合前不提前进入 baseline 胜负比较；这不是停滞，而是防止把
“服务完成”误写成“adapter 数值正确”，从而避免后续所有 GPU-s 和 SLO 结论建立
在不可验证的分母上。
