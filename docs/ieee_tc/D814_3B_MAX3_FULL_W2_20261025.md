### 已定位的失败链与仍待验证的原因

1. `req_03285`涉及`writing_lora_0419`。远端响应头已返回，声明归档
   2318346B、解包payload37453100B，但本地预分配失败，客户端接收0B。
   日志错误为`local file capacity conflict: retained copies plus transfer exceed tier budget`。
2. 随后residency准备链再次提交同一失败搬运；`OwnedMovementQueue.submit`
   按既有规则拒绝自动重试，后台任务错误由control路径抛出，整轮退出。
3. 外置回放器后续才记录连接断开。`launch.json`原始分类仍保留
   `protocol_or_launcher_error`；不能据此将更早的服务层错误归为外部污染。
   outcome无cleanup/measurement errors，工作区收尾已完成。

当前代码证据：`_ensure_local_async`的demand miss没有传入replacement
epoch；`LocalSourceReferences`默认`planned_only`，而`_prepare_file_allocation`
中的自动回收只在有replacement context或`demand_lru`时执行。另一方面，
GPU/HOST准备的中间NVMe搬运也未必属于当前file objective的candidate。
这是需要以既有fixture复现的执行缺口假设，尚未证明本轮每个阻塞副本均可
安全驱逐。不把关闭完整性错误、更换缓存策略标签或扩大预算作为修复。

对照已有历史：D277解决的是GPU准备lease/请求witness绑定，不是文件层
容量；D449增加的是ElasticLocality普通LRU，不能把Full改名套入。D680等
后续HOST传递优化也未改变这一按需NVMe入场语义。下一应核查既有文件预算、
引用与替换测试，构造同预算、存在可回收副本的最小反例，再决定正式修正。
保持IEEE九公式、真实footprint、引用保护和跨W0/W1/W2同配置。

联网参考已核查：[vLLM官方LoRA管理实现](https://docs.vllm.ai/en/v0.20.0/api/vllm/lora/worker_manager/)
显式处理入场时的cache capacity与eviction；其原生CPU LoRA缓存不等同于
本项目文件层，不能直接照搬其短暂超容量行为。
[dLoRA原文入口](https://www.usenix.org/conference/osdi24/presentation/wu-bingyang)
将请求和adapter动态编排联合考虑，但不能替本项目证明具体回收实现正确。
下一优化仍需针对本轮失败路径和当前固定vLLM版本核查，而非泛称借鉴论文。
