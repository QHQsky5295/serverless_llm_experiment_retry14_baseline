# D715：未达到95%的系统如何比较，以及避免无限SLO优化

日期：2026-10-22。回应用户最新目标：先分析评价体系，不立即启动下一优化。
本文件是分析与执行顺序建议，不是新冻结协议；没有修改PLAN、V1/V2、D648
阈值、代码、配置或历史结果，没有新增GPU实验、工件或负载。

## 1. 结论

**95%是特定服务质量承诺的约束，不是系统能否进入比较表的门槛。**
baseline未达到95%，PrimeLoRA达到95%，仍然能比较；两者都没有达到95%，
也能比较实际达成率、尾延迟、资源及取舍，只是不能声称已满足该服务要求。
不必把baseline优化到95%，也不应把所有后续实验永久阻塞在PrimeLoRA跨线前。

区分三层：

1. 数据是否可解释：输入、生成、身份、计时、资源、实现范围有效；具体异常
   先修复。不能用性能低证明复现错误，也不能用HTTP成功证明数值正确。
2. 实际表现如何：所有合法观测都报告完成状态、联合/边际SLO、尾延迟、GPU-s。
3. 是否满足特定承诺：G1/G2的95%和75%只用于相应约束下的判优；不达标标明
   不可行，不能删行或把低资源自动写成达标节省。

建议采用“完整资源—质量比较＋明确服务档位的条件性结论”，不恢复CE唯一排名，
不因为3B目前93.60%而把主阈值改为90%或93%。实际最优只能限定在已测配置。

## 3. 推荐的评价结构：无需先把全部系统调到95%

### 3.1 完整观测层：所有系统都展示

同一模型、负载、生成和资源包络下，报告：

- 正常完成/原生合同完成/独立数值正确性分别列示；未知不能补成通过。
- 联合SLO达成A、TTFT边际达成、TPOT条件达成及明确分母。
- 平均/P95/P99 TTFT、TPOT与E2E，失败/截断单列，不以成功子集掩盖失败。
- 真实生命周期GPU时间U、每请求资源、实际U/U_ref。
- SLO goodput及good requests/GPU-s作辅助，不替代原始A与U。

对已正确完成的相同N请求，R=U/N；如果正确性只能证明原生合同，列名须写成
GPU-s/native-contract-request，不擅自填N_correct。中止运行仅报告U_obs，
不能与完整生命周期形成虚假低资源排名。

在(A,U)平面，若某点A更高且U更低，可称在这两个观测维度上支配另一点；
不能由此宣称TTFT所有分位数或未测配置也被支配。一高一低则是取舍，不强造
唯一冠军。只拥有离散配置时展示观测点，不插值成未测的最优前沿。

### 3.2 条件性结论层：G1/G2继续保留

\[
I_r=z_r\mathbf1[TTFT_r\le\theta^T_r]
             \mathbf1[TPOT_r\le\theta^P_r],\quad
A=\frac{\sum_rI_r}{N}.
\]

该写法适用于多token正确完成请求；失败先判零，单token仅查TTFT，缺关键
证据为未合格/未知而不是默认通过。不能平均或相乘两个边际达成率。

\[
U=\sum_d\int\mathbf1\{\text{服务实际持有物理GPU }d\}\,dt.
\]

对各系统已测配置集合X_s，G1只在全部正确完成且A≥q的点中比较U/N：

\[
R_s^*(q)=\min_{x\in X_s:\,N_{correct}=N,\,A_s(x)\ge q}\frac{U_s(x)}N.
\]

X_s不是该系统一切可能配置；只有一个合法点时不是全局寻优结果。空集写
“未观察到满足该要求的配置”，不编造资源值或把某次不可行泛化为系统不可能。
既定q=0.95保留，0.90/0.99是既有敏感性档位，不追随结果挑档。

G2另检查U≤ρU_ref（既定ρ=0.75），在满足共同质量要求的W1/W2点比较P95
TTFT，另报联合达成差。预算是上限，不是所有系统实际GPU时间相等；若只有
PrimeLoRA可行，只能证明该点可行，不能宣称已证明对全部系统的同预算尾部
支配。ρ=0.5/1的既定敏感性保留。

### 3.3 不同未达标情形的正确表述

| 观察 | 可以说什么 | 不能说什么 |
|---|---|---|
| PrimeLoRA≥95%，baseline<95% | 此负载/配置下PrimeLoRA满足要求、baseline未满足；并列资源与延迟 | 必须继续优化baseline才可比较；未测配置都不可能达标 |
| 双方均<95%，PrimeLoRA质量更高且资源更少 | 该两个观测维度更好，但尚未满足95%服务要求 | 已完成G1/G2达标主张 |
| PrimeLoRA资源少但质量也低 | 明确量化资源—质量取舍 | 仅凭省资源或CE高宣告系统最优 |
| 双方均≥95%，PrimeLoRA资源少但尾部较慢 | 满足同一最低服务要求的资源效率更高，附尾部损失 | 所有质量指标都更优 |

### 3.4 阈值敏感性优先离线复用

完整可靠请求日志允许重算所有系统的A(k_T,k_P)，共同缩放既定TTFT/TPOT
阈值，不改变其实际运行。主点仍k_T=k_P=1；这不是把慢系统的SLO单独放宽。
相同缩放k下，对正确完整记录可用

\[
m_r=\max(TTFT_r/\theta^T_r,TPOT_r/\theta^P_r),\quad
k_{95}=Q_{0.95}^{Type1}(m_r)
\]

描述达到95%需要多宽松的共同要求。单token只取TTFT项；不完整/失败不能仅
对成功子集求该分位数后冒称全体达标。它是已有SLO敏感性的摘要，不替代绝对
时延，不是新的优化目标；本轮未计算或发表k95结果，也未重新选择工作点。
固定一条到达trace的完成吞吐不等于最大可承载输入率，后者仍需既定到达强度
实验。离线预算切片不产生新的在线资源配置。

## 5. 停止无限优化：对流程的建议，不偷换成功定义

已批准的规则继续适用：每个假设默认最多两轮最小验证；相同冻结性能键只跑
一次；没有新证据不重复；baseline完成必要适配后停止性能调参。

建议下一阶段先整理3B全部可复用的同合同比较，补齐必要的缺项，再根据差距
决定唯一PrimeLoRA候选；不要把“PrimeLoRA先95%”当成开始比较/机制分析的
永久先决条件。这是排程建议，尚未以本文件擅自替换旧计划的执行顺序。
用户明确确认后应追加非破坏性执行修订，冻结V1/V2本身不需改动。

每个候选事先写明瓶颈、预期改善、资源/尾部副作用、验证和停止条件。
验证失败就封存，不把大量工程工作当成性能改善；有新因果证据才开启新候选。
到达阶段检查点仍未95%时，可以形成完整比较、机制证据和适用范围；不能把
它写成G1/G2全部完成。论文可收窄为实测资源—质量优势，而非承诺所有模型/
负载/指标第一。任何有限实验都不能保证全局最优或投稿接受。

具体不做：因看到93.60%调低q、用各系统自己的慢warm参考放宽要求、删低分
baseline、忽略TPOT改用TTFT单项、用CE补偿漏请求、重复相同配置直到赢。
