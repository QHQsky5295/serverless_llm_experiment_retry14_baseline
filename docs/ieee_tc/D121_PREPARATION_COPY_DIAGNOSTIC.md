# D121 — 准备状态复制开销的边界诊断

本轮结论：同步状态处理确实会推迟同线程回调，但尚未证明它是当前
7B 排队的主因。**不接受生产优化，不改变并发、超时、公式或保护机制。**
这是 P2/P3 的 CPU 诊断，不是新的 Full、S10 正式结果或 baseline 比较。

## 问题与既有证据

D120 发现 7B 积压早于首个失败及隔离，成功请求的原生生成阶段平均
3.739 s，而从请求门槛通过至外层终态平均12.152 s。后者含准备、通信、
收尾和调度，且不是精确的门槛释放时间；不能把差值直接当 CPU 时间。
D110 的旧3B剖析提示状态整理开销，但随后实现已经改变。

当前 `owned_preparation_inputs` 冻结原生/文件状态时进行深复制、规范
JSON 编码和 SHA；执行入口再次复制计划。复制确保别名不污染已经冻结的
状态，哈希绑定输入，不能只为加速而删除。

先对 D119 的60,920,330 B普通结果作有界检查：完整遍历发现17处
`native_lora_sources_v1`，均是没有完整 footprint 的事件观察；没有保存
`source_view` 或完整准备 epoch。因此没有把这些摘要重构成“实测完整计划”，
也没有再次扫描或投影9.48 GB原始结果。

## 可复用状态与测量

复用 D88 已保存、由 D89 manifest SHA绑定的两模型真实原生状态，按
HOST allocation 数选择最大已保存完整视图。它们不是 D119 最大在线状态：
3B只有8个已注册adapter，7B只有2个。没有构造更多adapter或复制权重池。

每次只执行一次 `deepcopy → canonical JSON → SHA256`；同一个事件循环
预先排入一个回调，观察这段不让出执行权的操作推迟回调多久。三次均保留，
不删除第一次较高样本，不计算seed CI。复制内容/哈希不变，并检查修改复制件
不影响原始嵌套源身份。

这里仅测原生视图组件，不包含500制品文件视图、磁盘检查、DP、RPC或完整
准备执行。首次较高值可能包含分配/GC等影响，本次未分离，不能指定其原因。
不能按24/2等比例外推，也不能用这六次CPU样本推导Full加速比。

参考的机制依据是 [Python 3.12 asyncio的阻塞任务说明](https://docs.python.org/3.12/library/asyncio-dev.html#running-blocking-code)：
事件循环内的同步计算会阻塞其他回调。参考
[vLLM 0.30.0 core client源码](https://github.com/vllm-project/vllm/blob/v0.30.0/vllm/v1/engine/core_client.py)
的异步前端与独立core分工，但不能因此直接把本项目共享owner的可变操作送入
线程；快照、取消、成员和预算重检查必须仍然正确。

## 安全、失败和决定

- 3/4 GiB高/硬限制、swap0、CPU2,3,26,27。实际测量4.88 s，RSS911232 KiB，
  exit0，高内存/OOM事件0；没有GPU或远端服务。
- 第一次结构遍历启动因未显式taskset而在亲和性检查退出，尚未分析；保留日志，
  后续仅显式绑定既定CPU，没有改变资源包络。
- 第一次复制小测在读取前拒绝了253 MB的3B源文件（脚本的128 MiB通用上限），
  没有测量结果。核对D114已在同包络解析该源且峰值低于1.7 GB后，改成两个
  已知文件的精确大小+SHA检查；4 GiB硬限制未变。失败源码/日志保留。
- 不新增生产补丁，不更改超时，不删复制/校验，不进行GC关闭或缓存状态陈旧化。
- 下一步只安排一个**当前7B、既有1000请求开发前缀的定向CPU剖析**，复用现有
  profiler/runner和合法真实远程路径；它是诊断，不与普通Full作性能排名。
  获取实际准备/选择/文件观察的耗时证据后再选择一个候选。若证据不支持，
  归档该假设，返回请求并发与准备流程协调问题，不重复本次小测。

主线仍是 Prime IEEE Full→warm/Resident→恢复baseline→M1/M2→消融与敏感性。
当前3B已完整原生生成但存在大额排队；7B尚未全部完成。正式SLO、数值adapter
资格和全套对比尚未通过。一次性交付缓存D78/D80已经完成，禁止重建。
