# D1005: 3B max-four-replica outcome

## Decision

D1005 is a complete, auditable 3B W2 replay using the retained D1000
non-blocking arrival-prefetch path and one changed control parameter:
`max_instances=4`, equal to the number of visible RTX 3090 GPUs.  All 4,000
requests completed and all physical leases were released.  The candidate is
**rejected** as the current PrimeLoRA development point because it is worse
than D1000 on both frozen common joint SLO and physical lifecycle GPU time.
No baseline comparison or figure uses D1005 as a winning result.

## Frozen contract

The trace, adapter map, model, generation contract, preparation/service
profiles, remote endpoint, prepublished-gzip delivery, resource envelope and
nonblocking confirmed arrival-prefetch semantics are unchanged from D1000.
The complete replay uses a new execution key
`d1005_3b_max4_route_confirmed_w2_full`; the earlier 100-request smoke has a
separate key and is not combined with the 4,000-request result.

The launch receipt reports successful service, replay and watchdog return
codes.  The physical sidecar reports `measurement_complete=true` and an empty
`open_lease_ids` set; post-run GPU queries show no experiment compute
processes.  The D648 common-SLO reanalysis is source-bound and passed its
integrity checks.  This remains a development observation because independent
numerical adapter correctness is not established by the fixed-output timing
contract.

## Mechanism diagnosis

Increasing the replica ceiling did reduce the ready-idle component, but it
did not reduce the critical tail.  Relative to D1000, D1005 recorded:

| component | D1005 | D1000 |
|---|---:|---:|
| mean dispatch/admission wait | 330.21 ms | 303.85 ms |
| P95 dispatch/admission wait | 1,114.39 ms | 1,021.11 ms |
| mean ingress queue wait | 278.14 ms | 262.80 ms |
| P95 ingress queue wait | 876.75 ms | 817.69 ms |
| mean runtime-slot wait | 227.11 ms | 221.85 ms |
| P95 runtime-slot wait | 712.66 ms | 693.81 ms |
| P95 scale-up-affected TTFT | 2,934.47 ms | 2,397.20 ms |
| physical active GPU-s | 8,429.593 | 7,633.314 |
| physical idle-ready GPU-s | 1,285.055 | 1,629.550 |

The control trace performed five scale-ups and four scale-downs, including
transitions to four replicas and back to three.  D1000 performed four
scale-ups and three scale-downs and never needed a four-replica state.  Thus
the extra capacity did not supply a stable service lane; it increased active
GPU lifetime and scale-up first-service exposure while leaving queue and
dispatch tails higher.  This rejects the simpler explanation that the D1000
shortfall is caused solely by a hard three-replica capacity ceiling.

The result does not prove that four replicas are universally harmful.  It
rejects only this unchanged controller plus max-four setting under the
frozen 3B W2 trace.  The next optimization must address the observed
scale-up/scale-down oscillation or first-service path with an explicit
observable rule, and must be tested against D1000 on both joint SLO and
physical GPU-s/request.

## Next step

Do not start ServerlessLLM, HydraServe, Loquetier, or other baseline runs yet:
3B PrimeLoRA has not reached the frozen qualification target.  The next
candidate should retain max=3 unless a controller-level hypothesis justifies
otherwise, and use existing queue, active-load, first-service and readiness
observations to prevent a scale-in/scale-out cycle from exposing cold
replicas to requests.  No manual request subset, threshold change, or result
selection is allowed.
