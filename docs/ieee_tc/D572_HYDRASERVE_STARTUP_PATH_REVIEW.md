# D572：HydraServe 实际加载路径与扩容期间的请求分配

2026-10-16。继续复用D510/W0和D546/W1，没有新推理运行、参数变更、

控制行为、场景资源模型和本机适配引入的额外等待。

## 本机backbone路径不能按远端LoRA链路解释

共享内存每次分配13476855675字节，其中8字节是进度计数，实际交付内容为
13476855667字节。按完整预加载span计算，W0/W1平均有效交付速率分别约
19.754／20.237 Gbit/s。这是**本机provider→loopback→共享内存路径的应用层
有效速率**，包括查询、子进程启动、发送、接收及完成轮询，不是外部NIC吞吐。
原生provider日志标成GB/s，但源码实际除以1024³，本分析按GiB/s解释。

原生资源模型的`network_gbps=1`用于backbone模型获取；它不能直接用远端
LoRA物理1G链路代替。本机真实预加载约5秒，模型按13GB/1G预测约104秒，
说明输入含义确实不匹配。但单物理节点仍独立约束pp1；当前没有对照证明
只校准此参数会改善SLO，因此不直接设一个大带宽、强迫pp2或宣称收益。
[原生网络资源模型](https://raw.githubusercontent.com/LLMServe/hydraserve/8ae605de354ccfa2e9095514cdb4a9e9c56aa56b/scripts/kubernetes/vllm/src/resource_manager.py)

后续校准须采用真实执行路径和并发共享关系。两个同宿主逻辑节点不能各自
重复领取完整测得的本机带宽，也不能把两个地址写成两台物理服务器。

## 原生控制循环与适配锁分别处理

原生`check_model_loop`先检查可用实例，再等待cold-start任务完成，之后才
再次分配排队请求。D572观测到初始化期间旧请求仍完成、却没有新分配，与
这段控制流程一致。这不是本机wrapper新增的等待。保持原生机制的对照不能
悄悄改成另一种扩缩容／分配策略，也不能把全部影响归为GPU算力不足。
[原生调度代码](https://raw.githubusercontent.com/LLMServe/hydraserve/8ae605de354ccfa2e9095514cdb4a9e9c56aa56b/scripts/kubernetes/vllm/src/scheduler.py)

另外，本机`IsolatedPodmanPlatform`当前用同一把锁覆盖创建、地址查询及整个
容器删除过程；删除包含`stop --time=10`和实际释放核查。已有命令回执可见
多次worker stop约11秒，原生create-pod阶段尾部为13–17秒。这构成具体的
**适配层全局串行化假设**，但尚未以逐操作时间线或隔离测试证明每次尾部都
由该锁造成，不能直接把这11秒从实测时延中扣除。

下一项最小验证应复用现有平台测试，检查“删除无关worker期间，另一worker
创建／地址查询是否被全局锁阻塞”。若确认，改为短资源登记临界区与逐worker
生命周期互斥，保留同worker取消安全、真实release、关闭顺序和全部资源限制；
不减stop保护时间、不提前虚报释放、不改原生placement/autoscaler公式。
这是比直接改原生算法更明确、可证伪的适配方向。验证通过后新版本资格及
受影响完整运行另登记，旧结果永久保留。

## 证据边界与主线

- create/coldstart原生日志只保留0.1秒精度，表中汇总不代表更高计时精度。
- 原生executor的load-model平均约0.471／0.551秒，包含其自身加载过程；
  预取、进程创建、共享内存加载彼此重叠，不能相加伪造总体启动时延。
- D570中的逐步execute host span仍不是纯CUDA时间；本次没有测量或减去
  SSE计量开销，也未证明它解释TPOT退化。
- 独立数值正确性、完整pp2→pp1与LoRA/KV迁移资格仍未关闭。
- 现有rootless Podman接入继续复用；不访问、不更改其他项目k3s。
