## 1. 目标环节是否确实缩短

复用 D662 已修正的 scheduler/owner/lease/epoch 分域核查和单调事件链。
D665 全部1411 HOST、1839 GPU链通过，无缺失填零、无不变量错误。

| 同一请求且两轮同来源路径的条件比较 | 数量 | D660 | D665 |

| HOST acquired→post-snapshot 平均，ms | 884 | 83.110 | 1.320 |
| HOST 平均 TTFT，ms | 884 | 986.067 | 890.117 |
| HOST 联合达标数 | 884 | 797 | 799 |

| GPU 平均 TTFT，ms | 1428 | 675.790 | 686.416 |

D665真正触发新HOST事务的1392条中，目标段均值1.322ms、P95 1.455ms；
最后加载均值15.746ms。结果支持“减少该事务中的重复后检查”，而不是
“加载加速了约80ms”或“全系统因此达标”。相同HOST路径的884条中两轮实际
调用最后加载的数量为881/880，其余为合法复用；加载时间均值15.731/15.697ms，
并没有同量级变化。

来源路径、batch和占用轨迹均为运行后产生的条件，不是固定控制变量；上述
条件比较不构成随机因果效应。不能从旧TTFT减去81.79ms构造反事实结果。

## 2. 为什么均值下降而联合比例下降

按相同 request/adapter/arrival/prompt长度/target/阈值逐条匹配：

| 联合状态变化 | 请求数 | 旧平均TTFT | 新平均TTFT | 旧平均TPOT | 新平均TPOT |
|---|---:|---:|---:|---:|---:|
| 达标→达标 | 3253 | 761.964 | 725.502 | 16.066 | 15.931 |
| 达标→违约 | 322 | 903.059 | 1880.961 | 16.477 | 32.533 |
| 违约→达标 | 297 | 1932.465 | 812.953 | 32.037 | 16.531 |
| 违约→违约 | 128 | 2584.631 | 2686.413 | 23.502 | 24.819 |

所有时间单位为ms。净少25条不是全体请求一致变慢：两边跨阈值的集合都有
较大等待变化。322条新违约的均值增量分布在arrival→release（225.185ms）、
runtime-slot阶段（339.169ms）、admission→engine（269.851ms），并有decode
间隔增加；297条恢复的对应阶段反向变化。此分解解释计数与均值不矛盾，
**不证明这些变化由HOST优化造成，也尚不能把等待分配给某个具体函数**。

## 3. 剩余问题主要是稳态服务路径，不能只归因于扩容或远程

D665全部450条联合违约在其arrival→first-token区间均不与自然扩容区间
重叠。GPU已就绪组仍有146条联合违约，其中95条TPOT违约。180条TPOT违约
中148条输出不超过31个token；短输出更容易被少数长停顿拉高请求平均TPOT，
但这一解释需要原生执行/控制路径证据，不能从文本chunk间隔推造kernel停顿。

| D665阶段均值，ms | 全部4000条 | TTFT-only的270条 | 联合违约450条 |
|---|---:|---:|---:|
| arrival→release | 129.891 | 411.146 | 312.237 |
| runtime-slot阶段 | 268.800 | 566.699 | 518.380 |
| admission→engine dispatch | 270.358 | 1253.090 | 914.220 |
| engine-entry→queue | 59.117 | 116.087 | 131.317 |
| native engine queue | 5.181 | 15.160 | 17.229 |
| native prefill | 108.585 | 116.542 | 123.597 |

`runtime_slot_wait`是已定义区间，并非已证明纯槽位耗尽；上述span含IPC、调度
和控制工作，不等于函数CPU耗时。RPC wait-response与事件链重叠，不重复相加。
运行中来源不同也不能当成仅改变tier的受控消融。

资源缺口同样未消失：到达窗1888次控制检查中，queue低条件1658次、active低
条件1886次，但TTFT低条件0次、all-low 0次；自然扩容3次，无缩容。当前控制
P95最小874.472ms，仍高于既有3B缩容下阈值219.518056ms。此处只解释现象，
不据此放宽缩容阈值、共同SLO或复制7B配置。降低无效等待仍是质量与持卡的
共同研究方向，不保证解决后一定达标。

## 4. 决定与有界下一步

- D663的目标环节已被真实路径验证，局部收益记录保留；它不是整体性能验收
  成功，也不凭一次SLO下降断言该改动必然有害。本轮不新增或堆叠候选。
- 下一项仅核对已测共同等待路径的调用关系、旧D329/D352/D595/D610/D628/
  D635约束和官方vLLM实现，判断等待发生在新鲜状态观察、控制回执还是native
  调度边界；先形成一个可证伪的新假设和安全适用域，再决定保留/撤销/替换。
  不直接重跑D665、不扩成无界profiling，不另开独立数值oracle支线。
- 不把0.625个百分点解释成显著退化；不筛选赢家、不改SLO、不改指标分母，
  不按请求组挑选性能结论。下一有实质改动的新版本才重新资格及完整回放。
- 主线仍3B W0；3B W1/W2/基线/dLoRA、同版本7B、A1–A5、S1–S13、成本/
  审稿文档与最终图表全部保留。遵循用户后续要求，当前只保存数据，不画图。
