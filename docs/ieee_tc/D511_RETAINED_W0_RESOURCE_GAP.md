# D511：完整基线比较后，PrimeLoRA 剩余资源差距定位

2026-10-14。HydraServe D510 和七系统 W0 比较已经完成。当前按最新顺序
回到 PrimeLoRA 优化。本项复用 D476 全部 4,000 条请求及物理生命周期，
不重跑性能点、不改服务、基线、公式、配置或冻结指标，不生成图。
分析沿用 D473 请求分解、D454 控制/物理区间算法与既有验证函数。

## 1. 问题与完整资源分解

D476 联合 SLO 为 97.425%，ElasticLocality 为 95.775%；两者满足共同
95% 门槛。PrimeLoRA 的物理 GPU-s/request 为 2.694612，仍高于
ElasticLocality 的 2.473179，差 8.9534%。这不是改变 CE 或延迟阈值
可以解决的问题；G1/G2 和未知数值正确性限制保持原样。

| 互斥生命周期窗口 / GPU-s | PrimeLoRA D476 | ElasticLocality D453 | 差值 |
|---|---:|---:|---:|
| 业务前 | 34.824232 | 46.442574 | −11.618342 |
| 共同到达窗口 | 10713.984914 | 9677.612534 | +1036.372380 |
| drain | 2.330582 | 2.623431 | −0.292848 |
| 终态后释放 | 27.309074 | 166.037331 | −138.728257 |
| 总量 | 10778.448802 | 9892.715870 | +885.732932 |

两者到达窗口均为 3963.908903 s；窗口内平均物理持卡分别为 2.702884
和 2.441432。以下是精确物理区间并集的 wall time，不是利用率或样本数。

| 同时持卡数 | PrimeLoRA 秒数 | ElasticLocality 秒数 |
|---|---:|---:|
| 1 | 380.400512 | 866.439698 |
| 2 | 1313.912691 | 1460.711556 |
| 3 | 1372.623779 | 657.280872 |
| 4 | 896.971920 | 979.476777 |

因此不能将剩余差距归咎于收尾拖延，也不能简单称为“一直开四卡”。
PrimeLoRA 的业务窗口持卡更久，主要表现为三卡状态较多、一卡状态较少。
这定位了差距所在，但不证明主动准备、路由或某一个控制条件是独立原因。

4,000/4,000 分解齐全，逐请求恒等式最大误差 0 ms；均值和 Type-1 P95
与 D476 封存结果吻合。没有重新定义 TTFT/E2E，或删除慢请求。

1. decode 差 467.140 ms，约为平均 E2E 差的 80.06%。这是差值的位置
   分解，**不是** GPU 计算或某机制的因果贡献率。异步模型执行、CPU 控制、

2. PrimeLoRA 的全局许可等待反而少 222.287 ms；继续单纯增加接纳容量，
   没有本项证据支持。额外到达等待/完成接收仍存在，不能只看 decode。
3. 相对 D472，decode 均值仅降低约 23.361 ms；D474/D476 的总体改善
   不能被解释成已经消除了原生生成路径的剩余开销。

## 3. 控制反馈与不能做的推断

两配置的 IEEE 控制设置完全相同；运行后端、batch/token/slot 等非机制
配置也相同。D476 新增 CPU 前端准备，其余差异为 Full/ElasticLocality
机制门控与独占路径；后者是复合内部对照，不是单因素消融。

| 业务窗口控制观测 | PrimeLoRA D476 | ElasticLocality D453 |
|---|---:|---:|
| 样本数 | 1923 | 1931 |
| 扩容决策 | 17 | 34 |
| 缩容决策 | 15 | 30 |
| ready > 1 的样本 | 1637 | 1161 |
| 上述样本中 all-low | 1101 | 990 |
| queue 非 low | 102 | 43 |
| active 非 low | 182 | 69 |
| TTFT 非 low 或未知 | 323 | 80 |

后三类可以重叠，不能相加成阻塞时间；控制采样不等于连续状态。较慢完成
反馈与更多资源驻留相容，但不能据此修改 TTFT/cooldown 门槛制造领先。
实际扩容轨迹、路由、缓存与请求组合共同变化，本项没有反事实因果证明。

## 4. 历史排除、官方依据与唯一下一项

已核对 D351/D352/D355、D455–D466、D472–D476：

- 纯 planner 已移出主线程，已有事务间交错、文件视图精简、CPU-only
  前端准备和两个有消费者证明的 identity 观察精简；不重复实施。
- D462 直接 Python CUDA pin 查询未获得稳定局部收益，保留拒绝；
  D463 单独候选 D465 未达 SLO，不用后续版本倒推其独立贡献。
- D329 禁止基于 epoch/model-ID 缓存可变物理 tensor 图；不改成 TTL，
  不删除 pinning、别名、allocator、预算、完成 fence 或来源检查。
- D386 更激进 queue trigger 增加资源消耗，不重开无依据阈值扫描。
- 当前生产代码相对 D476 启动提交没有变化。D456 栈样本和 D351 原生
  时序来自更早版本，不能冒称 D476 的当前 CPU 时间份额。

本轮在线核对了 [vLLM 0.30 core](https://raw.githubusercontent.com/vllm-project/vllm/v0.30.0/vllm/v1/engine/core.py)
及 [UniProcExecutor](https://raw.githubusercontent.com/vllm-project/vllm/v0.30.0/vllm/v1/executor/uniproc_executor.py)：
原生控制调用和模型推进共享执行路径；CPU utility 与异步 GPU 工作可重叠，
主机包络不能等同 kernel 时间。[vLLM 的 CPU 开销分析](https://vllm.ai/blog/2024-09-05-perf-update)
支持分离这两类证据，不用于外推其加速数字。

**下一项仅做一次当前 D476 配置的原始前 1,000 请求原生时序诊断。**
复用 `CoreHostTiming`、已有受限 runner、D351 分析器；不开旧 Python 栈
采样，不换 profile/容量/控制/SLO，不新增权重或负载。详细观测包含开销，
不与普通 Full 性能排名，也不据前缀外推整轮资源。

需要回答的可证伪问题：剩余 decode 包络是否仍主要被同步 native utility
占用，具体是哪类当前操作？按 operation 的线程 CPU/host 时长和请求
decode 窗互斥分解回答。如果主要时间落在 step、utility 不足以解释停顿，
停止机械精简 snapshot，转向已有批次/迭代证据。禁止在诊断之前堆新补丁。
本项没有预定优化必然奏效，也不授权重复同键直到出现有利结果。
