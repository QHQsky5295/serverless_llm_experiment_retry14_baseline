### 资源增加的精确账目，而非未经证实的因果归因

复用D823配对阶段和D297物理区间方法，完整4000请求保留。父版两个扩容GPU
在业务起点后322.538/324.645秒开始持卡，本轮为9.040/11.097秒。逐卡分解：

`+625.276862 GPU-s = +626.144961（更早分配）−0.868099（更早释放）`。

两轮均没有缩容释放间隙。因此额外占用不来自较长drain或更慢收尾；主要
来自更早扩容。D866两次scale-up均记录`submission_request_index=1`，D858
为208/217，触发理由同为`ieee_max_score_above_one`。这只是实际触发/计费
证据，尚不能推出“整图优化必然导致早扩容”或“早扩容本身就是错误”。

联合状态配对有156条fail→pass，同时154条pass→fail，净增2；不是简单的
“修复了2条而其他不变”。原始分布、退化阶段与全部请求保留。平均TTFT的
18.031ms下降中，admission→acquired约下降10.161ms；arrival→admission
仍303.451ms，runtime-slot等待仍192.545ms。阶段层级中nested项不重复相加。
两轮自然控制的容量时间线不同，不能把全部时延差直接归因于单次HOST操作。
