## 1. 问题、方法与来源

问题：D465 新增派发前等待主要是申请容量前的执行滞后，还是申请后的
容量/恢复等待？在积压时，是否真的存在空闲接纳容量？

复用 `partition_retained_request_stages`、`summarize_dispatch_gate_intervals`
和 `summarize_dispatch_capacity_context`，不新建计量口径。每个来源逐一核验
完整 4,000 请求、相同输入/到达/prompt/target/adapter 合同、原生时钟和终态。
先保存十二段可加和分解，再以原 trace 的八个 500 请求阶段完整分组。
阶段编号在正文为第 1–8 阶段，JSON 为 phase 0–7。

`admitted_offset_s` 是后续 runtime reservation，不是全局 gate 恢复时刻。
申请→恢复仍混合等待 permit 和任务恢复延迟；已唤醒但未恢复的请求可能
已经持有 permit。确定占有下界为 gate-resume→native-completed；可能占有
外包络为 acquire-entry→terminal。下界覆盖采样容量只能证明该观测时刻
没有空位，不能恢复连续 grant/release。下界未覆盖时不等于确定存在空位。

压缩 outcome 由既有压缩回执映射，归档 SHA 和解压原 SHA 均再次验证。
所有 ready/unready activation 分开保留；不为缺失 ready 补时间戳。
D458 23 epochs=20 ready+3未ready；D465 22=19+3，其中各有一个 initial。

结果源 SHA：

- D458：`8d65bf7a9113909451d72a822098e1e464e27d031a7b0ea71357bf30fd52205c`。
- D465：`cb83dc960641a164be351680c8d69a54873491186eb1825b48afc0407393dd91`。
- 共同 SLO：`2d906f8aaf3fa1bf8cf30d116990db9970fb7be7bf1374fdbd1d8995090104f3`。

- D458 在 988.567386、1052.589883 s 缩容后仍有两个 ready 副本；
  1075.236740 s 起再次扩容，新副本 1120.092198/1122.666579 s ready。
- D465 在 888.855626、936.325544、995.810405 s 逐次缩到一个 ready 副本；
  1067.155597 s 起扩容，三个新副本在 1112.931743、1115.806099、
  1115.832834 s ready，实际 trigger→ready 为 45.737/46.519/44.516 s。
- D465 更早触发扩容、首次新副本也更早 ready，但仍有更长队列；不能只用

- 最长申请→恢复等待 20.276057 s 属于 req_01005；它在 1100.513270 s
  已恢复，早于新副本 ready。其全部等待虽然与启动重叠，却不是“等待新
  副本 ready 才恢复”的样本。原始恢复和目标副本身份完整保留。

支持的局部解释是：少副本驻留遇到突发段时，既有服务容量确实曾被占满，
新增副本尚未可用，形成积压。不能由此证明整轮退化都由扩容或 D463 一行
改动造成；微小实现变化与闭环轨迹变更不等于已经隔离的因果实验。

## 4. 历史/官方依据及下一主线边界

已核对 D337/D338 启动日志与 import 诊断、D342 容量积压、D359 接纳后
准备等待、D386 更激进 queue trigger 的负结果、D459–D463 控制成本。

- 当前 runtime capacity 已为 14，不重复 D342 后完成的 C8→C14 资格。
- D386 queue_upper 8→4 使 GPU 占用增加 23.50%，不能重开同类无新证据扫描。
- D338 已否定“删 sitecustomize 就能消除约十秒总启动”的推断。
  导入移到后面不等于工作消失；不重复同一导入微测。
- planner offload、checkpoint prefetch、AOT 缓存、同事务 HOST 观察复用、
  core-turn 交错均已存在，不包装成新优化。
- 当前 FIFO grant 在设置 Future 结果前转移所有权，release 会立即 grant；
  没有证据支持添加定时重试/强制唤醒补丁。
  Python 官方说明 [Future 回调通过事件循环调度](https://docs.python.org/3/library/asyncio-future.html#asyncio.Future.add_done_callback)，
  这支持“完成不等于任务已恢复”的边界，不证明本次恢复开销。
- 已在线核查 [vLLM 0.30 engine process 管理](https://raw.githubusercontent.com/vllm-project/vllm/v0.30.0/vllm/v1/engine/utils.py)；
  frontend 与 EngineCore 是不同启动层次，不能直接把 CPU import 时间当作
  可减少的整个 ready 时间。后续批量文献请求遭遇 HTTP429，未据未读内容修改代码。

本轮结束这项保留数据诊断，不再反复拆分同一尾部，也不重跑 D465。
D463 仍在工作分支中，但没有获得性能接受；下一版本须显式记录保留或撤回。

下一项优先核查 **CPU-only 初始化与真实 GPU owner 创建能否合法分离**：
当前每次 activation 从 fresh frontend 开始，是否能在同一服务资源包络内
提前完成与请求无关的 Python/frontend 初始化，随后才创建新的 GPU owner
及原生 core？这与删除 import 不同，尚未实现/验证，不先承诺节省秒数。

GPU 从真实保留至释放计费；不把 sleep/显存下降当作物理整卡释放。
对成功路径须验证初始化、取消、失败、设备身份与释放，再做新键最小原生
