## 二、当前服务质量问题在哪里

D688的172条TPOT违约中151条（87.79%）目标不超过31 tokens；共同短输出
总体仍为1106条，没有删除短请求或改变TPOT定义。151条的decode超过共同
许可时间的P50/P95为92.133/419.377 ms；其中73条GPU-ready请求分别为
83.301/429.660 ms。这是原生首末token计算的超额，不是已经测得可移除的CPU
耗时。完成通知延迟没有被混入TPOT。

183条仅TTFT违约请求的平均2533.969 ms分解如下；各项采用已有互斥阶段：

| 阶段 | 平均ms |
|---|---:|
| 计划到达至释放给服务 | 394.902 |
| 释放至acquire | 102.878 |
| acquire至resume | 0.063 |
| runtime slot路径 | 549.326 |
| controller admission至engine dispatch | 1291.953 |
| engine入口至原生队列 | 82.029 |
| 原生引擎队列 | 1.989 |
| 原生prefill | 110.829 |

`runtime slot`路径还含路由、状态确认、引用保护和重选，不是纯容量排队。
admission→engine也不是纯GPU计算；这里不能用阶段名称直接认定某锁或函数
导致全部等待。最大的后端原生队列并不是本分组的主要耗时，下一项必须检查
进入原生执行之前的控制工作及其消费者，不能无证据提高batch/timeout。

355条联合违约都不与自然扩容trigger→engine-ready重叠，不等于都已排除
初始激活、扩容后的缓存/路由反馈或后台准备影响。它只能否定“全部主要违约
直接发生在自然扩容尚未ready期间”的简单解释。GPU-ready子集也不等于零
控制或无并发干扰，因此不能仅靠减少远端fetch解释全部问题。

## 三、为什么资源仍接近四卡常驻

D688在业务第11.000、13.100、15.170秒作出三次scale-up；首次queue=0、
active=0，窗口只有一条已完成样本，P95 TTFT7540.972 ms。三次扩容均由
TTFT/5000>1触发，不是队列超过上限。保留这个真实冷启动反馈，不删掉样本。
首1000请求窗口平均持卡3.963147，后面三个1000请求窗口均持续持四卡。

|---|---:|---:|

实际TTFT下阈219.518056 ms来自旧source-only标定，当前控制输入是完整TTFT；
这个来源范围不一致已在D679说明。它支持重新审视配置依据，但不自动证明
数值错误，更不能从9段区间反推一个让结果达标的新阈值。必要条件分析仅使用
采样，不能证明采样间状态不变；缩容会改变后续负载，不能据此计算反事实
GPU-s或承诺95%/75%达标。本次不扫描阈值、不删除TTFT gate。

## 四、与原始实现及历史反例对应

本轮重新核对[vLLM 0.30.0 EngineCore源码](https://raw.githubusercontent.com/vllm-project/vllm/v0.30.0/vllm/v1/engine/core.py)：
`run_busy_loop`先处理输入再执行engine step，utility在client请求路径分派。
这说明同步控制操作可能影响下一次迭代的边界；它不是本项目耗时的测量证据。

仍按实际batch调用adapter管理器，不能用一次静态注册代替执行时绑定。

本项目已有`atomic_control_yield_v1`及原子HOST/GPU保护，不应再把“控制与
生成交替”作为未实现的新方案。D684观察到已有工作时的控制开销与短decode
重叠，但其观察器有开销，不能从普通回放扣除该时间。D329的pin/alias/隐藏
存储状态反例、D333中间状态边界、D595并发屏障退化、D628锁外验证退化，

仅借鉴“信号、目标和时窗应对应”的控制原则；它不是本项目TTFT毫秒阈值的
依据，也不能直接移植默认配置替代IEEE控制律。

下一工作限定为：复用D684已有控制操作记录，对`source_snapshot`、
`routing_source_snapshot`及请求保护的调用者/实际消费者作有界审计，寻找
