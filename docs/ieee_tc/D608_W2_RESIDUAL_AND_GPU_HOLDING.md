## 分析前固定的问题与边界

1. 将全部 4,000 请求按相同源序四等分，分别统计共同冻结阈值的联合违约、
   TTFT/TPOT 违约，以及完整同钟阶段分解。另按 dispatch 前 tier、激活实例
   和最大 TTFT 阶段作条件诊断；这些是内生分组，不是机制因果效应。
2. 比较逐请求的达标状态转换，保留改善与退化。按实际阶段报告差异，不从
   请求时延中事后扣除任何开销，不把某阶段最大说成它独立造成全部违约。
3. 直接积分物理 GPU 持有区间，按共同到达窗口及源序季度时间边界分解；
   报告各持卡数持续时间、释放空档及真实控制事件。少扩容不等于少占用。
4. 对已记录的控制采样核查 all-low 的 queue/active/TTFT 条件、连续低负载
   持续时间及实际缩容。采样比例不是连续时间比例；不能从相关性推断最优策略。
5. 与 D554 的差异是两个已知开发回放的描述性观测，非独立留出或重复实验。
   原始 N_correct=null、独立数值证明缺口仍保留；本分析不升级排名资格。

冻结口径：METRIC_PROTOCOL_FROZEN_V1 + METRIC_PROTOCOL_SINGLE_RUN_V2；
共同 SLO 使用 20261010_7b_slo_d394_frozen.json。G1/G2 不变，九公式不变。
只使用 D554/D607 已封存完整结果及闭合的物理账目；压缩历史流式读取并校验
解压后 SHA，不生成大体积临时副本。CPU 辅助域 3/4 GiB、swap=0、四逻辑核，
输出预算 32 MiB；分析前检查无 GPU 作业、已释放与保护清单，分析后记录真实
域关闭及资源峰值。若证据不能说明原因，明确保留未知，不直接追加候选。

全体请求的平均 arrival-release 从第一组 51.679 ms 增至末组 328.675 ms；
completion-return 从 63.436 增至 381.542 ms，native prefill 则从 203.460

逐请求状态转换完整保留：3534 条两次均达标、228 条由违约变达标、190 条

后两组两次都持续持有四卡，仍观察到尾延迟改善，因此改善不能全部解释为
这两个时间窗多用了 GPU；缓存/调度历史等其他差异仍存在，不当作独立因果实验。

## GPU 占用为什么增加

D607 到达窗口的 GPU-s 比 D554 增加 **451.491000**，全部来自前两组：
第一组 +321.387525，第二组 +130.103475，后两组差为零。准备、drain、cleanup
合计反而减少约 13.839325 GPU-s，故总量净增 437.651675（2.989%）。

D554 记录 7 次自然扩容、4 次缩容；D607 为 4 次自然扩容、1 次缩容。
D607 在业务开始后 748.387 秒重新持有四卡，并持续到业务到达窗口结束；
D554 的最后四卡连续区间从 1406.875 秒开始。少量更长的生命周期可以比
更多次短生命周期花费更多 GPU 时间，这与实际物理账目一致。

记录的控制条件解释了后段为什么没有回收：D607 的 1870 个到达窗口控制
采样中，1333 个采样同时满足 queue/active 低阈值，但 TTFT 低阈值不满足。
第二、三、四组分别有 333/394、292/363、456/589 个此类采样。
第三组没有 all-low；第二/四组观测到的连续 all-low 最大仅 12.471/18.833 秒，
未达到冻结的 38 秒回收冷却期。TTFT 下阈值为 2339.924886 ms、观测窗 45 秒。

这里 active 是已绑定请求/ready capacity，不是 GPU kernel utilization；
采样数比例不是时间比例。控制器的行为与冻结逻辑相符，本轮未发现“已经
满足回收判据却没有执行”的证据。不能为了降低 U 直接绕过 TTFT 条件、调低
共同 SLO 或取消冷却期。当前更有针对性的方向是消除抬高该反馈量的实际
准备/控制开销，再在同公式下验证服务质量和持卡时间是否共同改善。

## 复用交付记录：不能把准备阶段都叫网络时间

两次都为 497 次真实交付、418,365,205 线上字节，请求中打包次数为零。
客户端与服务端按 transfer ID/工件/字节一一绑定，时间只在各自同钟内相减。

| 每次交付的平均观测 ms | D554 | D607 |
|---|---:|---:|
| 客户端交付总时长 | 1596.465 | 1034.595 |
| 请求至响应头 | 3.852 | 3.870 |
| 本地预留、接收与写入 | 498.522 | 285.285 |
| 解包与内容校验 | 268.643 | 226.510 |
| 校验完成至发布完成 | 651.687 | 436.168 |
| 发布完成至交付函数完成 | 164.245 | 79.576 |
| 服务端 handler（与客户端重叠） | 481.080 | 270.571 |
| 服务端文件读取（嵌套） | 0.427 | 0.383 |
| 服务端 socket write（嵌套） | 480.112 | 269.633 |

客户端完整分段还包括 body→extract 与加载前余项，JSON 中全部保留；表中
服务端行不与客户端相加。发送调用阻塞会受接收端进度影响，故 socket write
耗时不能直接认定为物理链路带宽瓶颈。尚无逐请求因果映射将 497 个 transfer
分段等同于 201 条违约的分段，预取和合并等待可能不同。

本轮代码只读核查显示，响应头后执行本地预留，校验后还要经历发布容量和
身份检查；这些都属于系统准备路径，不能从 TTFT 中扣掉。D606 已减少单次
文件观测的路径对象开销；D608 进一步支持检查**所需新鲜文件观测的组织和
串行等待**，而不是放弃容量/身份/引用安全检查或重新制造异步兜底机制。
是否能复用同一有效事务内的观测、消除冗余工作，需要先核对历史反例、实际
调用边界和官方实现，再建立可证伪候选；本轮没有据此直接改生产代码。
