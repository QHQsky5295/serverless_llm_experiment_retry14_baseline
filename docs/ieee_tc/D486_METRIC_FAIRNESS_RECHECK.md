主线仍为 HydraServe 必要原生适配和实际结果 → 全部可用基线比较 →

## 1. 最终评价方式没有改变

令 a 为计划到达、f/l 为首/末原生 token、n 为实际原生输出数量：

- TTFT = f − a，包含实际排队、远端获取和准备，不以 backend-only TTFT 替代。
- TPOT = (l − f)/(n − 1)，n=1 时为 N/A，不将完成通知计入 decode。
- 每请求必须同时满足共同 TTFT、TPOT 阈值才计为联合达标；失败保留在
  4,000 个计划请求的分母中，不能用边际达成率的平均值替代联合值。
- G1：全部正确完成且联合达标至少 3,800/4,000，再比较 R=U/N_correct。
  U 为实际持有物理 GPU 的生命周期积分；同卡重叠区间取并集，不用利用率、
  显存比例、逻辑副本数或 idle 折扣替代实际持卡。
- G2：同时满足共同资源包络、完整正确、联合 SLO 和 U≤0.75U_ref，
  再比较 W1/W2 P95 TTFT，并报告联合达成率差值。W0 通过不意味着 G2 完成。
- CE、价格、goodput 为补充；不以 CE 第一或单项 TPOT 退化决定最终胜负。
- 一个冻结执行键一次性能观测，保留全部失败/旧版本；不补 CI，不筛重复赢家。

正式定义与证据边界继续以 METRIC_PROTOCOL_FROZEN_V1.md 和
METRIC_PROTOCOL_SINGLE_RUN_V2.md 为准。它们的 SHA 分别为
`5f0732ef54d629b40cece42bdbf536e8e74c6505e3ec5d4c7e8742408ad80f22` 和
`193bf1535af1aa50f83d98dc2e944ecbdc7bd27aa96baeca82f0654e02f9357d`。

## 3. 为什么“等待严重”与“全程达标”可以同时出现

| D414 ServerlessLLM 指标 | 完整 W0 观测 |
|---|---:|
| 请求／原生合同核验／失败 | 4000／4000／0 |
| TTFT 达标 | 3929／4000 = 98.225% |
| TPOT 达标 | 3996／4000 = 99.900% |
| 联合达标 | 3925／4000 = 98.125% |
| 平均／P95 TTFT | 973.686780／1052.246361 ms |
| P99／最大 TTFT | 23238.101457／79281.846124 ms |
| 平均／P95 TPOT | 26.736734／32.929275 ms/token |
| 物理生命周期 GPU-s | 16089.762743524276 |
| GPU-s／原生合同核验请求 | 4.022440685881069 |

71 个 TTFT 违约、4 个 TPOT 违约，共 75 个联合违约；本轮两类违约没有重叠。
95% 门槛允许最多 200 个联合违约，并不承诺每个请求、每个时间片都达标。
前 500 请求仅 446 个联合达标（89.2%），其 P95 TTFT 为 44.825548 秒。
这些请求完整保留；其后七个 500 请求段的联合达标数依次是
485、494、500、500、500、500、500。阶段仅为事后诊断，不是独立重复。

因此结论应是“该完整 W0 观测通过共同 95% 门槛，但启动附近存在严重尾部
等待”，不能写成“无冷启动问题”或“所有阶段都满足 SLO”。全程 P95 本身
无法描述最慢 1% 的恶化；同时报告 P99、最大值、违约数和预定义 W1/W2/A4
正是为了避免掩盖这部分行为，不是在看到结果后改变主验收阈值。

审稿中的平均 Dispatch Wait 约四分钟来自旧合同/旧控制路径，不能与 D414
的 98.125% 拼接为同一运行。当前完整运行平均提交后 dispatch wait 为
533.644773 ms，service TTFT 为 437.193547 ms；旧轮询/入口失败证据独立保留。
不以新结果抹掉旧结果，也不将旧等待无证据地归因为硬件或框架必然缺陷。

## 4. 公平性结论及不能省略的限制

已复核的时间定义、阈值、请求分母和联合运算没有给 ServerlessLLM 特殊
豁免。快解码不能抵消某一请求 TTFT 违约；高 CE 不能抵消失败。
后端版本不同是论文基线保真限制，应公开，而非给不同后端另设宽松 SLO。
最终跨系统比较仍须 join 输入、生成、资源、初态和远端合同，不只比较两个
百分数。此前已封存的同合同核验结果复用，不重复 GPU 实验。

原始 n_correct 未知、独立逐请求数值正确性未证明，保持未知。本轮重算
不把 HTTP 200、adapter 名称或目标数量等同独立数值证明；故上表资源分母
明确标为“原生合同核验请求”。资源积分复用 D414 已封存的 allocation/release
审计，本轮没有重新积分；完整内容/worker 校验也没有重做。主要零/重复权重、
单轮、已知开发 trace 的证据限制继续披露，不能声称独立留出或统计稳健最优。
