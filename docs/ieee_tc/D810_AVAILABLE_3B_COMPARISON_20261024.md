## 3. 支持什么、不支持什么

1. W0中，PrimeLoRA满足95%共同联合时延要求，其U比vLLM低7.8078%、
   比ServerlessLLM低7.6444%。这是达标观测点之间的资源差异，不是完整
   G1资格或跨场景最优。相对二者联合SLO低4.20/1.95个百分点；P95 TTFT
   分别为9.066/3.741倍，不隐藏服务质量取舍。
2. PrimeLoRA W0的U为75%预算的1.22923倍，仍超预算22.923%；要达到
   同一预算需在自身当前U基础上减少约18.65%。W0这里只是资源诊断，
   正式G2还要求W1/W2；两场景缺当前版本结果，不能提前宣布胜出。
3. HydraServe确实低U，但三个场景联合SLO均0；低资源与达标服务不能混为
   一个冠军。三个运行均pp1，不能宣称验证了流水线/consolidation收益。
   必要模型和SHM交付适配已经完成；不因低SLO再启动性能参数搜索。
4. Loquetier W0早期长尾与完整池准备/顺序初始化相符；其各phase TPOT
   仍约52–54ms，高于共同阈值，所以联合0并非仅启动造成。详见D800；
   本表不证明原系统在其他机器或部署同样差。
5. dLoRA取消一致性修正后的失败仍须保留。D794有效响应的大部分等待在
   原生service TTFT内部，同时存在memory.high回收和swap；不能把全部
   等待称为网络或纯GPU计算。既有机制/资源证据支持报告限制，不支持
   不加区分地称为原论文机制缺陷。D795同样保留878条失败。
6. 90/95/99%达成要求、50/75/100%资源预算已对本批固定点离线分类。
   W0在90/95%时资源顺序为PrimeLoRA、ServerlessLLM、vLLM；99%只剩
   vLLM。三个场景均无同时满足95%与75%预算的已测点。不能据此断言所有
   系统的全部配置都不可行；没有搜索基线最优配置，也没有插值未测前沿。

## 4. 下一步回到 PrimeLoRA，而非延长基线调参

当前D752与D749的控制表示改动降低了时延，但U仅变化0.091%；D752有3次
自然扩容、0次缩容，表明资源目标不能靠继续微调局部表示开销自动完成。
这是选择调查方向的证据，不是已经证明autoscaler错误。

下一按P3先核对D703/D711/D725/D742/D749/D750–D752以及更早控制尝试，
明确哪些方向已经失败，检查当前持卡区间、队列与触发条件。再核查相关
原始论文和官方实现，形成一个可证伪的资源/尾延迟假设；保持九公式、共同
阈值和输入不变。没有新证据不重复历史无效优化，不临时硬编码少一张卡，
不把每场景分别调参冒充自适应。必要改动验证后完成同版本W0/W1/W2，
单键一次并保留退化。尚未实施或启动新的PrimeLoRA优化。
