# D509：必要适配后的混合 LoRA 与显存验证

本轮仅验证 D508 改动所影响的路径，不是完整性能比较。复用原 W0 的前 100
条请求、500-ID 静态清单、既有工件、真实远端只读交付、共同生成与时间合同。
不重复安装、500-ID 覆盖或 1000 请求资格阶梯，不生成新数据。

此前 D507 的 124 条超时、取消处理错误和不完整释放账目保持原样。异常差的
结果不能在排除适配缺陷前作为 PrimeLoRA 优势证据。D508 已完成 100 项 CPU
测试和原生 Python 下 36 项测试；本轮使用逐字节一致的 16 份已验证 overlay。

## 唯一改变及固定条件

- 开启 D508 的取消所有权交接与按原生接纳量推导 LoRA 容量两个 opt-in。
- 实际控制器 batch 必须等于固定官方源码提取的 8；三个 EngineArgs 位置均
  使用 `max_loras = batch × PP_SIZE`。不是 500 槽预装，也不扫描容量。
- 保留原生 Scheduler、placement、启动重叠、pipeline、consolidation、
  vLLM 0.4.2、模型注册、cache=0、30 秒空闲回收和 1800 秒请求保护。
- 60 秒准备通知、72/80 GiB 内存包络、2 GiB swap、四张真实 GPU 与物理持卡
  积分不变。属于其他项目的 k3s 不访问、不修改；仍使用已验证的隔离平台。

## 验收与解释边界

1. 100/100 原生合同完整响应，无失败；逐请求核验 prompt、adapter/index/path、
   原生 token 数、时钟与进程身份、远端内容与传输关联。
2. 至少一个实际 worker 出现不同 adapter 的解码区间重叠，峰值不少于 2。
   这证明原单 adapter 串行限制已经解除，不自动证明全部性能损失被解释。
3. 记录实际显存、原生 KV/slot 配置与资源事件；没有 OOM 或未释放 GPU 租约。
   代码中的预算顺序不能替代本次测量。
4. 原生空闲回收和所有资源实际退出。取消路径若本轮未自然触发，只引用已完成
   的 CPU 所有权测试，不冒称完成 GPU 取消压力验证。
5. 保留数值可区分性和单机/pp1 限制。不用 HTTP200 或 token 数单独证明数值
   正确，也不从 100 请求外推完整 W0 的联合 SLO 或 GPU-s。

通过后进入一个新的完整 4000 请求 HydraServe 运行；来源绑定地汇总全部可用
基线后，再优化 PrimeLoRA。失败则保存并定位受影响路径，不放宽指标或超时。
全部 3B、W1/W2、G2、消融与敏感性任务保留。

## 启动前清理记录

D507 五个剩余容器的原始日志与 State 已先备份。第一轮精确 ID 清理删除三个
已退出 worker，随后因存储容器依赖尚未删除的 provider 而停止。后续检查遇到
Podman 已回收的 State 变化及缺失的 ConmonPid；失败脚本/回执全部保留。
最终以保存的原始 PID、当前 PID、cgroup 的实际缺失为准，先删除 provider 再
删除存储容器。没有终止其他进程或删除唯一工件，不回填旧运行的 release 时间。

当前是已准备、未启动检查点；实际 GPU 结果须另存追加产物。原始目录：
