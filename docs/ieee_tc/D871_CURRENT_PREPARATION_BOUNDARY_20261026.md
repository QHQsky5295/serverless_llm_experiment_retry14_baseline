## 4. 下一项单一问题：原生 CPU 构造与状态提交能否分开

当前已具备 D863/D868 的原生控制干扰证据，不另起 GPU profiling：在有
推理请求的窗口内，431 次 HOST prepare 调用平均 wall 152.729 ms、线程
CPU 151.790 ms；这不是 GIL 占用的直接测量，也不是 D870 的逐调用计时。
现在仅核查与全文件 owner 线程化不同的边界：**原生 checkpoint→CPU tensor
构造是否必须与 owner/cache 状态提交一起阻塞推理 core。**

实际代码事实：

1. gpu_monitor.py 的 file_host_loader 在一次同步调用中做实时分配检查、
   官方 _load_adapter、合并/注册，以及新鲜物理清点。不是纯文件读取函数。
2. residency_manager.prepare_file_host_and_hold 在同一次调用前后校验 GPU
   slots、CPU cache 与 pins 未发生非目标改变，并登记真实 HOST/staging 租约。
   此不变量依赖当前串行执行，不能原样包进线程后假定仍成立。
3. host_workspace_check 保护 cache growth 和一个 demand load 的预算，
   但其 projected 数值是检查结果，不是新后台工作的生命周期 reservation。
   两次异步预检查不能各自把同一剩余空间当可用。
4. 因此不会直接对现有方法加 to_thread，也不把所有 owner 操作搬到后台。
   候选若可行，必须是有预算持有者的准备/提交两段：后台仅构造私有 CPU
   对象；原生 core 上重新检查身份、当前 cache/容量后才提交；GPU 激活和
   Eq. (8) 当前 KV/headroom 检查继续留在 core。构造中的实际 tensor、
   workspace、取消和释放仍在同一服务资源域计量，不能提前宣告就绪。

下一步只对该边界作有界实现可行性核查，复用现有 owner/取消/预算 fixture。
需要明确的在途预算与单线程提交协议，不用陈旧快照或未知→ready 兜底。
如果不能在既有语义下完成，拒绝此候选；不以“异步”作为性能已改善的结论。
形成候选后只测受影响路径，再按既定规则运行一次新键完整 W2，保持当前
SLO/预算/输入不变。不再追加重复短前缀或同键择优运行。

本轮核对的原始资料：

- [vLLM 0.30 worker manager](https://raw.githubusercontent.com/vllm-project/vllm/v0.30.0/vllm/lora/worker_manager.py)
  的 _load_adapter 使用 CPU checkpoint 构造；这不意味着整个 manager/注册
  可以跨线程并发，也不证明本机加速。
- [vLLM LoRA 官方说明](https://github.com/vllm-project/vllm/blob/main/docs/features/lora.md)
  的异步 engine/动态加载接口不构成原生加载事务可并发的证明；采用固定
  0.30 源码核对实际边界，不更新后端来绕开此问题。
- [ServerlessLoRA §3–4](https://arxiv.org/html/2505.14468v1)分别讨论准备、
  batching 与 GPU offloading，支持分析准备/执行干扰这一研究方向；其
  offloading 不是本项目 CPU loader 线程方案，不能移用其性能或安全结论。
