从现有投影复用得到：

| 新目标 | 计划 `91755aed1ab846b3b3e40a3f8af43bf9` 于 epoch 1391 注册，包含 ID 683755；拟从 HOST 文件准备同一内容 SHA |
| 失败前后 | 第一次提交因 epoch 变化明确未执行；返回 epoch 1411，之后命令使用该 epoch，但来源绑定 guard 抛错 |
| epoch 1411 的保护 | 该 ID 不在 GPU 槽、GPU/HOST 引用或 staging 中，却在 pending targets 中；计划关闭后 pending 清空 |

以上支持“新计划被错误视作旧路径持有者”的假设，但 D133 没有导出失败瞬间
`_sources` 的全部内部状态；不追造该瞬间的缓存字典，也不据此指认 D132 必然
导致错误。随后以实际 owner/selector 的可重复反例验证这个实现缺陷。

D108/D109 处理的是**其他 adapter 的旧来源变化使旧计划失效**，本次是
**目标旧副本已退役，新计划有意选择另一层的同内容文件**，不能把两者混为一谈，
也不能让后一种合法新计划不断失效、永远无法准备。

## 原理、参考与唯一修正

逻辑 adapter 身份、已加载 native 对象、文件来源与准备计划的选择不是同一个
生命周期。逻辑身份保持不变；活对象不能原地重标来源；新计划应保护它实际
选择的来源，而不是自动延长这个整数 ID 过去使用过的路径寿命。

[vLLM 0.30.0 官方 worker manager](https://raw.githubusercontent.com/vllm-project/vllm/v0.30.0/vllm/lora/worker_manager.py)
按整数 ID 检查缓存，缺失时才加载，并在单线程 core loop 中操作；这并不使跨
多个 RPC 的准备过程成为原子事务。借鉴的是对象身份与操作边界，不照搬性能数字。
[dLoRA 原论文](https://www.usenix.org/conference/osdi24/presentation/wu-bingyang)
将请求与 adapter 迁移作为动态管理对象；它不能直接证明本项目具体 guard 的
正确性。本修正依据仍是本地不可变内容证据及下面的实际执行反例。

只改 `_validate_source_binding` 对计划所有权的解释：旧对象全部退役后，
检查所有仍拥有该目标的计划所选 `(adapter_id, lora_path)` 与待加载来源一致。
同来源 staging 可以继续使用；不同来源 staging 仍拒绝。完成单个 target 不
结束整个计划的保护，直到原有 plan close。

保留逻辑名称、活 CPU/GPU 对象、引用、内容、owner/epoch、物理容量与 admission
校验。不吞异常、不增加重试、TTL、sleep 或兜底路径；不修改九个公式、选择收益、
profile、模型容量、超时、工作量、后端或远端配置。没有基于这次结果调参。

发布并保护内容相同的 HOST/NVMe 副本；实际 native owner 驱逐旧对象；实际
planner 选择新 HOST 来源、注册计划并进入原来的混合执行器。原生模型/缓存是
既有 CPU 测试替身，不执行 CUDA，不生成论文实验权重或新负载。
