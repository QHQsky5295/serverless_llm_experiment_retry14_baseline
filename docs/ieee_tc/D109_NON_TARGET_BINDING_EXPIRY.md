# D109：非目标副本变化与旧准备计划的结束边界

2026-09-28。基于已备份的 D108 反例 `06ec406d23234c65ab105d2da51db4025ce54a82`；
此前生产代码为 D106 `b7161bdcafe05117dcc9434f12ede5a7003c121d`。
本轮是 Prime IEEE Full 的正确性修正，尚不是完整回放或性能资格。

## 问题、依据与单一假设

D108 用实际文件发布管理器和 native owner 复现了以下情形：准备目标 c 不变，
合法请求将非目标 b 从已退役的 NVMe 来源重载为同内容 HOST 来源；冻结来源域
仍覆盖缓存，名称及 GPU 确认完整，旧实现却在定价之前抛出不可恢复异常。
该反例证明一条实现缺陷路径，不能补造 D107 未保存的确切失败快照，也不能说明
此前完整回放中 30 个超时全部由此造成。

[vLLM 0.30.0 官方 worker manager](https://raw.githubusercontent.com/vllm-project/vllm/v0.30.0/vllm/lora/worker_manager.py)
说明 adapter 加载在单线程 core loop 中执行，LRU 以整数 ID 查找并加载/复用。
由此结合本地多次 RPC 的控制流程可推断：单次操作串行不等于整个准备计划原子。
正常 demand 可以在观测与提交之间改变状态。该源码不是性能证据，也不证明两份
文件内容相同；内容证明仍来自本地实际发布记录及冻结 SHA。

假设：**合法的非目标物理来源变化应使路径绑定的旧准备目标失效，不应终止整个
服务；身份损坏和结果不明的操作仍必须保留错误与引用。**

## 本次改动与不变项

| 论文规范语义 | 当前实现证据与限制 |
|---|---|
| 收益/成本对应所观测的具体来源 | 旧来源变化后结束旧目标，不将新路径代入旧收益继续定价或驱逐 |
| 快状态在物理执行点检查 | native owner 在成本 provider、admission、拷贝、驱逐之前返回明确的未执行回执 |
| 计划不等于已持有所有缓存对象 | 只允许非目标副本的合法变化；目标绑定、逻辑名称、GPU 确认仍严格检查 |
| 同工件须有内容证据 | controller 核对 ID、名称、rank、冻结 SHA、完整 owner 视图及两份当前文件发布 |
| 回执不能凭错误文本推断 | 校验 owner/clock、plan/hash、lease、期望/计划/观察 epoch、变更列表及 `native_operation_applied=false` |
| 并发变化不能依赖一次前置检查 | 前置观测可直接结束旧计划；实际观察至 RPC 之间变化先得到 stale 回执，再由实际状态事件唤醒后检查 |
| 失效后必须完整收尾 | 使用原有队列撤回、已提交操作等待和计划关闭；下一正常 residency 周期重新规划 |
| handoff 目标不可偷偷替换 | 传播失效，不在同一次 handoff 调用中隐式重选目标 |
| 未知操作仍可能使用文件 | 损坏或丢失回执不标成功/正常失效，不释放实际持有的文件 fallback |

只改 planner 的负面证据检查、native owner 的失效回执、现有 runner 的校验与
对应测试。共享 D106 的双文件发布校验，未新建运行框架。九个行间公式、需求与
准备 profile、预算和 admission、后端、负载、生成合同、超时与远端配置均不变。
没有增加兜底加载、固定重试、sleep、TTL 或经验阈值，也不删除物理安全检查。

本次仍要求两份当前发布证据。原文件已撤回等其他状态不自动被归为合法相同内容；
不存在通过任意异常捕获来继续服务的许可。
