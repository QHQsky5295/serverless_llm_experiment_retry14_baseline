### 后续依赖核查：不能直接删除执行副本

只读核对 `planning_cpu.py` 与 `_execute_ieee_file_preparation_plan` 后确认：

- D163 已消除成员查询引起的重复完整解析；正常执行仍只打开一次私有 bundle。
- 这次打开不仅服务日志。执行器消费选中 option、来源身份、内容路径、profile、
  原生 owner 以及文件和 GPU 执行目标。pre-init 分支还把计划交给初始化后的
  GPU 目标构造；不能仅保留一个计划 ID，或盲删全部 `source_view`。
- D159 已将目标构造合入既有规划进程，D193 已研究并精简规划输入的无关描述。
  把这些既有工作重新“外移”不构成新候选；D737 改的是原生消息接收边界，
  其失败也不能作为所有计划表示都会失败的证明。
- D734 的 14/536 栈样本只支持检查复制路径，没有独立同步耗时或受影响请求
  数。D733 的 child-finish→parent-join 也不能全部算作解码。当前不据此启动
  另一完整回放；只有能保留全部消费者语义、并实测减少工作量的具体方案，
  才能成为后续候选。

本轮在线复核 [vLLM CPU 路径分析](https://vllm.ai/blog/2024-09-05-perf-update)
与 [Python pickle 文档](https://docs.python.org/3.12/library/pickle.html)：
前者支持区分 CPU 组织与 GPU 执行的开销，后者说明反序列化重建对象图和
共享关系；二者不证明本机加速。pickle 仍只用于可信本地 IPC，不能扩展到
真实远端工件输入。本次只读核查后尚未选定或实施新的性能候选。
