## 2. 到达迟到主要在本机提交之后

同一Linux monotonic时钟下，按既有字段逐条拆分。外置publisher使用本机
Unix socket发送到达消息；此处不是LoRA制品HTTP链路。全部4000条身份、
顺序和既有阶段加和核验通过，误差详见diagnosis.json。

| 分段 | 全请求均值ms | P95 ms |
|---|---:|---:|
| 计划到达→publisher task创建 | 1.949576 | 4.345848 |
| task创建→publisher提交 | 0.834744 | 0.299896 |
| 提交→服务端接收 | 149.717743 | 928.956311 |
| 服务端接收→取出到达消息 | 12.916516 | 36.102924 |
| 取出消息→dispatch window准入 | 35.681524 | 84.606989 |

均值大于P95并不矛盾：少数长尾仍影响均值，未删除这些点。到达→接收总均值

**支持的判断：**单纯发生器唤醒/提交迟到不是这一段的主要贡献；进一步
检查服务端接收调度有实际依据。**尚未识别：**提交→接收包括socket交付、
接收事件循环调度以及在接收时间戳之前的消息处理，不是纯网络耗时，也不是
某个Python函数已测得的CPU时间。不能仅凭阶段包络认定全部由文件清点造成。

## 4. 不把小往返优化误判为主要解决方案

源码中确有一次bind utility完成后再提交原生ADD的顺序；它和已经完成的
pending登记/GPU保护合并不是同一个边界。但本轮没有逐请求bind专属span。
作为投入优先级检查，只对已观察时间线做“删除整个包含区间、其他区间与
TPOT全部保持原值”的算术投影：

| 假想删除的完整包络 | 联合通过新增条数 |
|---|---:|
| engine entry→native queue | 20 |
| publisher提交→服务接收 | 75 |
| 整个runtime slot等待 | 97 |
| 仅GPU命中的pending ack→acquired | 13 |

这些不是新性能结果、可执行系统或真实干预收益上界。改变执行会改变排队、
decode和控制反馈，不能据此宣称因果收益最多只有这些条数。它们仅说明：
把完整包络都当作可省成本仍不能在固定其余时间线时补齐171条，因而没有
依据立刻为bind合并启动新完整回放。此候选暂不实施，不添加私有字段补丁。
其他投影同样不能成为删时延、改统计或放宽SLO的依据。

## 5. 控制反馈复核及下一项有界问题

D729三个扩容决策在业务后10.542/12.595/14.696秒，TTFT P95均等于第一条
请求6847.901858ms；样本数依次为1/2/2，queue均0，唯一超过1的归一化分量为TTFT。
控制公式、ready+pending和all-low谓词逐条一致。1628个低queue/active、
无pending的观测中，P95 TTFT均值2179.096847ms；低阈为219.518056ms，
全程all-low为0。无实现证据表明应缩而未缩；不以调高低阈解决本轮未达标。

下一优先核查**控制器新鲜状态维护的同步工作组织**，而非重复HOST字段
格式、pin查询、GC、startup loader或identity-only候选：

1. 当前`_plan_ieee_preparation_for_slot`原生查询返回后，仍同步执行文件
   `preparation_snapshot`；该函数在file owner锁内构造来源与容量视图。
   D456/D603旧版本栈曾定位此类工作，D457/D606已改表示，不能把旧耗时
   当成D729现测值。普通完整D729没有该函数的独立span，份额仍未确定。
2. 纯背包规划早已在独立进程，不能再次将其外移宣称为新改动。当前
   `planning_cpu.py`还保留同步输入冻结和执行副本解码；须按实际消费者
   判断，不机械改为异步或复用过期图。
3. 不能仅给锁内函数包一层to_thread：其他controller同步取同一锁仍可
   阻塞循环；file-change回调与取消/释放也有owner语义。下一候选应先
   确认整个事务的访问和发布边界，保持新鲜容量、来源保护与执行重检查。
4. 优先复用已有时间线与有界CPU证据。只有上述未识别问题确需原生观测时
   才登记针对性诊断，不因数据不利重复D729，不另添广泛资格门禁。

[Python 3.12 asyncio文档](https://docs.python.org/3.12/library/asyncio-dev.html#running-blocking-code)
说明同步CPU工作会延迟同事件循环任务；
[vLLM CPU路径分析](https://vllm.ai/blog/2024-09-05-perf-update)
提供隔离CPU密集组件的设计依据，不把其硬件收益移用于本机。
本轮同时核对[vLLM 0.30 EngineCore源码](https://raw.githubusercontent.com/vllm-project/vllm/v0.30.0/vllm/v1/engine/core.py)：
输入预处理可在输入线程执行，调度owner状态不能盲目迁入该线程。
这些来源支持检查方向，不证明PrimeLoRA修改必有收益。
