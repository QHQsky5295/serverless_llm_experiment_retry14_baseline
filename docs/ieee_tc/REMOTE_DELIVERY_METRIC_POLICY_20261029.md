# PrimeLoRA 远程制品交付与时延计量冻结口径

版本：`remote-delivery-metric-policy-v1`  
日期：2026-10-29  
适用范围：PrimeLoRA、ServerlessLLM、HydraServe、Loquetier、S-LoRA、vLLM 及后续同合同对照。  
对应主协议：`PrimeLoRA-PLAN.md`、`PrimeLoRA_Metric_Protocol_Codex_20260925.tex`。

本文冻结“远端服务端准备工作”和“推理请求真实交付路径”的边界。它不修改 PrimeLoRA 的论文公式，也不把远端服务的运维成本从系统结果中悄悄删除。所有系统必须使用同一份已发布制品内容清单、同一请求轨迹和同一请求生成协议；系统因缓存、驻留和请求路由不同而产生的合法获取次数与传输字节仍然可以不同。

## 1. 研究对象与边界

本实验研究的是：在远端已经发布可读取的 LoRA 制品集合、推理机按请求选择和获取制品、并在本地多层级驻留的条件下，PrimeLoRA 是否能在共同服务要求下减少生命周期 GPU 占用，并在扩容和 adapter churn 下改善尾延迟。

因此，远端制品节点分成两类事件：

| 事件 | 是否属于请求服务路径 | 主 TTFT/E2E 处理 |
|---|---|---|
| 研究开始前一次性发布/压缩/哈希/内容清单生成 | 否 | 不计入请求延迟；单独记录准备墙钟、字节、CPU/磁盘峰值 |
| 请求触发的远端对象读取 | 是 | 计入请求的准备与 TTFT；记录远端读取 span |
| 请求触发的网络发送、接收和本地落盘/解压到可用文件 | 是 | 计入请求的真实总时间；若与其他阶段重叠不得重复相加 |
| 远端节点的维护、哈希扫描、清理、备份、无关打包任务 | 否 | 不得安排在正式测量期；若意外发生，作为外部干扰记录，不用事后减去 |
| 推理机缓存命中、miss、分层 promotion、并发传输竞争 | 是 | 按真实事件计入；这是 PrimeLoRA 的研究对象 |

远端预发布归档可以由一次性的只读交付缓存提供。它不是“给 PrimeLoRA 的特殊预热”：所有系统共享同一不可变发布集合和内容清单，缓存未命中仍由各系统按自己的合法策略触发读取与本地物化。

## 2. 时间定义

对请求 (r)，主客户端时间线保持既定协议：

\[
\mathrm{TTFT}_r=t_r^{(1)}-t_r^{\mathrm{arr}},\qquad
\mathrm{E2E}_r=t_r^{\mathrm{done}}-t_r^{\mathrm{arr}}.
\]

其中 (t_r^{\mathrm{arr}}) 是冻结轨迹的计划到达时间，(t_r^{(1)}) 是客户端观察到首个输出 token/chunk 的时间，(t_r^{\mathrm{done}}) 是客户端确认正常完成的时间。远端网络传输是服务路径的一部分，所以不能从 TTFT/E2E 中删除。

对请求内可校准的阶段，记录以下 span：

\[
T_r^{\mathrm{delivery}}
=T_r^{\mathrm{remote\ read}}
 +T_r^{\mathrm{network\ transfer}}
 +T_r^{\mathrm{local\ materialize}},
\]

但只有在这些 span 在同一请求时钟、边界明确且没有重叠时才可相加。跨主机 monotonic clock 不直接相减；请求级 TTFT/E2E 是最终裁决，阶段分解只用于解释收益和瓶颈。

远端**发布前**压缩时间 (T^{\mathrm{publish\,offline}}) 与请求时间线无关，不能写成 
\(\mathrm{TTFT}-T^{\mathrm{publish\,offline}}\)。同样，不能用“所有请求累计打包时间”从每个请求 E2E 中统一扣除。若历史动态打包曾进入请求关键路径，旧数据保留为交付方式诊断，不伪造成当前发布协议下的主结果。

## 3. 为什么传输必须计入，而预发布打包不计入

远端到推理机的数据移动会直接改变请求何时拥有可执行的 adapter；它对 cold/miss 请求的首 token 服务具有因果作用，而且 PrimeLoRA 的核心优势正是通过 GPU/HOST/NVMe 驻留减少后续远端获取。因此删除传输时间会删除研究问题本身的一部分。

相反，发布前压缩是制品供应方式的部署准备。如果每个系统都使用同一不可变发布集合，它既不由某一个请求触发，也不反映调度器选择；把它加入每个请求会把供应方的离线运维工作错误地重复计入每一次服务。它仍必须单独报告，以避免把“未计入”误写成“没有成本”：

- 发布墙钟时间、CPU 时间、峰值临时字节和日志大小；
- 发布归档字节与原始 payload 字节；
- 发布前后内容 SHA-256；
- 发布失败或内容不一致证据。

如果研究问题改为“端到端制品生成服务”，必须另立协议；本 PrimeLoRA 论文不使用该定义。

## 4. 统一比较与合法差异

所有系统固定：

1. 同一基座模型、LoRA 内容清单和 adapter subset；
2. 同一 prompt、arrival、target output、tokenizer 和生成合同；
3. 同一远端 endpoint、认证、发布归档版本和应用层限速；
4. 同一推理机资源包络、GPU 生命周期计量和 SLO 阈值。

以下差异不强行抹平，因为它们是系统机制的结果：缓存命中率、远程 miss 次数、读取并发、实际传输字节、promotion 次数、GPU/HOST/NVMe 驻留时长。它们必须同时报告，避免“更少传输”被误认为测量缺失。

主结果仍按冻结目标排序：

1. 所有计划请求正确完成，并满足共同联合 TTFT/TPOT SLO；
2. 在满足第 1 条的已测运行中，最小化物理生命周期 GPU-s/request；
3. 在共同资源预算下，比较扩容/churn 的 P95 TTFT 与联合 SLO 达成率；
4. CE、美元成本、平均延迟、吞吐和阶段分解作为补充。

物理 GPU 时间使用分配事件积分：

\[
U_s=\int_{W}\sum_{d\in\mathcal G}a_{s,d}(t)\,dt,
\qquad
\mathrm{GPU\!\text{-}s/request}=U_s/N_{\mathrm{planned}}.
\]

失败、超时或不正确请求仍进入计划分母并保留其资源开销；若运行不满足共同服务资格，不以低 GPU-s/request 取得主排名。

## 5. 100 Mbps/1 Gbps 证据与解释

历史记录不能支持“当前永远只有 100 Mbps”这一结论：D77 的链路检查记录过对端只通告 10/100；D78 在两机重启后记录过 `1000baseT/Full`。这说明 100 Mbps 是当时的物理协商状态或链路/端口条件，不是 PrimeLoRA 的算法设定；它可能来自交换机端口、网线、自动协商状态、端口配置或重启前链路状态，不能仅凭应用日志判断具体硬件原因。

正式运行前只读记录本次链路的：接口名、`ethtool` advertised/partner/speed/duplex、路由路径、应用层实际字节和吞吐。正式测量期间不重启远端服务、不改端口、不做并发压测、不进行远端打包或清理。若正式运行间链路状态改变，两个状态分开登记，不把它们合并成一个平均带宽。

100 Mbps 会放大远程 miss 的交付时间，因而影响绝对 TTFT；但这并不自动使结论无效，因为所有系统在同一链路和同一发布集合下比较，而 PrimeLoRA 的机制正是减少不必要 miss。论文不得把该结果外推成 100/400 Gbps 数据中心性能，也不得声称已验证某个未测物理带宽。为消解“硬件不足”质疑，报告：

- 实际协商链路与应用层 achieved throughput；
- 请求级远程 miss 次数、字节、并发和等待分解；
- no-delay/local-sim 或应用层带宽敏感性作为乐观上界/敏感性，而非伪造的 100 Gbps 实测；
- 在相同链路下的 PrimeLoRA 与 baseline 配对结果。

因此，远程传输延迟**不能从最终 TTFT/E2E 删除**；应通过共同环境、阶段分解和带宽敏感性说明它的外部可迁移边界。只有远端无关维护和请求前一次性发布准备不进入主请求延迟。

## 6. 远程节点污染规则

正式测量前完成只读健康检查和发布内容核验；测量窗口内远端节点不得执行额外打包、压缩、哈希扫描、清理、备份、模型下载或服务重启。任何意外外部任务必须在运行记录中标记其开始/结束时间、受影响请求和资源；不能选择性删除受影响系统的运行。

制品节点独立磁盘门槛按“并发临时打包峰值 + 日志峰值 + 安全余量”计算，不再套用推理机 150 GiB 门槛；推理机现有 150/100 GiB 磁盘和 OOM/cgroup 门槛不变，不删除唯一工件。远端发布准备产生的文件可复用，但不在请求期生成第二套解压池。

## 7. 审计字段与冻结检查

每个运行必须保存：

- 发布集合、归档和 payload 的 SHA-256；
- 远端 endpoint、接口协商状态、应用层 configured/achieved MiB/s；
- 请求级 `remote_read_ms`、`network_transfer_ms`、`local_materialize_ms`（可得时）；
- 请求级缓存 tier、miss/hit、传输字节、并发和重试；
- `TTFT`、`E2E`、共同 TTFT/TPOT 通过标志、正确性状态和物理 GPU 分配事件；
- 发布前离线 span 与请求内 span 的明确类别；
- 外部干扰事件和是否污染正式资格的裁决。

图表生成器不得把离线发布 span 直接加到请求 TTFT，也不得从请求 E2E 中扣除；不得将缺失阶段字段填零。阶段未知就标记未知并保留总时延。

## 8. 固定裁决

本文件从 2026-10-29 起作为所有后续 PrimeLoRA/baseline 对比的冻结口径。它不改变既有历史结果的身份；历史结果只能在字段和交付合同匹配时复用。若未来需要研究“在线打包服务”或另一种远端供应协议，必须新建协议版本、重新登记执行键，并与本协议结果分开。
