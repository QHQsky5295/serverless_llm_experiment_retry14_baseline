冒称精确重建所有 reserve/release 时刻。

## 3. 增加的 200.54 GPU-s 从何而来

逐物理设备使用已闭合 allocation/release 区间。定义每卡从首次持有到
最后释放的 envelope，其间真正释放后的间隔记为 gap，则恒等式为：

`U = sum(envelope) - sum(gap)`。

每轮都独立验证该式，再作候选减参照的差；没有跨不同运行时钟直接相减。
gap 是观测到的无持卡时间，不是“禁止缩容”的反事实节约量。

| 物理 GPU 时间 (GPU-s) | D318 | D323 | D323 − D318 |
|---|---:|---:|---:|
| 首次持有至最后释放的总 envelope | 15851.250655 | 15843.190439 | -8.060216 |
| envelope 内实际释放间隔 | 324.251432 | 115.647227 | -208.604205 |
| 生命周期 U | 15526.999223 | 15727.543212 | **+200.543989** |

因此 `+200.543989 = -8.060216 + 208.604205`，与原互斥窗口积分一致。
两轮均两次实际缩容，但时间不同：

| 运行 | 相对业务起点的释放→重新分配 (s) | 间隔 (s) |
|---|---|---:|
| D318 | 143.148 → 363.340 | 220.192 |
| D318 | 965.166 → 1069.225 | 104.059 |
| D323 | 683.108 → 741.321 | 58.213 |
| D323 | 1265.946 → 1323.380 | 57.434 |

不能说“少缩容两次”，也不能归因于打包或 cleanup；D323 的实际缩容
次数相同，而空闲间隔变短。D323 的 mean/P95 TTFT 与 P95 TPOT 改善仍
按 D323 完整报告保留；预测更准不保证整条闭环同时最小化资源。

## 4. 下一单一假设：缩容决策与实际排空的衔接

不是立即改阈值。先对照 IEEE 原文、历史实现和工业实现，发现了具体差异：

- IEEE LaTeX 附件第 215 行明确规定：先撤销路由可用性，再排空已接纳
  工作，最后释放副本。附件 SHA 为
  `35da2d89941452df2959b022aedddd4a984e45b8c15efb9951b5295deb198b90`。
- D48 提交 `faf5c855b0cbb2e13d841ff711ac7aaead43a5ae` 接入了已经排空
  副本的回收，文档当时明确一般 withdraw-then-drain 尚待衔接。
- 当前 `_evaluate_ieee_live_control` 仍仅选 active/load/forwarding 全零
  的非 primary 副本；没有这样的副本时只记 `awaiting_drained_replica`，
  不撤销任何路由可用性。`IEEEReplicaControl.evaluate` 此时已重置
  `low_since`，虽未真的启动一次回收，也需要重新满足 cooldown。
- D323 在 311.818820 秒真实出现该分支：queue=0、active=6、capacity=32、
  pending=0、P95 TTFT=1848.077ms，三项低压与持续条件已通过，但没有
  执行 drain。下一次实际缩容决策在 674.883314 秒。两者之间的时长
  **不是可直接回收的 GPU-s**，因为实际后续负载和闭环会变化。

[Ray 2.59.0 官方 replica 实现](https://raw.githubusercontent.com/ray-project/ray/ray-2.59.0/python/ray/serve/_private/replica.py)
的 `perform_graceful_shutdown` 明确等待 ongoing requests，并在结束前
处理可能仍到达的请求；支持将排空作为显式生命周期，而不是等待随机
出现的空副本。其 timeout/force-kill 和默认配置不移植到本系统。
[Kubernetes HPA 官方说明](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/)
区分多指标决策与缩容稳定窗口；不据此删除本论文 TTFT 条件、借用其默认
窗口或声称优化效果。以上仅支持机制设计边界，不证明本项目会更快。

可证伪问题：**保持三指标控制律、上下阈值、38 秒 cooldown、9 个公式
及 profile 不变，显式完成已决定的 withdraw→drain→physical release，
能否减少被放弃的缩容机会，并在完整回放中降低 U 而不损害服务目标？**

下一动作先用确定性 CPU 测试复现“已有 admitted 请求、无空副本”的分支，
再实现单一受管排空状态机；不得只是回滚计时器、不断重试、杀掉活动请求
或立刻把 draining 当作已释放 GPU。必须验证：

1. 撤销新 admission 与已有 reservation 原子衔接；已有请求能正常完成。
2. drain 由真实 completion/release 事件推动，不新增人工 polling sleep。
3. routing capacity、ready/admitted 计数、pending、物理设备占有各自准确；
   尤其不能用排空请求除以已排除该副本的容量产生不一致快照。
4. 同一回收只执行一次，min replicas 保留；新扩容仍受真实 GPU 预留约束。
5. 与 planner、HOST/file/native 引用、失败、取消和统一 shutdown 同步；
   未确认释放继续计费，不吞掉异常，不重复 cleanup。
6. 最小验证后完整原 4000 W0；不以重复短回放筛赢家，不改控制或评价阈值。

本轮没有实现上述 serving 变更，也不预报可省多少资源。D324 这项日志
复核到此结束，不继续拆分相同日志以寻找更有利解释。7B 仍优先，后续
3B、baseline、主比较、消融和敏感性全部保留待做。
