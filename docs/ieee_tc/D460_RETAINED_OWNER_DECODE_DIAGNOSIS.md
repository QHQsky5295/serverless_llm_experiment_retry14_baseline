## 实际结果

复用已有分析器，新增主动准备的严格区间关联；110 项 CPU 检查全部通过。
三轮各 4,000 条请求、合计 12,000 条全部分析。每个原生 owner 的 PID、启动
身份与已封存 GPU census 一一核验：旧 PrimeLoRA 12 个、ElasticLocality
31 个、新 PrimeLoRA 20 个 owner，各对应 4 张物理 GPU。所有请求 decode
及 10,994 个主动操作子区间均落在对应 GPU 的真实持有区间内；包含嵌套的
加载/fence/HOST 事务，10,994 不是独立加载数。

| 同口径观测 | 旧 PrimeLoRA D371 | ElasticLocality D453 | 新 PrimeLoRA D458 |
|---|---:|---:|---:|
| 平均 decode / ms | 3336.563 | 3102.616 | 3636.602 |
| 平均 TPOT / ms | 31.032 | 29.212 | 34.022 |
| TPOT 超共同阈值请求数 | 33 | 27 | 42 |
| decode 期间其他原生请求平均占用 | 1.898 | 2.223 | 2.654 |
| 与其他请求 prefill 包络重叠的请求数 | 2349 | 2521 | 2720 |
| 与请求驱动加载重叠的请求数 | 1398 | 1279 | 1742 |
| 与主动加载重叠的请求数 | 735 | 0 | 750 |
| 主动加载重叠 / decode，逐请求比值均值 | 0.763% | 0% | 0.832% |
| 主动 GPU 实际加载次数 | 1645 | 0 | 1650 |
| 主动 GPU 加载区间累计 / s | 95.766 | 0 | 94.735 |
| 主动 HOST 实际加载次数 | 1083 | 0 | 1067 |
| 主动 HOST 加载区间累计 / s | 181.268 | 0 | 166.099 |

平均其他请求占用是同 owner 请求入口→末 token 区间的时间加权占用，不是
原生 kernel batch。累计加载区间是不同事务的测量总量，不是单请求延迟、
GPU 忙时或可直接扣除的节省量；GPU 加载内含完成 fence，不能重复相加。

新 PrimeLoRA 的 2,245 次主动 GPU 尝试中：1,650 次实际加载、52 次复用、
538 次有拒绝/延后回执但无精确执行区间、5 次没有该回执。2,498 次 HOST
尝试中：1,067 次实际加载、1,429 次有延后回执但缺区间、2 次无回执。
后两类不作为零耗时加载；其完整状态在原始记录保留。

## 对下一优化方向的裁决

1. **不支持“新版主动加载工作量增长导致全部解码退化”。**主动 GPU 加载
   次数接近不变，累计 GPU/HOST 加载时间均下降，平均 decode 却增加。
   新版 42 个 TPOT 超阈值请求中，31 个没有同 owner 主动加载重叠。
   这不能证明准备没有间接影响；准备前的控制、排队和状态观察未完整覆盖。
2. **并发/prefill 是应保留的解释变量，不是已证实的因果结论。**新版平均
   其他请求占用 2.654，旧版 1.898；与 prefill 包络重叠从 2349 到 2720。
   33/42 个新版 TPOT 超阈值请求属于 prefill 重叠组。但慢请求自身更易
   遇到重叠，且路由、批组成和副本轨迹不同，不能据此推导应调低多少并发。
3. **不能只看一类干扰。**旧 PrimeLoRA 的并发低于 ElasticLocality，但
   解码反而更慢；这不符合“并发量是唯一解释”的说法。未观察到 startup、
   请求加载、prefill、主动加载四类重叠的条件组，其平均 TPOT 分别为
   24.219/22.294/25.083 ms；成员与长度不同，只作诊断，不作反事实比较。
4. **主验收没有改变。**D458 联合 SLO 96.45% 仍满足当前 W0 可行性；不是
   因 TPOT 相对退化就判失败。继续优化的主因仍是达标资源高于
   ElasticLocality 21.0622%，以及跨场景 G1/G2 尚未完成。

下一步限定为复用 D456 已有 10 个原生 GPU core 的函数级采样和 D351–D355
历史，定位尚未覆盖的当前控制事务；D457 只改变控制器文件视图，未修改
原生 worker，因此可用于候选定位，但不将 D456 的观察器运行当作 D458
的时间份额证明。不再扩展更多条件组，不先重跑 GPU profiling，不盲目重复
C8、token-budget 或阈值扫描；证据支持后登记一个公式等价的实现候选。

## 原始资料与既有优化边界

本轮核查 [vLLM 0.30.0 core 源码](https://raw.githubusercontent.com/vllm-project/vllm/v0.30.0/vllm/v1/engine/core.py)：
原生循环处理输入后推进模型，utility 可以占用控制执行路径；这是检查事务的
依据，不能把它当作本机新测量。D355 已实现完整事务间交错，不能再次“开启”
同一优化。[vLLM 优化文档](https://docs.vllm.ai/en/latest/configuration/optimization/)
说明 prefill/decode 的调度权衡；本项目已有 chunked prefill，D306 也做过
token-budget 候选，不能仅凭重叠重做旧干预或套用其他 GPU 的推荐值。
D329 的跨请求 HOST 缓存反例、D352 的同事务证据复用边界继续有效。
