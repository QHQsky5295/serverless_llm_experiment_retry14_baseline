# D336：检验按实际接纳容量推导的扩缩容工作点

2026-10-08；7B 开发候选，尚不是正式达标或性能改进结论。

## 问题、已有证据与一个可证伪假设

D335 完整 4000 请求已结束并备份，不重复短测或同配置筛胜运行。其物理
U=15748.053154 GPU-s、平均/P95 TTFT=1202.490/2857.905 ms；D332 对应
15382.488214、1175.624/2715.336。D335 增加的 U 主要来自少了实际释放
间隔，不是最终清理变慢。仅单次开发观测，不能宣称显著退化。

历史 D88 以单副本 C=2 推导 7B queue/active 软目标；D298（配置资格提交
9cd6a4a）验证 C=8 后，后续 Full 仍保留原目标。软目标低于硬上限是合法
设计，不能把它直接称为错误。但旧设置可能过早扩容，并使当前中等接纳
占用无法进入持续低负载回收窗口。

假设：在不改变 IEEE 控制律、延迟保护和实际接纳容量的条件下，将原 D88
容量规则应用于 C=8，能够减少完整 W0 的持卡时间，而服务质量不会出现
不可接受的损失。若 U 未下降、尾延迟/联合 timing 明显受损、保护条件长期
阻止回收，均保留反证；不再提高目标、降低最大卡数或放宽 SLO 寻找胜出。

## 唯一配置因素：同一容量规则的新工作点

| 字段 | D335 | D336 | 来源 |
|---|---:|---:|---|
| queue_upper | 2 | 8 | C |
| active_upper | 0.5 | 0.875 | (C−1)/C |
| active_lower | 0.25 | 0.4375 | active_upper × m/(m+1)，m=1 |

queue_lower=1 保持。D88 的规则从既有生成器抽为
`derive_ieee_capacity_targets`，原完整生成器也调用它；不是复制三个无来源
常数，更不是新的在线预测器。确定性测试覆盖 C2/C8、非法类型、严格上界、
完整低负载窗口，以及缩容后总体接纳比例不立刻越上界的原有条件性关系。

该关系只在同构副本、回收瞬间 A 不变且每副本 C 固定时成立，不保证队列
均衡、KV 可行性、将来负载、吞吐拐点或延迟。服务仍独立执行物理 admission。

保留 min1/max4、C8/slot8/rank16、0.92 显存比例、1024 token budget、160/24
服务/准备 profile、路由/驻留/准入、D333 合并操作实现、TTFT 上限5000、
下限2339.924886357039 ms、窗口45秒、cooldown38秒、间隔2秒和原 EWMA。
保留 D333 仅作为已通过功能验证的执行基线，其完整性能收益并未得到证实。
不同时回退代码或限制为两卡，避免混入第二个因素。

## 原始资料和适用边界

- [Ray 2.59 官方 autoscaling 文档](https://raw.githubusercontent.com/ray-project/ray/ray-2.59.0/doc/source/serve/advanced-guides/advanced-autoscaling.md)：目标在途数与最大值不同，应结合端到端延迟测量选择。借鉴这种区分，不照搬默认值或20–50%经验数。
- [Knative concurrency 文档](https://knative.dev/docs/serving/autoscaling/concurrency/)：软目标和硬限制服务不同目的。它不证明本次容量规则或工作点最优。
- 项目历史 `D88_DEVELOPMENT_CONTROL_DERIVATION.md`、D298 capacity contract、D300 的 Full 延迟下界修订、D325 实际 drain/withdraw、D332/D335 完整阶段和生命周期结果。

两项在线官方资料于2026-10-08重新核查。IEEE max-score、三个条件全低且
持续 cooldown、真实 allocation/release 以及九式均不变。缺 TTFT 仍未知，
不补零，不删除延迟条件。原 `workload.concurrency=2` 是保留的输入身份，
当前外部 open-loop 和实际 runtime cap8 不由此缩成全局2并发，不能盲改。

## 执行与判读

1. 先通过 CPU 配置/控制边界测试和保护检查；不重复 D334 或旧 profiling。
2. 新独立目录 D336，复用已有 trace、500逻辑工件和已批准 D78/D80 发布缓存；
   固定输出、真实 HTTP、无请求打包、无附加等待。权重/负载不重建。
3. 测试、diff/SHA/secrets 检查并推送 V2 后，以原受控 runner 执行完整4000
   请求 W0，非正式开发身份、不裁前缀、不启用详细 profiler、不作新图。
4. 一个重型任务；推理机150/100 GiB及防 OOM 限制不变。磁盘恢复只删除
   核验过的公开下载归档，不删除提取后安装包、环境、工件或唯一测量。
5. 完成后先释放本轮资源，再用原完整分析器比较 D335，D332 保留为上下文；
   不把优于上一慢候选等同于已优于旧 Prime。原生 token/身份/输出变化、
   TTFT/TPOT/E2E、U 和真实释放间隔、queue/active/TTFT 控制条件均保留。

   尚未封闭，N_correct 不由 token 数量或 slot 身份填造。单轮不出 CI。

## 启动前结果（不属于性能实验）

187项 CPU 测试通过（54.171秒），包括原完整 launch/control/capacity 检查
及新增边界测试。峰值2504757248 B，high/max/OOM/swap事件零。实际组装的
子进程模型配置仍与 D298 contract 完全相同，160/24 profile 正常加载；
除独立输出路径及上述三个软目标外，配置逐字段与 D335 一致。

安装下载归档清理复用旧核验程序：九个明确对象共1590808576 B，先与官方
实际对象的 SHA/大小核对并检查引用/打开句柄，再删除下载副本；提取后的
包、已安装环境、模型、结果均保留。首次因一个旧本地记录无 SHA 字段而
停止，零删除；第二次以官方实际字节作 SHA 验证，未修改旧元数据、未放宽
为 MD5 验证。原始失败和成功记录均存 D336/cache1、cache2。

预检时磁盘161556115456 B、主机可用112497967104 B，通过原150 GiB/102 GiB
启动门槛。只意味着该时刻可以启动，正式启动仍重新检查。保护清单保留
147项中已登记的 baseline replay 脚本差异，不写成全体不变。用户 manifest
SHA不变且不stage。尚无 D336 完整回放结果，不宣称 G1/G2 已达标。
