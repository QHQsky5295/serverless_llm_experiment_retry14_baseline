2026-10-17。D629完整结果已封存并推送ac5ab57；3727/4000联合达标，
不接受为性能改进。这里不启动新GPU回放、不改源码、公式、配置或阈值。

历史D342已经区分许可申请前与申请后等待，并以保守持有下界核查采样容量。
D623/D625显示早期单副本期间的集中等待及稳态准备路径问题，D386更激进
queue触发增加U，D595并行压力读取已经失败并撤销。不能重复这些方向，
也不能把D628组件锁占用改善当作完整服务性能收益。

本轮复用D342已验证的`summarize_dispatch_gate_intervals`和
`summarize_dispatch_capacity_context`。
读取D621/D629完整原始日志的最小字段，检查冻结输入、原生终态、时钟及
阶段恒等式，保存容量采样和实际扩容时间。不重新生成数据或复制完整结果。
确定持有区间为gate-resume至controller-completed；可能持有的外包络为
acquire-entry至terminal。采样时确定持有已覆盖容量，支持该时刻不是纯空闲
容量未唤醒；其余样本保持原因未辨，不能把容量样本插值成精确连续占用。

联网复核：Python 3.12 Future回调通过事件循环调度而非立即调用，因此
Future完成不等于请求已经恢复执行。该语义不是实际等待归因的证据。
参见[官方文档](https://docs.python.org/3.12/library/asyncio-future.html#asyncio.Future.add_done_callback)。
vLLM官方性能说明区分CPU调度开销与GPU计算，支持测量关键路径，而非用单一
组件加速替代服务结果：[官方文章](https://vllm.ai/blog/2024-09-05-perf-update)。
[Llumnix](https://www.usenix.org/system/files/osdi24-sun-biao.pdf)把实例资源与
尾延迟共同评估；这支持检查资源—质量取舍，不证明某个副本下限在本机最优。

额外只描述原到达时间窗内各实际持卡数的时长；“若固定观察轨迹补至两卡”
的缺口不是新配置成本预测，因为扩容、准备、路由、排队和释放均会反馈变化。
不从这个离线量构造新的SLO或虚构min2性能。整个诊断限4GiB、swap0和辅助
CPU，原输入/输出/远端证据与147项历史保护不变，不画图。

本检查结束后必须给出具体下一决定，不继续同一锁微测或无界容量剖析。
完整7B目标、独立数值、3B、dLoRA、A1–A5、S1–S13、成本/审稿文档和最终
图表不缩减。未知独立数值正确性继续保留，不把125条输出hash差异自行判为

1. **观察：**平均TTFT增加306.142ms，其中许可申请至恢复增加287.125ms，
   占新增均值的93.788%。申请前均值反而减少1.661ms。不能用组件锁缩短
   代替端到端收益，也不能把全部退化直接归因于锁、GIL或某个kernel。
2. **时间位置：**D629源序501–1000与1001–1500两个描述窗口的许可等待
   均值分别为2363.070、864.263ms，后五窗口均不足0.071ms。这些500条
   窗口只是报告分组，不是实际rotation100的工作负载phase。
   最长等待请求在1079.993s申请、1102.870s恢复；此前1047.815s缩到一副本，
   1065.032/1067.112s触发两次启动，1102.938/1105.662s记录ready。
   相邻采样出现一ready、两pending和38条尚未恢复申请。事件与采样边界
   不同，不能以恢复早于ready记录的约68ms推导不变量破坏。
3. **解释边界：**启动重叠是关联，不是可扣除的“启动造成时间”。只有
   部分采样能由保守持有下界证明容量已满；其余样本原因未辨，不等于
   已证明容量空闲。物理持卡不等于ready，单卡时长不能量化完整服务缺口。
   不从113秒的固定轨迹缺口预测min2新增U、改善SLO或预算可行性。
4. **决定：**不接受D628为性能优化，不运行其W0/W1。下一实现动作仅按
   已备份差异撤回D628的私有hash移锁改动及专属测试；保留D606/D610、
   D618正确性修复、所有结果和失败。不重跑原D621/D629键，也不展开第二轮
   锁微测。回到已核验父实现后，下一单一假设是7B模型级min1→min2，
   max3不变，保持九公式及全部阈值/批量/profile/层级/准入/远端合同。
5. **可证伪检验：**只验证这一资源边界，跨W0/W1/W2冻结；两个initial
   副本的准备与持卡全部计量，不免费预热、不强制未来扩容、不改变到达。
   先CPU边界/生命周期资格，再新执行键完整W2；若达标再同点W1/W0，
   不拼接历史点。W1父点U=6519.896、预算6756.571，余量仅236.675GPU-s，
   因而多保留副本可能破坏G2，必须实测；失败保留，不反复重跑寻优。

min2是经历史瓶颈支持的部署候选，不是新算法或自动学习结论，也不是保证
最优。工业系统也明确区分持续副本下限与仅初始化规模：
[Knative官方scale bounds](https://knative.dev/docs/serving/autoscaling/scale-bounds/)。
借鉴其边界表达，不在原k3s中部署Knative，也不替换论文控制律。
本机已登记configs/ieee_tc未见min_instances大于1的配置；这一有限检索
不证明整个机器所有历史都未用过min2。
