# D740：初始化后准备执行的消费视图研究

## 问题与历史边界

D734 的控制器业务栈中有 14/536 个样本进入 `execution_bundle_copy`；
D733 记录完整规划输出平均约 1.407 MB。这些只支持检查对象展开的工作量，
不是独占 CPU 时间，也不能将 worker-finish→parent-join 全部归为解码。
当前完整 3B 父版 D736 联合达成 92.65%；D737 的消息延迟解析候选在
D738 完整回放中退化，D739 已恢复父版。本研究不是再次延后 RPC 解码。

检查过的已完成/关闭方向：D163 已消除成员查询的重复解码，D159 已将纯
执行目标构造合并到规划事务，D193 已精简输入中不消费的原生详细描述。
本次改变的是**已验证规划结果→初始化后执行器**的消费边界，不更换选择器、
不缓存过期物理状态、不删执行重检查、不重做这些旧方向。

## 依赖与原型

完整原始计划、选择和执行目标保持不变。初始化后的执行器实际需要：

- mode、profile_id、原计划 SHA 与 replacement_policy；
- 已选 HOST/NVMe option；
- 已选 GPU 的 selected_source，以及 native owner_id；
- 完整 selected 和完整 file/GPU objectives。

特别保留 objectives 中**所有**来源，包括未选 adapter；执行时新的物理
victim 仍可能需要它们定价，不能只留下选中 ID。pre-init 在 engine-ready
后重建 GPU 目标、显式 file-only replacement 需要完整输入，保留原合同。
投影视图不是新的完整计划；普通校验器拒绝其作为规划输入。

原型只在独立 CPU 进程中替换执行 helper 的返回副本，没有修改生产代码、
运行 GPU、访问真实远端或新增工件。使用既有四逻辑 adapter 夹具，保存全部
三轮交错、每轮100次组件调用；另运行既有27项执行测试。不是500池服务测量。

[vLLM 0.30.0 的 scheduler output](https://raw.githubusercontent.com/vllm-project/vllm/v0.30.0/vllm/v1/core/sched/output.py)
按新/既有请求区分通信内容，并避免复制消费者不读取的 block tables；
可借鉴的是消费边界设计，不是把它的缓存或性能数字直接移植到本系统。
本次仍在同一规划事务构造执行描述，不复用跨时刻来源状态。

时间均为每次 decode 的 wall µs；轮次不是独立性能运行，不计算CI。

选择、完整目标及原计划 SHA 全部一致，投影视图作为完整输入被拒绝。
27项通过，30次初始化后消费使用投影，1次 pre-init/file-only 保留完整视图。
包含文件/GPU混合链、陈旧 epoch、取消、共享目标、原收益、原生 fallback
持有/释放及 sibling 身份变化。检查145项保护文件及5份生产/测试源 SHA未变。
峰值510,738,432B，high/max/OOM/swap0；最终释放回执另存原始目录。

解释：原型确实减少此消费环节的对象展开，但要多编码/传输/保留一份执行
描述，小夹具额外字节约原完整 payload 的27%–28%。尚未测500池的净收益、
IPC竞争或端到端效果，不能由微秒比例推导 TTFT/GPU-s 改善。
