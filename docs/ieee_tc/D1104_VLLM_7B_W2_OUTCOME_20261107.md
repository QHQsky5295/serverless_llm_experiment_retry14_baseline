## Failure and diagnosis

The first attempt used the same name-only subset that ServerlessLLM's
request-time path accepts.  Static vLLM staging calls the strict
`HttpArtifactStoreClient` path, which requires a frozen file-level
`artifact_content_v1` manifest.  The staging helper had not loaded that
manifest, so the client rejected the prepublished response with:

```text
RemoteArtifactError: published object requires matching frozen content manifest
```

This happened before any model process or request replay.  It was therefore a
missing baseline input-contract binding, not a performance or model failure.

The authoritative 7B manifest is
`paper_results/ieee_tc/inputs/20260927_7b_materialized_content_index.json`.
Its client canonical digest is
`684c7ab113b6a51b694066753b340fce4eb0b26f565e1f9b7ebbd97d3b8ea050`.
The remote prepublished response for `code_lora` returned the same digest;
the one-adapter strict staging probe completed successfully with file-level
content verification.  The remote service's name-only manifest also contained
exactly the same 500 adapter IDs as the W2 subset.  No alias or unchecked
content mapping was introduced.

## Minimal compatibility correction

The baseline repository now accepts
`VLLM_REMOTE_ARTIFACT_CONTENT_MANIFEST` for `static_remote` and passes it to
`materialize_remote_adapter_subset.py`.  HTTP staging configures the frozen
manifest and calls `download_artifact(..., require_content_manifest=True)`.
The change is a qualification/input-contract correction only; it does not
alter routing, caching, vLLM engine arguments, trace, adapter selection,
bandwidth, or the request protocol.
