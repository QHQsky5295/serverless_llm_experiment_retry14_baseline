# D104：准备目标的有效期与实时缓存集合

2026-09-28。基础证据版本 `587ce9f476cbeadb21bccaa283b77c5fb13d1382`，
此前生产版本 `2f1bc4ba1d9fb3a1b17428390c4c3c63dbb09f1d`。
这是 Prime IEEE Full 的正确性验证，不是性能或正式 SLO 结果。

## 观察、假设与限制

D103 的 4,000 请求诊断在 59 条到达、58 条提交后中断。此前的异常把
来源集合覆盖不足、名称/路径冲突、GPU 未确认合并为一个错误。原始失败 RPC
没有回执，因此不能追认当次一定是哪一个条件成立，也不能归因于采样器。

本轮检验一个具体假设：计划注册不是缓存预留。普通请求在注册后加载新的
adapter，可能使原本完整的冻结收益/后备来源集合不再覆盖当前缓存；此时旧计划
应明确结束，而不是执行未定价驱逐或终止整个服务。已有身份冲突仍然报错。

两个 CPU 反例调用真实 native owner、按需加载与公共任务队列，原生缓存和
模型对象使用既有测试替身，不执行 CUDA、不生成实验权重或工作负载。
原实现均到达 `residency_manager.py:2505` 并报原 ValueError。
断言确认唯一失败条件是新增 ID 不在冻结集合中；原有名称、路径和 GPU 确认
都保持有效。此因果证据证明实现存在这条缺陷路径，但不补造 D103 的缺失事实。

## 设计依据及公式边界

[vLLM 0.30 原生 LoRA 管理器](https://raw.githubusercontent.com/vllm-project/vllm/v0.30.0/vllm/lora/worker_manager.py)
允许按请求加载与 LRU 替换；单次 core 操作串行不意味着整个多 RPC 准备计划
具有原子性。[Kubernetes 的版本冲突语义](https://kubernetes.io/docs/reference/using-api/api-concepts/#updates-to-existing-resources)
也区分旧版本操作被拒绝和读取新状态后重新处理。本次只借鉴这一区分，不复制
其重试实现，亦不把这些外部资料当作本机性能证据。

IEEE 九个公式及需求、收益、逐层预算、admission 和物理容量语义不变。
不放宽任何预算、不延长 deadline、不添加轮询、重试系数或隐式来源兜底。
冻结 profile、后端、权重、trace、真实远程交付和计量协议 V1 不变。

## 一致的生命周期处理

| 情形 | 处理与安全条件 |
|---|---|
| 新的完整、同 owner 后继状态超出旧目标的来源域 | 在准备/定价之前结束旧目标，保留实际负面观测 |
| controller 已观察到集合改变 | 不提交旧准备 RPC，不取得额外文件后备引用 |
| native commit 处发现集合失效 | 返回绑定 plan/hash/lease/epoch 的明确未执行回执 |
| 混合层级成本计算 | 移至同一串行 native 操作中，先验来源域，再读取真实 footprint 定价 |
| 目标已经被正常请求准备为 confirmed GPU-ready | 保留直接复用，不因无关来源增加而一律撤销 |
| 来源身份冲突、未知 CPU 来源或未确认 GPU | 继续失败，不视作合法集合更新 |
| 回执丢失、错误 owner/clock/plan/hash/lease/epoch 或矛盾 acquired | 所有权未定；不以此释放文件后备引用或伪报成功 |
| 明确失效后的收尾 | 等待已执行动作结束、关闭 GPU/文件计划、释放已确认引用，再接受 superseded |
| 后续稳态周期 | 正常重新观测和规划；旧 objective 不自动重试 |
| 受控 handoff | 原有不允许静默改目标的规则保留 |

复用既有 `PreparationPlanSuperseded`、公共队列终态及收尾机制，未增加第二套
调度器或恢复框架。成本提供函数只是同一 native 事务内的延后求值，不是新公式。
