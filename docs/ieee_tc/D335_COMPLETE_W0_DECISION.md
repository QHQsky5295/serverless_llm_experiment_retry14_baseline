# D335：合并原生操作未在完整 W0 上改善资源与尾延迟

2026-10-08。7B 开发优化主线；D333 候选的原 4000 请求完整回放及核验
完成。没有重跑筛选、改 SLO、生成新工件/负载、覆盖历史数据或绘图。

## 结论与比较身份

**不把 D333/D335 接受为已验证的性能改进。** D334 的 100 请求短测收益
没有延续到完整 W0；不能用短测替代此结果。D335 的平均 E2E 略好，但
物理 GPU 占用、平均/P95/P99 TTFT、平均/P95 TPOT 均未好于 D332。
每配置只有一次完整开发回放，不能据此证明因果退化或统计显著性，也不
追加相同运行寻找胜出。当前代码保留可回退 checkpoint，不因此冻结正式工作点。

D335 实际代码 `e0b1060d906ee401bba5468c4330d6cb0b114c43`；服务改动来自
`74587830983bd28fd4791ed8ffeec9192262c56d`。相对 D332，唯一服务候选是
选中 GPU 来源时把 pending 登记与保护合入一次 native core turn。HOST
次序、九式、配置、160/24 类 profile、生成和远端协议不变。配置仅三个
输出/冷缓存路径有身份差异。两轮输入和执行合同的对应字段逐请求核对通过。

## 为什么不能把“少一次调用”当作服务收益

2009 个最终 GPU 来源请求有 `single_native_core_turn_v1` 凭据；973 HOST、
881 NVMe、137 Remote 未进入该分支。触发是实测的，但不是因果节约计数。
原生 scope 发布仍有 2890 次、种入 67892 个 scope、命中 8933 次；不能
从这些计数直接推出避免多少 RPC 或减少多少 GPU-s。

| 平均 admission 分项 (ms) | D332 | D335 |
|---|---:|---:|
| 计划到达到接收 | 218.301 | 228.491 |
| dispatch 窗口等待 | 33.803 | 31.098 |
| runtime 选择/保护包络 | 344.607 | 347.121 |
| 总 admission | 596.710 | 606.710 |

前 3 项可加；routing 的 71.717→77.715 ms 已包含在 runtime 包络，不能
再相加。runtime 包络包含来源确认和保护，不全是缺少推理容量的排队。
本次没有观测到候选希望减少的完整负载平均 runtime 等待。不同运行的
路由/缓存/并发轨迹会变化，不把条件 GPU-hit 组当成共同请求因果对照。

## GPU 占用退化来自何处

复用已有 `lifecycle_gaps`，按每张卡实际 allocation/release 区间验证：
`U = 首次持有至最后释放的 envelope 总量 − 中间真正释放的间隔`。

| 物理资源分解 (GPU-s) | D332 | D335 |
|---|---:|---:|
| 首次至最终释放 envelope | 15840.039268 | 15845.145223 |
| envelope 内实际释放间隔 | 457.551054 | 97.092069 |
| U | 15382.488214 | 15748.053154 |

所以增加的 `365.564940 = 5.105955 + 360.458985` GPU-s，主要对应实际
释放间隔缩短，而不是终态清理延长。D335 唯一释放间隔为业务开始后
647.828361→744.920430 秒；该恒等式不估计任何未执行策略的反事实收益。

1865 次控制观察中，扩容/缩容动作从 D332 的 9/6 变为 D335 的 4/1。
低队列且低 active 的观察数 1400→1471，其中仅 TTFT 条件阻止 all-low
的次数 845→992；all-low 555→479。控制阈值和 38 秒持续窗口未改。
这些解释实际轨迹的差别，不证明应该增加阈值、删除 TTFT 条件或强制缩容。
更少启动也没有自动转化为更少资源，因为绝大部分时间仍持有四卡。

## 下一主线问题，而不是再重复这项优化

D333 的最小验证和完整验证到此结束，不再重复 D334/D335、D328 profiling、
D295 数值块或既有 profile。下一项优先回到资源工作点：区分推理容量边界、
触发扩容的队列压力与控制路径自身等待，核对旧 C2 soft targets 与当前
cap8 的关系；不得把更大的 hard capacity 自动等同于合理 soft target。
尚未选择新配置、修改 controller 或启动新性能运行。

重新核查的 [Ray 2.59 官方调参说明](https://raw.githubusercontent.com/ray-project/ray/ray-2.59.0/doc/source/serve/advanced-guides/advanced-autoscaling.md)
要求依据端到端目标测量 ongoing-request 目标；
[Knative](https://knative.dev/docs/serving/autoscaling/concurrency/) 明确区分
软目标与硬上限，并警告不合适的硬限制可能增加延迟。这只支持核查方向，
不支持照搬默认值或预报两卡足够。Ray 网页429后核对了官方版本源码。
[HydraServe](https://www.usenix.org/system/files/nsdi26-lou.pdf) 同时检验 SLO
与资源代价；不据此更改本项目已冻结的物理 GPU-s 或共同评价条件。

当前可用磁盘低于新重型任务的150 GiB门槛；后续启动前先依既有规则回收
可重建缓存或核验无损压缩，不能放宽门槛、删除唯一测量或混入性能期。
数值、共同 warm/Resident、新旧 Prime 的 G1/G2仍开放；顺序保持7B→3B→
基线→主比较→消融与敏感性。此报告关闭的是一项假设验证，不是7B或总目标。
