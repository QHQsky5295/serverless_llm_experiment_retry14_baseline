## 历史与可证伪假设

D843观察到长回放后文件观察耗时增长，但采样不是纯CPU/GIL因果证据。
D844只将第二遍stat换为批量FFI，仍重新生成所有Python元数据，其capture组件
9.311495→10.257258ms，未被接受。D854全owner异步方案联合达标下降82请求，
D855已撤回。二者均不重复。

新的具体边界：在**同一次锁内观察**中，C保留首次实际lstat记录，Python只
转换首次记录用于既有核算；第二遍重新lstat后在C内对比，返回完成/错误，
不再构造第二套Python stat和签名。首次目录遍历也在同一原生调用内进行。
没有跨调用缓存、TTL、线程、延迟核验或跳过物理分配检查。所有输出仍在
第二遍成功后才公开。已成功settlement的逐路径额外stat和FIEMAP逻辑保留。

它确实删除了第二套Python元数据/签名构造，但新增首次native→Python转换、
DFS排序和边界数组；**净收益未确定**，只作有界组件验证，不预报服务收益。

Python官方明确DirEntry.stat缓存不能代替新鲜os.stat；本候选仍使用两遍新鲜
lstat。[Python os文档](https://docs.python.org/3.12/library/os.html#os.DirEntry.stat)
CPython的单次stat在系统调用边界释放/重取GIL；这只是实现事实，不足以断言
本机慢因果。[CPython 3.12源码](https://github.com/python/cpython/blob/v3.12.0/Modules/posixmodule.c)
vLLM的官方优化记录说明CPU对象/调度开销值得实测；不移植其百分比或跳步策略。
[vLLM原始实现说明](https://vllm.ai/blog/2024-09-05-perf-update)

## 结果：未显示净收益，不进入 GPU 回放

19项相关检查通过，999文件/1003路径的完整输出一致；每路径两遍新鲜
观察由原生成功完成数及Python调用数交叉核验（不是strace测得的syscall数）。
首次编译/测试直接完成，无失败重试。既有147保护项和生产源码保持不变。

原始交错组件调用如下，单位ms；这是组件调用，不是独立性能运行或CI：

| 模式 | 父版三次 | 候选三次 | 均值相对变化 |
|---|---|---|---|
| 不返回观察映射 | 9.019500 / 9.314586 / 9.822265 | 9.806405 / 10.648113 / 9.352042 | +5.8609% |
| 返回观察映射 | 12.517445 / 11.254877 / 9.354332 | 11.898819 / 11.236793 / 10.135477 | +0.4360% |

小差异不作显著性判断。单独cProfile显示Python签名调用确实从2006减为1003；
但新增首次记录转换、排序和数组准备抵消收益。返回观察映射时原生会话
`__enter__`累计9.040ms、validate累计1.551ms；这些带仪表数值不能与上述
普通计时相加或视为真实服务等待。没有测出在线GIL竞争份额。

决定：关闭D856这种ctypes事务边界候选，保留诊断源码/全部点，不接入生产，
不因某一次较快而选择该点，不追加GPU验证。D846仍是恢复参照，不是达标版。
没有通过删核验或缓存旧事实来弥补这个负结果。
