# D100：源副本失效与准备任务的完整生命周期

日期：2026-09-28。基础版本 `b1cfa3b04623c03ad59597b816b6db57d35114ee`。
这是 Prime IEEE Full 的开发期正确性工作，不是性能实验或正式对比。

## 原始问题与可证伪假设

D99 Full4000 attempt6 在 843 条成功、302 条整轮取消时中断。
失败来自 GPU 准备动作检查其原生 HOST 来源的边界。旧报错同时覆盖
“来源缺失”和“名称/路径不符”，当次日志没有记录具体谓词，不能追认
究竟是哪一个条件成立。全部历史数据原样保留。

源码显示：准备计划的目标保护不等于永久持有原生 CPU 张量；普通请求仍可
驱逐未引用对象。合法驱逐后，不应使用失效来源，也不应把这次无操作的拒绝
当成整个服务的永久失败。更重要的是，原队列把所有异常记为 `failed` 并保留
物理目标键，因此仅更换一个异常名称仍不能让新计划接替。

本次假设：明确、完整的后继状态证明来源已不存在时，结束旧动作和旧计划，
待现有所有权全部结束后由正常规划周期重新观察；未知状态或真正失败必须继续
报错。由实际队列、原生缓存回调、规划器和驻留任务回收路径共同检验。

## 参考与论文约束

[vLLM 0.30 官方 LoRA manager](https://raw.githubusercontent.com/vllm-project/vllm/v0.30.0/vllm/lora/worker_manager.py)
包含按请求加载、复用和 LRU 驱逐；其单线程 core 操作并不使多个控制 RPC
组成原子事务。这支持区分快照和引用，而不是要求关闭原生缓存。
[Kubernetes API 冲突语义](https://kubernetes.io/docs/reference/using-api/api-concepts/#updates-to-existing-resources)
区分旧版本更新冲突与重新读取状态后的处理；这里借鉴结果分类，不复制重试策略。
以上仅为设计依据，不是本机收益证据。

九个 IEEE 公式、需求权重、准备收益、admission、资源容量、冻结 profile、
生成协议、工作负载、deadline 和远端交付方式均不变。不增加轮询周期、经验系数、
旧计划自动重试或来源兜底。按请求打包仍为零，已发布缓存无需重新生成。

## 一致的处理规则

| 观测/结果 | 执行语义 |
|---|---|
| 同 owner/clock、完整缓存覆盖、严格后继 epoch，目标不在 registered 或 staged sources | 记录确切负面快照；在提交 prepare RPC 前结束该动作 |
| 同一动作有多个订阅者 | 全部观察同一终态；不重跑旧闭包；新计划可以使用相同物理目标键 |
| 已延后动作后来发现来源消失 | 保留 deferred→superseded 历史；不由 wake 复活旧动作 |
| owner/clock/epoch、完整覆盖或 staged 记录非法 | 继续失败，不推断驱逐 |
| 同一整数 ID 对应不同名称/路径 | 继续失败，并保留 expected/observed 身份；不当作普通过期 |
| 尚未确认释放、关闭失败，或并行实际动作失败 | 真实失败优先，不能返回正常 superseded |
| 正常驻留任务 | 旧计划清理后返回 superseded；后续正常周期使用新观测 |
| 受控 handoff | 仍传播 supersession，不静默改变其受控目标 |

复用 `NativeSourceSnapshot` 校验和 `PreparationPlanSuperseded`；队列增加显式
superseded 终态。故障目标键仍保留，不能把任意 RPC 异常翻译为可重试。
并行收尾除等待任务结束外，还检查实际动作结果：首个正常冲突不得遮蔽其余
动作在取消/释放阶段的真实失败。

文件 NVMe 来源失效和来源身份冲突的既有校验没有被一律放宽。本次有真实驱逐
反例支撑的是原生来源缺失边界；不把未经定位的所有 ValueError 都改成可继续。

## CPU 因果验证与状态表

| 检验 | 结果/意义 |
|---|---|
| 修改前：GPU 动作前真实驱逐 | 实际驻留回收传播旧 ValueError |
| 修改前：原生 staging 前真实驱逐 | 实际驻留回收传播旧 ValueError |
| 修改前：共享动作抛出已验证过期信号 | 队列错误标为 failed，不能正常接替 |
| 修改后上述两个驱逐边界 | 旧计划和引用关闭，新计划实际完成同一 adapter 的 GPU 准备 |
| 完整性、外部 owner/clock、非法 epoch、身份矛盾 | 不接受为 supersession |
| 关闭未确认、受控 handoff | 分别保留失败和不允许静默重规划的语义 |
| 本地复核：兄弟 GPU 动作、文件动作在收尾时失败 | 反例证明旧 gather 只处理首错会遮蔽失败；修正后保留真实失败 |

这些使用现有 CPU 原生缓存 fixture 和真实文件所有权，不执行 CUDA 模型。

profile 后，`red3.log` 才是有效的两个因果反例。首轮文件兄弟错误测试也因
fixture 选择不同目标而提前失败；`file_review_red2.log` 才到达预期反例。
所有日志保留，不把 fixture 错误当作生产失败证据。

## 结论边界与下一步

本次支持的是特定状态变化的安全继续语义，不证明 D99 原始失败一定为“缺失”
而不是身份冲突，不证明排队瓶颈全部消失，也不证明完整性能、共同 SLO、
数值 LoRA 可区分性或优越性。历史中未记录的事实不补造。

完成最终回归和备份后，按同配置执行独立的 canonical 3B Full4000 W0 attempt7。
仅源码版本和本轮独占输出/缓存目录改变；原输入、已发布工件、60 秒通知、
1,800 秒到达起算 deadline、实际资源包络均保持。之后仍按清理→校验→状态表
决定下一步，不重复 profile/短前缀。3B 合格后才进入 7B；基线仍暂停。
warm SLO、Resident、M1/M2、A1–A5、S1–S13 的待办状态不因这些测试而改变。
