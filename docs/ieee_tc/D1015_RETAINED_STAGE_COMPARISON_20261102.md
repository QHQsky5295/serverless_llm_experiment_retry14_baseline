## 3. 优化方向裁决与当前证据缺口

已核对D721–D725、D863/D868、D886/D887、D997和D1004–D1014：

- 不重开chunked-prefill开关或无依据扫描token预算；扩展图捕获已经启用。
- 不重开完整文件事务线程、独立文件owner进程、ISA-L、物理清点微优化。
- 不再仅调查询顺序、提前等待文件、常驻数量或控制调用延后。
- D863的旧前缀控制/step剖析曾指向同步控制事务，但它早于当前文件owner、
  物理清点与arrival-prefetch修改，不能把旧占比充当D1000的当前实测占比。
- D1000完整结果保留原生请求边界，但没有该问题所需的逐控制调用/engine-step
  thread-CPU分解。此次源字段检索没有找到相应计时字段；不从包络补造CPU值。

**下一具体问题是：当前短输出解码窗口中，同步控制事务还是实际engine-step
仍占主要延迟？** 复用D863已有host_spans_v1和原前1000请求诊断入口，仅将
配置绑定当前保留D1000，保持原输入与观察上限，不另造完整profile框架。
若现有同版本原生span能补足则直接复用，否则只做一次有明确覆盖边界的诊断；
不以诊断的SLO代替完整4000，也不为凑样本重跑。当前尚未创建或启动该执行键。

分析必须先分控制事务、input非控制、engine step、其余；只有定位到此前未
处理的实际依赖，才登记一个新候选。控制主导不等于允许恢复已拒绝的deferral；
step主导也不等于立即改batch/token。没有新定位时保留未知，不连续追加小补丁。

本轮联网复核了[vLLM 0.30.0 EngineCore](https://raw.githubusercontent.com/vllm-project/vllm/v0.30.0/vllm/v1/engine/core.py)：
busy loop先处理输入再step；本地已有atomic_control_yield，不能重新宣称发现
“一次处理太多utility”。[官方优化说明](https://docs.vllm.ai/en/v0.30.0/configuration/optimization/#chunked-prefill)
指出prefill预算涉及ITL与TTFT取舍，没有提供本机应直接采用的最优常数。
官方机制支持区分观察边界，不能证明本机当前瓶颈或候选收益。
