## 3. 与存储维护同步推进的3B问题

距3800差85；U=11929.629332GPU-s，预算12083.063870。D711独立数值

启动反馈提前扩容导致资源增加，不能把延迟变化全部归因于D845局部查询。

复用D847现有4000请求分组（单轮条件均值，非共同跨系统因果组）：

GPU组的acquisition在准入前已完成，0不表示所有GPU获取均免费。Remote组
有505次实际获取与8条没有新获取的请求；不把两种样本定义强行改成一致。

复用D846已经核验的505条client transfer projection，按D818同钟顺序边界
统计；下列所有传输都有published终态，仍不把transfer当独立实验重复：

| 客户端顺序阶段 | 平均ms | Type-1 P95 ms |
|---|---:|---:|
| 获取开始→HTTP headers | 3.373 | 6.497 |
| 空间预留＋接收＋写盘 | 254.724 | 1031.145 |
| body完成→解包开始 | 0.143 | 0.214 |
| 解包/结构核查 | 85.178 | 153.534 |
| 解包完成→文件确认发布 | 352.502 | 1096.758 |
| 发布→获取线程完成 | 114.908 | 347.806 |
| 完整获取线程跨度 | 810.828 | 1881.129 |

同一505次传输的平均阶段可加和，P95不可加；也不能从513条Remote请求的
平均准备时间减去505次平均获取时间，推造“获取前等待”。发布后的清理已经
可以与消费者执行重叠（D831），不把114.908ms全部当请求关键路径。

505条服务端记录均sent且pack_performed=false。平均对象打开0.052ms、
对象读取2.124ms、socket write累计230.801ms、发送包络232.955ms；这些
服务器跨度与客户端跨度重叠，不能相加或跨主机减绝对时刻。socket write
可包含接收端背压，不能称为纯链路传输时间。仍保留所有真实传输时延。

源码核对：客户端在headers后先调用reserve_files，再读response body；因此
254.724ms明确含本机空间检查/预分配。publish_transfer在owner事务内先做
最终物理容量检查，再核查目标文件内容和身份并发布；352.502ms是该包络，
不是已经分辨的SHA、锁等待或stat耗时。D825已经去掉解包流的重复payload
SHA；本轮不再次“优化”相同步骤，不去掉发布前唯一内容校验。

## 4. 原始资料、历史排除与下一项有界工作

本轮在线复核[dLoRA OSDI论文](https://www.usenix.org/system/files/osdi24-wu-bingyang.pdf)
的adapter-aware调度：其等待估计同时考虑adapter加载和队列。此处借鉴的是
区分准备与排队成本，不替换PrimeLoRA的九式，也不由文献推导本机瓶颈份额。
[S-LoRA官方说明](https://github.com/S-LoRA/S-LoRA/blob/main/README.md)和
[MLSys论文](https://proceedings.mlsys.org/paper_files/paper/2024/file/906419cd502575b617cc489a1a696a67-Paper-Conference.pdf)
采用HOST驻留及统一页池管理LoRA/KV；其内存模型不能直接当作本项目
真实远端/文件层级场景的免费前提。

维持已关闭方向：D514/D516完整GPU执行快照替换，D329跨调用容量缓存，
D595/D598并行pressure ACK，D628/D629发布SHA移锁，D712/D713缩容阈值，
D733整体to_thread，D737/D744规划时序，D822共享压力，D834成员复用，
D844事务内批量stat，以及D839/D840解码继续调参。现存包络大不构成重开依据。
