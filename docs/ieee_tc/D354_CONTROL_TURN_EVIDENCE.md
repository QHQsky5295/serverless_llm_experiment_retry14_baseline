# D354：复用已封存日志检验控制操作连续执行

2026-10-08。继续7B优化；这是D351诊断日志的离线分析，不是新GPU实验，
不改变D353结果、服务代码、九个公式或冻结评价协议，不生成性能图。

## 问题与结果

D353普通Full的4000请求已全部完成原生数量合同，但暂定联合时延通过
3752/4000，尚未达到3800，且相对D336的TPOT仍退化。
仅减少一次重复清点尚不足以关闭7B。下一问题是：在仍有模型工作时，
多个控制操作是否连续执行，直到整轮输入处理结束才让模型继续？

复用D351的12个完整进程、171284个嵌套span及1000个完整decode窗口。
逐文件核对既有SHA、进程身份、共同时间域及窗口；旧client/input/step
交集与既有统计一致。没有重新推理、重新抽样或从延迟中扣除观察开销。

## 历史与官方实现核对

- D351已有证据显示物理HOST清点和准备是昂贵的同步控制操作；D352只
  复用同一已确认GPU命中事务中的第二次HOST证据，D353检验其完整收益。
  D354没有重复这些统计，而是增加“操作是否在同轮连续执行”的信息。
- D329否定跨请求HOST清点缓存的安全性；这里不重提那条路径，不以陈旧
  清点或删安全检查换延迟。D333的pending+GPU引用保护仍必须原子执行。
- 已检查本机与[vLLM 0.30.0官方core实现](https://raw.githubusercontent.com/vllm-project/vllm/v0.30.0/vllm/v1/engine/core.py)：
  busy loop先处理输入，再执行engine step；输入处理在等待阶段之后继续
  排空可用client请求。这与日志中的连续操作一致。保存本机文件SHA，
  不假定其他vLLM版本/DP路径完全相同。
- [Sarathi-Serve](https://www.usenix.org/conference/osdi24/presentation/agrawal)
  将prefill/decode干扰作为调度问题研究，支持检查工作交错的研究方向；
  它并未证明本系统的CPU控制路径瓶颈或本机收益。本系统已启用chunked
  prefill，不能重新开启已有机制并称作新优化。

## 客观裁决与下一项最小候选

**假设得到进一步支持，可以进入正确性设计；尚未证明性能改善。**
主要证据不是“出现一次慢操作”，而是在有未完成工作时，约四分之一
非空输入轮次连续执行多个UTILITY；短输出超界组与其有明显时间重叠。
诊断发生在D352之前，且有详细观察开销，不能当作D353的精确归因。

下一候选：在一个完整的Prime同步控制事务结束后，若后端仍有合法
模型工作，让原生主循环获得推进机会，再继续处理后续控制事务。
优先考察无需人为时长阈值的有界交错；不在事务内部递归执行模型。
这只改变底层执行公平性，不改九式、候选选择、预算、权重或输入。

实施前必须验证：

1. 控制请求FIFO及回包身份不变；不能丢弃、合并或伪造完成。
2. 保持idle阻塞、取消/abort、shutdown与异常的原生语义；不因交错
   推迟必要清理而泄漏资源。未知执行器/DP拓扑不得静默套用TP=1设计。
3. pending注册、引用保护、HOST准备/原子准入的单事务不可拆开；模型
   可以在独立事务之间改变状态，后续操作仍必须重新检查实际容量。
4. 测试有工作/无工作、单个/多个控制操作、ADD和ABORT混合、异常与
   取消、空队列、原子事务及扩缩容；记录是否实际交错，不仅检查开关。
5. 最小验证后才做普通完整W0。保持D353配置/输入/远端合同及当前尺子，
   同时报告TTFT、TPOT、联合通过和物理U；交错可能改善decode却拖慢
   admission、改变batching和扩缩容，不能只验收一个方向。

若最小验证没有改善或破坏语义，保留失败并回到下一可证伪瓶颈；不叠加
容量、超时、软目标扫参掩盖。D354尚未修改服务或证明新候选可用。
