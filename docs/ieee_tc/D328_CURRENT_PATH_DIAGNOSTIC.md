# D328：当前 7B 请求路径的一次有界诊断

2026-10-08。状态：入口与安全检查完成，等待启动；不是性能改善或模型验收。

## 为什么仍停留在 7B

D327 已复用 D323/D326 的完整回放：两轮都结束扩容启动后的共同 2,703 个
请求，P95 TTFT 从 2,951.051 增至 3,350.996 ms。排队和服务阶段均有增长。
这排除了“退化全部只来自当时启动不足”的解释，但没有排除较早的缓存、
路由历史影响，也不是对退出机制的因果估计。不增加重试或扩缩容计时补丁。

D187/D200 的栈和控制路径观察早于当前 cap8、实际输出长度类、加载和退出
实现。旧热点已改变，不能直接搬用。当前问题是：在当前配置下，控制器、
frontend 与 GPU core 的同步工作和异步等待分别出现在哪里？

## 单次诊断合同

- 完整沿用 D326 配置；测试断言只有本次独占结果/NVMe/HOST 路径不同。
- 既有 source42 W0 的前 1,000 条索引；原始 4,000 请求与 500 adapter 集合
  不变。不生成负载、权重或新 profile。160 service / 24 preparation 类继续
  通过实际 joint loader 与 runtime model 身份核验。
- 复用 D200 的 wrapper 和既有 `python_frames_v1`：资源准入之后才启用，
  每 2 秒一次、每线程最多 100 帧、无局部变量；实际延迟、idle、截断全部保留。
- 复用当前受限 launcher、独立回放/watchdog、60 秒通知、原生固定输出、
  1,800 秒保护、72/80 GiB 服务限制和真实远端已发布交付。不改九个公式。
- 只运行一次当前路径诊断，不重复 D140 高频采样或 C 栈遍历。带观测器结果
  不与普通 Full 宣称资源/延迟胜负，不生成图或 CI。

观察依据 [Python frame API](https://docs.python.org/3.12/library/sys.html#sys._current_frames)：
帧是采样时观察，不保证读取时仍反映活动。GIL 调度偏差和看不到 CUDA 内部
保留；栈出现次数不是 CPU 时间比例。vLLM 的
[CPU/调度分析](https://vllm.ai/blog/2024-09-05-perf-update)提供检查方向，
不证明 Prime 当前存在同一瓶颈，更不能借用其加速比例。
