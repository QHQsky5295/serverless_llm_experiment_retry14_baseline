## 完成结果：诊断，不是普通 Full 性能点

原生输出数量合同及十项 request/adapter/owner/slot/content/clock 绑定检查
均为 1,000/1,000；失败零，原生 TTFT/TPOT 重算误差零。数值正确性
`N_correct` 仍为未知，不能由输出数量或 SHA 传输绑定替代。文件名中的
`r4000` 是原 runner 命名；本轮实际执行的是已声明的 1,000 请求前缀。

|---|---:|

GPU-s 的互斥分项为：业务前 37.553826、到达窗口 3,931.880653、drain
32.942624、清理 173.971390。总和与实际生命周期一致。包括请求结束后才
启动、没有业务栈样本的最后一组 frontend/core；不删除 unused activation
来缩减成本。详细 observer 开销包含在内，不能与普通 Full 宣称胜负。

1,403 次控制查询均完整成功，无截断日志行。每次调用的边界统计如下：

| 同次调用的区间 | 均值 ms | P95 ms |
|---|---:|---:|
| parent 总往返 | 119.264 | 438.942 |
| frontend 发出 → native 开始 | 62.946 | 316.183 |
| native 开始 → ready | 11.905 | 18.408 |
| frontend ready → parent 收到 | 21.526 | 117.332 |

这些是嵌套/组成区间，不全都可相加；不同调用还可能并发，P95 也不满足
加和恒等式。发出到 native 开始包括传输、序列化和调度，不能全称 GPU
排队；总往返不是单请求 TTFT。当前查询均值主要位于 native 函数外部，
但也不能据此认定函数内部优化不会影响执行循环。

业务期 controller 有 539 次采样。nearest-business-frame 中实时文件库存
32 次、规划源观察 31 次、消息解码 28 次；main 352 次不能直接解释为 idle。
五个有业务样本的 core 中，nearest `add` 分别为 49/355、78/543、86/523、
76/466、4/30。关联调用栈明确指向 `_ieee_lora_host_inventory` 的
`tensor.is_pinned()`，不是 token-event 的 add。采样受 GIL 和周期影响，
上述分数不是 CPU 时间比例，更不是这些操作贡献的 TTFT 比例。
