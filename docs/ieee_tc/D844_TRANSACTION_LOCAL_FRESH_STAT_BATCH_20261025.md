# D844：事务内新鲜文件元数据批量观察（有界组件候选）

承接D843完整诊断；不新增GPU profiling，不修改生产实现、IEEE九式或评价协议。
目前3B W2仍以未插桩D840的92.10%作为性能观测，未达共同95%；D843为诊断。

## 一个假设与历史差异

D843文件观察区间内104个控制器样本中，66处于inventory调用内部；八段文件
观察均值由61.514增至300.142ms。样本频次不是CPU占比，不证明GIL等待份额。
当前函数对每个路径执行第一遍stat和第二遍fresh stat，成功extent settlement
另有一次重查。D606字符串表示与D610扫描合并已经保留，不重复实施；D329
跨轮容量缓存、D627/D631发布锁方向与D733整体异步不恢复。

假设：仅将第二遍的逐路径系统调用合为一次原生调用边界，可减少解释器往返，
同时保持每个路径都重新lstat。第一遍遍历、extent回调/重查、签名/容量判定、
owner锁、输出与发布逻辑不变。没有TTL、跨调用缓存、线程池、重试或异常兜底。
先用已有CPU组件方法判等和计时；无收益则不运行GPU，也不连续扩展候选。

## 原始来源与范围

- [vLLM官方CPU开销分析](https://vllm.ai/blog/2024-09-05-perf-update)：
  CPU对象管理和组件同步可能限制服务。本次仅借鉴诊断方向，不借用加速数值。
- [CPython 3.12 posixmodule](https://raw.githubusercontent.com/python/cpython/v3.12.0/Modules/posixmodule.c)：
  posix_do_stat在每次lstat周围释放/重新获取GIL。批量调用减少这些边界；
  不因此断言当前观察耗时全部来自GIL。
- [Python os官方文档](https://docs.python.org/3.12/library/os.html#os.scandir)：
  DirEntry会缓存stat，本候选不使用它替代第二遍fresh observation。

本次联网重新核查以上来源。native查询采用本机编译的Linux lstat，固定宽度
输出并核对ABI大小；不是Windows/任意文件系统可移植性结论。批量期间仍持
cooperative owner锁，释放GIL不表示转移owner。非合作写入仍由原双遍检测
观察，不把有限扫描称为跨文件原子快照。

## 组件结果：不接入生产，不启动GPU

17项组件断言/既有fixture检查通过，包括完整准备快照、导出签名、第二遍
修改拒绝、跨调用新鲜性、分配包络、特殊文件、硬链接顺序、未初始化extent
保守收费及extent探测时修改拒绝。999文件/1003路径的两版完整输出相同；
第一遍Python查询与第二遍native完成数合计均为2006次fresh stat。没有跳过
第二遍检查、用旧缓存顶替物理状态或修改任何服务源码。
