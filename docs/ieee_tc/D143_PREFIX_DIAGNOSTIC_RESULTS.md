## 2. 观察覆盖与局限

观察器在普通 Python 线程中读取引用，不使用此前失败的 C watchdog 或
高频全子进程采样。它每次写入后等待两秒；实际延迟逐次保留，不假定等间隔。
10 个进程每条完整记录都含主线程，未出现末行残缺；控制器有 3 条、四个

## 3. 有证据的线索，而非已证明的因果结论

控制器业务期最近项目帧包括 source_snapshot 44/570、
_gpu_runtime_snapshot 42/570、_local_file_inventory 39/570、
_footprints 29/570，以及 owned_file_execution_objective 17/570。
因此先前看到一次 file objective JSON 编码，不能据此认定它是唯一主因。
规划器多数样本在接收等待；不能仅凭进程存在断言 planner 已饱和。

四个 GPU core 的业务期最近项目帧 `gpu_monitor.add` 分别为
152/665、137/644、140/643、145/641（21.27%–22.86%）。原始栈须进一步
按 caller 消除同名 helper 歧义；已查看的实际行 80/82 及 caller
`_ieee_lora_host_inventory` 指向 HOST 张量枚举，而非 GPU kernel 执行。
完整 caller 计数与来源 SHA 保存在配套 curated 结果。

当前 source_snapshot 在同一次串行 worker 调用中分别构造 registered
inventory 和 registered+staged inventory；staged 为空时重复枚举同一对象。
单个 add 又对新 allocation 两次查询同一 tensor 的 is_pinned。
这两个静态事实支持“同次观察中存在冗余张量属性查询”的可证伪假设，
但不证明它解释全部控制器等待，也不授权跨状态复用陈旧 inventory。

[vLLM 官方 CPU/GIL 分离分析](https://vllm.ai/blog/2024-09-05-perf-update)
说明同步 CPU 处理可以妨碍推理推进，适合作为检查执行边界的参考；其测得
加速比不适用于本机。下一候选只研究同次观察的等价复用，必须保持 alias
去重、真实 storage 容量、staging、pinning、异常检查和动态源状态不变。
若该候选没有验证支持，不能靠加大容量、超时或删除保护来宣布优化成功。
