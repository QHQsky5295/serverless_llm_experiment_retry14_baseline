## 有界异常核查与可支持的解释

1. 成功响应的平均E2E五段分别为：提交5.805863ms、提交后dispatch等待
   35423.270606ms、service TTFT510211.223972ms、decode19891.718613ms、
   完成通知14.503080ms。主要观测等待在后端dispatch之后；service TTFT包含
   内部排队/调度/准备/prefill，不能称为纯GPU计算，也不能全归因启动。
2. 后半部分同样存在大等待。例如源序号3000–3499的500条全部响应，但
   service TTFT均值908427.232884ms，router queue均值73.014834ms。
   这是事后描述切片，不是独立实验或无启动主结果。
3. 原生日志有50次ILP求解，求解时间总和59.008183002s、最大2.758577108s；
   有54条迁移决策打印、686次请求提及（不是686个独立请求）。实际配置迁移
   不再仅是静态开关证据，但打印位于搬移执行之前，不能当作完整迁移成功
   回执，也不能量化迁移收益。求解span总和不直接加到/减去TTFT，不足以单独
   解释数百秒等待。原生EngineManager、credit/batch调度和DP2路径保留。
4. 严格匹配正常日志得到3378条`INFO ... Finished request`，与响应数一致。
   另11条`Finished request ... not in ... request streams`全部对应已超时ID，
   同一日志中均有更早的Aborted记录；它们不是成功完成，不构成当前证据下
   “先丢失成功响应再超时”的证明。取消之后的计算资源仍计入U。
5. 已检查主worker和Ray错误记录：存在metrics exporter连接警告，未据此
   断言服务失败。未找到可将本轮622超时直接归因于输入、绑定、时间计量或
   适配异常的新证据；这不是所有正确性已证明，数值证明未知保持未知。

主结论限定为：这个保留原生机制的已冻结DP2/TP1工作点在本机完整W1负载
上出现明显后端等待和15.55%请求超时。不能泛化为dLoRA在其他硬件/配置上的
全局最优表现，也不把未拆开的内部等待无证据称为原论文算法缺陷。
低SLO本身不触发参数搜索；保存本轮后继续既定W2。若后续发现具体错误，
只修复并重跑受影响键，保留本次失败。当前未改runtime/analyzer算法。
