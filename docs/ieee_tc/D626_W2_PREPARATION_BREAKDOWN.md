## 判断、反证与下一项检查

1. 当前证据不支持把整个2.43/3.76秒准备包络称为网络传输，也不支持将约
   51/52ms的native load认定为主要瓶颈。远端真实传输仍在用户延迟内。
2. 压力确认与本地发布是具体检查位置，不是已证明的独占原因。D595/D598
   已表明减少局部屏障耗时未必改善整体SLO/U，因此不重试并行屏障或直接
   删除确认、降低检查频率、放松共同阈值。
3. 当前`LocalSourceReferences.publish_transfer`在全局owner RLock中调用
   `_publish_verified_source`；后者逐文件重读SHA并执行发布前后实时观察。
   HTTP路径的解包已经在私有、预留的workspace中完成。此锁也被其他请求
   的来源/容量观察使用。静态事实提供一个可证伪方向，但现有span没有分开
   锁等待、hash、库存核验及发布，不能认定317/456ms全部来自hash。
4. 下一步只做一次有界组件核查：复用现有publication/取消/来源测试，测量
   原路径的锁持有、完整内容校验与文件观察组成，并验证私有transfer pin
   是否足以允许内容校验与全局容量提交分离。保留完整SHA、实时物理重查、
   未发布不可见、取消join与失败恢复。若锁不是重要部分，或不能证明并发
   安全，则拒绝该方向；不再扩展同一诊断、不因此开新GPU回放。最多两轮
   有理由的组件验证，合格后才登记新生产候选及完整回放。

这是一个待验证的临界区假设，不是已接受的生产改动；与D606/D610减少
同一次文件观察中的重复操作不同，不复活D329/D529的陈旧状态捷径。

## 本次官方资料核查的范围

官方资料，未安装、登录或上传本项目数据。以下只提供设计依据，不提供本机

  等待同一同步锁。这是对当前代码的推断，需组件检查。
- [vLLM官方CPU路径分析](https://vllm.ai/blog/2024-09-05-perf-update)：
  支持检查管理工作与推理的同步依赖；不借用其版本、硬件或加速比例。
- [huggingface_hub v0.34.4源码](https://raw.githubusercontent.com/huggingface/huggingface_hub/v0.34.4/src/huggingface_hub/file_download.py)：
  `_hf_hub_download_to_cache_dir`使用repo/etag粒度的锁与incomplete对象，
  `_download_to_tmp_and_move`完成后交付目标。这不是本项目跨tier容量预留
  的实现，不能直接照搬、移除全局容量检查或宣称目录替换对无锁读者原子。
