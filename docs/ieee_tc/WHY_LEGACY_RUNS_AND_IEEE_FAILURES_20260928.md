# 为什么旧版能运行，而当前 IEEE Full 频繁失败

2026-09-28；回答用户的新问题。依据本地历史结果、实现差异、测试和 D92–D98
原始运行，不把审稿意见、代码断言或测试通过本身视为正确性的证明。

## 直接结论与责任

旧版本确实完成过实验，不能因为新版本失败就否认旧运行。当前运行的不是
旧服务仅调几个参数后的版本：IEEE 路由/驻留/准入、原生 GPU/HOST 所有权、
新后端、外置到达和生命周期计量已逐步接入，服务控制路径发生了实质重构。
原来的成功不自动继承到新路径，但新路径反复崩溃也不是合理常态。

已经发现并证实的主要问题在本轮实现与集成验证：状态版本粒度过粗、资源
退出状态不完整、以及将可以明确拒绝的过期准备计划提升为整轮致命错误。
这是 Codex 实现与验证的责任，不能归咎于用户要求优化、3090 硬件或“模型
输出有随机性”。必要的安全检查应保留；如何在拒绝旧操作后继续提供服务，
也必须成为正确性的一部分。

## 1. “之前跑通”有两种不同证据

| 证据 | 实际证明 | 不能自动证明 |
|---|---|---|
| 旧论文 7B/3B 回放 | 旧执行与生成合同下运行完成，并产生历史测量 | 新 IEEE 实现、固定输出及原生引用合同已合格 |
| D90 两模型各 100 请求成功 | 新路径有限联动、原生 token、远程内容和释放通过 | 4,000 请求、多个轮换及主入口并发下持续正确 |

P0 审计确认旧 7B 主表/消融都执行 4,000 请求，但属于独立运行；输出总量为
407,351/405,927 token，不等于本轮固定输出合同。P1 初始审计发现旧路径在
路由排序、热度/收益、EWMA、可行集、KV/headroom 和物理引用上与 IEEE
规定存在具体差异。这说明需要对齐，不说明旧结果全部无效或必须推翻项目。

D90 还有已经记录的资格边界：3B 四副本时诊断入口总准入上限是 8，主入口
是 32；7B 分别为 2 和 8。短前缀不能覆盖当前完整回放的并发交互。此次
没有为了通过而降低主入口并发或修改回放时刻。

## 2. 最近失败不是一个笼统的“系统不稳定”

| 已观测问题 | 已有证据 | 机制含义 |
|---|---|---|
| 文件来源刷新与规划快照不一致 | D92 原始拒绝；D93 CPU 反例重现刷新推进 epoch 的同类条件，原 D92 具体谓词未保留 | 快照内部要自洽，不能只增加外层重试 |
| 副本退出但仍持有物理 GPU | D93 物理上下文拒绝；D94 实际 selector 反例 | “不接新请求”不等于“GPU 已释放” |
| 请求引用变化导致无关来源失效 | D96/D98 同副本 32 次 acquire 对照：旧全局 epoch 仅 1 次接受，副本身份校验接受 32 次，无额外加载 | 引用计数变化与工件副本身份变化不能混用一个失效条件 |
| 隔离副本不退出、不能补充服务容量 | D96 零可用副本时 1,207 次扩容决策均无空闲设备；D97 CPU 反例证明隔离 owner 被跳过 | 既要安全保留所有权，又要有明确、可完成的退出路径 |
| 正常过期拒绝变成整轮中断 | D98 计划第二个 HOST fallback 回执 `held=false, reason=stale_snapshot`，随后 ValueError 导致 504 个任务取消 | 过期计划与无法确认所有权的故障没有被正确区分 |

D98 的 `stale_snapshot` 只证明版本检查拒绝，不能进一步声称权重文件实际
改变或 owner 消失。第一个已持有引用随后成功释放，计划成功关闭；本轮
没有清理错误或 OOM。下一个因果测试必须保留这些边界，不能把检查删掉。

## 3. 为什么一千多项测试通过仍然会失败

主要不是测试数量，而是测试问题不完整。有一条很直接的证据：
`tests/test_ieee_tc_transfer_pressure.py` 中
`AutomaticFileReplacement.test_lost_native_source_stops_before_file_io_and_returns_earlier_holds`
明确将 `ValueError('fallback changed')` 当作预期通过结果。

它验证了“不使用失效来源、不进行错误文件 I/O、归还先前持有”，这些是
必要条件；但没有验证上层服务能否把这个已确认的拒绝记为计划失效、继续
服务并基于新状态规划。当前 `_reap_ieee_residency_tasks` 将该异常上抛，
于是局部测试通过，整轮仍崩溃。这是测试合同和集成合同之间的具体缺口。

此外，有限并发、短前缀和替身后端无法覆盖真实多进程延迟、热点轮换、多个
计划与请求交错、取消后的资源回收等全部顺序。已有测试是证据的一部分，
不能替代完整真实回放；今后不能用增加局部测试数量掩盖尚未通过的全流程。

## 4. 当前慢在哪里，哪些解释没有证据

D98 仅 623 个成功请求的条件均值：

| 时间段 | 平均值 |
|---|---:|
| 用户 TTFT | 140.686841 s |
| dispatch/admission 等待 | 125.239548 s |
| service TTFT | 15.447293 s |
| 其中原生 vLLM TTFT | 0.329858 s |

前两阶段之和严格构成用户 TTFT；原生 vLLM TTFT 是 service 的子阶段，不能
再加一次。当前大量等待位于控制和准备路径，不应直接声称“3090 算不动”。
这不能证明后端完全无优化空间，也不能用截断成功子集与旧整轮做速度排名。

1,323 个资源样本未见 high/max/OOM/swap；51 次远端交付全部 UUID/字节/内容
匹配，请求路径打包为零；623 个成功请求全部符合原生生成数量合同。因此
现有证据不支持把此次中断解释为内存不足、远端打包或概率输出长度不一致。
固定长度会改变相对旧协议的工作量，但不是本次 ValueError 的原因。

## 5. 对实施方式的反思及下一步边界

从初始审计 commit `040296e6` 到 D98 源码 `f761662`，相关目录累计变更
46 个文件，新增 36,983 行（含 18,129 行测试；faaslora/ 新增 9,200 行，
scripts/ 新增 9,654 行，后者也含计量/安全/实验工具，不全是在线路径）。
行数不是质量指标，但足以说明不能再称“只做小幅参数优化”。在获得稳定
完整回放前累计接入的改动过多，增加了故障归因与交互验证的难度。

当前不另起框架、不删除安全检查、不通过延长超时或删请求获得成功，也不
用旧近似算法冒充 IEEE Full。先对上述有证据的错误类别完成状态契约：

- **合法状态改变：**旧操作明确拒绝，归还真实持有，旧计划结束为失效；由
  现有控制流程基于新观测产生新计划，不偷偷重跑旧计划。
- **未确认所有权/真实错误：**保留隔离、实际回收和可追溯失败，不能一律
  `except: pass`，也不能伪造 release。
- 同一个测试既验证安全拒绝，也验证后续请求可继续服务及资源守恒；再回到
  完整 4,000 请求，而不是把短前缀当完整验收。

这不是为审稿人增加人为限制：来源真实性和资源安全要保留，但“正常并发
变化不得杀死服务”同样是系统正确性。性能收益最终仍按冻结 G1/G2 评价，
不因不报错就宣称 PrimeLoRA 最优。本轮解释没有修改生产代码或 IEEE 公式。
