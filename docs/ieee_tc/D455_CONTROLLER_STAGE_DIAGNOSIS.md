# D455：7B 同合同请求分解——资源差距后的控制路径定位

2026-10-12。只复用 D371/D453 各 4,000 条请求及规划回执；没有新 GPU
实验、服务修改、基线调参或图形。D454 的六系统结果及冻结 V1/单轮 V2
保持不变。一次性远端只读交付缓存继续复用 D78/D80，不重新发布或打包。

## 1. 当前结论与证据边界

D454 已确认 PrimeLoRA 的联合 SLO 为 97.70%，但 GPU-s/request 高于
可行的 ElasticLocality 46.3958%。额外持卡主要发生于业务窗口，控制器
较多次因已完成请求的 TTFT 未降到既定下界而不能缩容。D455 进一步发现：
PrimeLoRA 的平均全局许可等待很低，入口和完成接收延迟却随业务推进增长。
因此下一步优先检查控制器同步路径，而不是放宽缩容阈值或增加 GPU 容量。

这是定位，不是已证明规划器导致全部差距，也不是完整系统的因果消融。
ElasticLocality 同时关闭多项主动管理，缓存状态、路由和生命周期会改变；
不能把全部差值归给某一个机制。完成后接收延迟不直接计入同请求原生 TTFT，
但可能延后完成反馈及后续控制决策，须进一步验证。

## 4. 规划和本机消息路径的进一步核查

PrimeLoRA 保留 2,859 次完整规划 CPU 回执，均 completed：2,849 次
owned_execution_epoch、10 次 initialized_gpu_objective。
ElasticLocality 主动规划为零，与其门控一致。

| 规划调用包络 | 均值 ms | Type-1 P95 ms |
|---|---:|---:|
| 主线程冻结序列化 |10.038|13.525|
| 规划 owner 等待 |173.295|791.579|
| 提交→worker 开始 |13.988|18.941|
| worker 执行 |220.858|510.454|
| worker 完成→主线程接收 |146.898|839.024|

worker CPU 合计 631.339 s；冻结序列化合计 28.700 s。调用和请求可并行，
这些值不能相加成为服务 E2E，也不能把 worker 的 220.858 ms 全称为主线程
阻塞。规划计算已经运行在受服务资源限制的单独 CPU 进程，不重复实现迁移。

生成 RPC 的平均 channel-acquire 为 0.026 vs 0.055 ms；平均响应接收延迟
为 254.727 vs 3.251 ms，P95 为 1272.624 vs 1.825 ms。响应平均大小约
1,781 vs 1,782 bytes，worker RPC queue 均值为 1.599 vs 1.636 ms。
这些不支持“生成连接池被长期占满”或“响应正文很大”作为直接解释。
RPC pickup 使用同机 wall-clock 和生产端非负截断，原始 parent read 时间
未单独保留；以第 2 节单调时钟分解为主，不能将该辅助字段当纯 CPU 测量。
native async transport 的 thread-resume=0 是结构值，不是无调度延迟的证明。

## 5. 历史、代码与外部原始依据

- D93/D153 已合并同次文件库存扫描；D188/D189 已编译静态工件描述。
  D193/D194 已缩小规划快照，D202 已移除无消费者的 tensor 描述；不重复。
- D128/D130/D159 已把纯选择、校验和目标构造放进 CPU owner，保留冻结
  输入和执行时物理重检。D329 的反例否定“只凭 owner epoch 缓存整个
  tensor 物理状态”，本轮也不添加 TTL 或跳过确认。
- D330/D331 已把新规划观测供 router 复用；D355 已在 native core 中做
  完整控制操作后的协作交错；不能将已有功能包装为新候选。
- 当前 `_plan_ieee_preparation_for_slot` 仍在 controller 上同步获取
  `LocalSourceReferences.preparation_snapshot`，包含实时文件遍历和校验；
  请求解析、消息解码和其他同步工作也共享事件循环，实际份额尚未测出。
- `_current_coord_metrics` 虽复制完整历史，但现有调用点在结果收尾，
  不在每次 live progress；因此不能仅凭大对象就认定它解释业务期增长。
- [Python 3.12 asyncio 官方文档](https://docs.python.org/3.12/library/asyncio-dev.html#running-blocking-code)
  说明同步计算会阻塞同一事件循环的其他任务；这是诊断原理，不证明本机原因。
- [Llumnix 的观测路径设计](https://docs.llumnix.ai/design/scheduler/instant_accurate_load)
  区分引擎状态与调度器接收状态的时间差。这里只借鉴区分观测延迟的原则，
  不改 IEEE 的队列、EWMA、需求窗口或路由公式。
