## 问题与可证伪判断

D182 的平均 TTFT 为 2.730194 秒，其中进入引擎前 2.389572 秒。
GPU-selected 的 1300 个请求平均 arrival→admission 仍为 1.777912 秒，
所以不能把整个缺口归因于远程传输。该条件分组不构成跨系统因果对照。

本次先检验：已经记录的 routing 计时是否解释 gate→source admission
的大部分等待。若不是，就不能因 RPC 数增长而继续只优化初次 source
observation；应定位选中后的待准入登记、源保护和控制事件处理。
`routing_decision_us` 不覆盖返回 None 后直接重试的观察，也不是 CPU
独占时间；差额必须保留为混合残余，不冒称单独的 admission RPC 耗时。

## 结果：全部请求的非重叠分解

单位毫秒；均值可按下列层次相加，P95 不能相加。完整逐请求表、各层
条件分组和所有 RPC 字段另存 `20261003_d183_control_path/`。

| 阶段 | 均值 | Type-1 P95 |
|---|---:|---:|
| 计划到达→服务端接收 | 326.534 | 1650.898 |
| 接收→全局 gate | 299.478 | 2142.456 |
| gate→源准入：已记录 routing | 582.821 | 1983.562 |
| gate→源准入：其余残余 | 526.435 | 2091.770 |
| 源准入→generation handoff | 583.696 | 2442.769 |
| generation handoff→native dispatch | 70.607 | 391.465 |

前四项合计为1735.268 ms；六项合计为2389.572 ms，与 D182 既有
引擎前分解一致。所有请求的分解校验都在1 ms门槛内，没有裁掉负值、
缺失填零、原始结果重写或重新定义时间边界。

进一步拆解第一项：计划到达→回放任务创建均值1.861 ms，创建→提交
0.683 ms，提交→服务端接收323.989 ms。源码证实这是同机 Unix socket
请求入口，不是174节点的 LoRA HTTP 下载；不过该段包含发送、背压、
接收与调度等待，不能仅凭平均值全算作控制器CPU或回放器性能问题。
这些子段不能与上表第一项再次相加。

## GPU-selected 的条件诊断与解释

| 观察 | 1300个 GPU-selected 请求均值，ms |
|---|---:|
| gate→源准入总计 | 1254.938 |
| 其中已记录 routing | 587.842 |
| 其中其余残余 | 667.096 |
| 源准入→generation handoff | 1.267 |
| generation handoff→native dispatch | 96.305 |

观察支持：GPU 已就绪并不意味着控制路径即时完成。主要缺口在本次
源准入之前，不能仅从0.583秒的 routing 计时推断初次状态查询是唯一
瓶颈。这里的源准入包含成功保护的完成点，GPU 引用获取已经发生在
该点之前；不能把1.267 ms当作GPU获取耗时为零。

完整 generation RPC 的平均响应领取等待为437.978 ms，channel取得
0.014 ms、send flush0.113 ms、回复约1774 bytes。前者采用旧 producer
的同机 wall-clock/clamped计时，保持其诊断限制，不与monotonic分解
混加，也不以它证明所有 source RPC 都有相同等待。原 `gpu_admission_decision_us`
和 `adapter_path_resolution_us` 全零属于该路径的结构性未计量，不解释为
机制没有成本。保留这两个字段，不能用它们关闭审稿人的控制开销质疑。

## 决定与下一步

本轮不接受新的服务优化，仅收窄定位范围。两个近似同量级的阶段提示：
不能继续只减少初次状态查询，也不能未经测量删除pending或源保护检查。
下一项候选研究应检查**选中副本后，pending登记与源保护能否在同一
前端所有权事务中连续完成**，减少控制器中间往返而保持登记先于准备、
新鲜owner/epoch校验、精确引用、取消/失联清理及冲突重新路由。
这不是已确认的根因或已接受实现；先审查依赖/失败路径并做有界测试，
若改变语义或无法减少实际等待则拒绝，不能为了顺利运行旁路检查。

其他仍未归因的控制处理保留开放，不同时叠加缓存、并发或参数改动。
