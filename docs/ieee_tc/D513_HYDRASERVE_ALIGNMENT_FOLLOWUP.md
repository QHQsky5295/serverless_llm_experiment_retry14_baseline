# HydraServe 的 5/2 倍率能否作为 PrimeLoRA 主评价依据？

2026-10-14，D513 用户追问补充。不是新协议或新性能实验。
使用 research-lookup 核查官方全文、analyze-results 区分观测与推论；
Parallel CLI 0.7.1 未认证，采用可用网页工具，不安装依赖或上传项目数据。
本文不改冻结 V1、单轮 V2、D394 数值、运行配置、论文或历史结果。

## 1. 明确结论

**可以对齐其评价思路与 5/2 标定倍率；事实上现有协议已经这样做了。**
主评价应是“TTFT / TPOT 服务要求、达成率、生命周期资源消耗”的组合，
不是 CE 第一，也不是只按原始 TTFT 排序。

但 warm TTFT×5 和 warm TPOT×2 是两个**单请求时延门槛**，不是一个
综合排名分数。它们既不规定总体需要达到 95%，也不规定 GPU 预算为 75%。
用 5/2 代替 95%/75% 是混淆不同层次，不能解决原来的依据问题。
保留已冻结 G1/G2 的计算与选择规则，同时完整展示连续指标和预定敏感性；
不把单个 95%/75% 工作点写成普遍最优。

## 2. 对齐什么，不照搬什么

| 层次 | HydraServe 原文 | PrimeLoRA 当前协议与决定 |
|---|---|---|
| 延迟门槛 | §8.3 以 warm 请求标定 TTFT×5、TPOT×2 | 已采用同倍率；所有系统共用一次冻结标定 |
| warm 条件 | 1024 输入 token、batch 8，并有应用特定调整 | batch 8；复用现有变长输入，按原生输入长度分组，不造新 1024-token 负载 |
| 服务结果 | Fig.9/10 主报 TTFT 达成率，TPOT 达成另报 | 并列 TTFT、TPOT、联合达成率及原始时延；不以边际的平均或乘积代替交集 |
| 达成要求 | 文中“多数场景 TPOT 超过 95%”是观测结果 | 联合至少 95% 是本项目约束，不能从那句话推出；90/95/99% 均保留 |
| 资源 | §8.3/Fig.13 的成本与 GPU memory-time 成比例 | 主报实际整卡生命周期 GPU-s；不把半显存虚构成释放半张卡 |
| 预算 | 不是本项目的共同 Resident 参考 75% 规则 | 75% 是节省 25% GPU 时间的研究场景；并列 50/75/100% 预算与资源—质量关系 |

原文还对 summarization 的 TTFT 和 chatbot 的 TPOT 作应用调整，所以
不能声称其所有应用无例外地用 5/2。我们的任务未对应地分类并验证应用 SLA，
不借用这些例外事后放宽部分请求。
出处：[HydraServe，NSDI 2026，§8.3/Fig.9–13](https://www.usenix.org/system/files/nsdi26-lou.pdf)。

方法合理性：首次响应包括排队、准备和 prefill，后续生成则需持续供给 token；
区分两种服务要求能暴露“改善启动却损害生成”的取舍。这是与本系统机制的
对应分析，不是由 5/2 数学推导出的最优 SLA，也不是用户体验验证。
共同 batch-8 warm 参考是一个明确服务条件，不称单请求绝对最快速度。
长度分组避免所有长短请求都套同一个绝对标尺；此扩展必须披露，不能称为
完整复现 HydraServe 的评价设置。固定 prompt/target、全部完成和原生计量不变。

## 3. 三层规则与精确公式

对模型 μ、输入组 κ，共同标定为 T_warm、P_warm：

\[
\theta^T_r=5T^{warm}_{\mu,\kappa(r)},\qquad
\theta^P_r=2P^{warm}_{\mu,\kappa(r)}.
\]

多 token 请求令
\(x_r=TTFT_r/\theta^T_r\)、\(y_r=TPOT_r/\theta^P_r\)。
正确完成后同时满足 x≤1、y≤1 才联合达标。失败先计零；单 token 只检查
TTFT，TPOT 为 N/A。归一化只是解释已有规则，不是新增在线公式或加权分数。

\[
A_T={1\over N}\sum_r z_r\mathbf1[x_r\le1],\quad
A_{joint}={1\over N}\sum_r I_r,\quad
U=\sum_d\int\mathbf1\{\text{服务持有物理 GPU }d\}\,dt.
\]

TPOT 达成按正确完成且至少两个输出 token 的条件集合计算，公开分母。
95% 联合达成要求 N=4000 中至少 3800 同时满足；并不允许 200 个失败。
TTFT 和 TPOT 分别达到 95% 只能保证其交集至少 90%，不能冒称联合 95%。

| 问题 | 冻结判据 | 主排序量 |
|---|---|---|
| G1：达标服务花多少资源？ | 全部正确，A_joint≥0.95 | R=U/N_correct，越小越好 |
| G2：预算内能提供怎样的扩容/churn 服务？ | 全部正确，A_joint≥0.95，U≤0.75U_ref | W1/W2 P95 TTFT，越小越好；另报联合达成差值 |
| 主展示：有哪些真实取舍？ | 所有已测点，包括不达标点 | A_T、A_P、A_joint、TTFT/TPOT 尾部、U/R 并列，不合成唯一分数 |

G1 的“同质量要求”不等于两系统实际达成率相等；G2 的“同预算上限”
不等于实际消费相同。只有一个点满足预算时，不能宣布对所有对手同预算更快。
没有配置搜索，不把已测点称为该 baseline 的全局能力边界。

以满足 TTFT/TPOT 要求的有效服务能力为目标，有
[DistServe，OSDI 2024，§2/6](https://www.usenix.org/system/files/osdi24-zhong-yinmin.pdf)
的直接先例；它重点用 90%，另报 99% 和 SLO 倍率变化，不提供统一 95% 规范。
固定 trace 的 N_good/U 可作效率补充，但不同于扫描请求率获得的最大 per-GPU
goodput，不把两者混称同一测量。

因此：5/2 有直接引用；95% 是已冻结 5% 时延违约预算；75% 是已冻结
25% 节省场景。后两者没有本次找到的统一规范或唯一最优证明。保留原始数值、
预定多档要求和预算切片，比把它们包装成行业标准更能回应两轮审稿。

## 5. 现有数据已经如何回答这套指标

以下复用 D513 的 7B W0 六行主比较及 D510 HydraServe 已封存评价；
不是新回放、新配置、独立留出或重复均值。六个运行原生输入/adapter 绑定与
token 计量均为 4000；独立数值正确性仍未闭环，原始 N_correct=null 不填造。
故此处资源列准确写作 GPU-s/原生合同请求，而不是已证明的每正确请求成本。
正式 G1/G2 的全部正确性要求不因此降低。

|---|---:|---:|---:|---:|---:|
| PrimeLoRA | 98.000 | 99.200 | 97.425 | 2.694612 | 2.315363 |
| ServerlessLLM | 98.225 | 99.900 | 98.125 | 4.022441 | 1.052246 |
| vLLM | 99.475 | 100.000 | 99.475 | 4.028844 | 1.200507 |
| S-LoRA | 94.575 | 99.850 | 94.425 | 3.789269 | 17.699067 |
| Loquetier | 5.500 | 74.900 | 4.350 | 4.249596 | 555.110032 |
| HydraServe | 89.775 | 74.675 | 68.725 | 2.415538 | 8.851575 |

此处所有 TPOT 样本数都是 4000；不是将单 token 或失败请求补零。
原计数、分母、表格重算和来源 SHA 保存到同目录发布的 follow-up 回执。

1. **观测：**PrimeLoRA 满足既定 95% 时延要求，相比同样达标的
   ServerlessLLM/vLLM，物理 GPU 时间分别少 33.0105%/33.1170%；
   但联合达成低 0.700/2.050 个百分点，P95 TTFT 也更高。
   **含义：**支持当前工作点的资源—质量取舍，不支持全部指标第一。
2. **观测：**HydraServe 资源更低但联合只有 68.725%；S-LoRA、Loquetier
   也未到 95%。**含义：**全部保留，不以低资源宣称其达标效率最优；
   HydraServe 全部 pp1，不能用这些结果否定未触发的 pipeline/consolidation。
   Loquetier 异常长等待仍须依实际适配证据判断，不先归为论文机制缺陷。
3. **观测：**99% 要求下当前只有 vLLM 通过，PrimeLoRA 不通过。
   **含义：**不能说 5/2 天然保证 PrimeLoRA 获胜；需要改善系统，而不是换尺子。

95%/75% 的旧离线敏感性已完成，不重复；SLO 倍率曲线仍未完成，留在既定
S13/离线分析。当前 W0 数值不代替 W1/W2 的共同参考、预算内比较或 3B 结果。

## 6. 可用于论文的表述（需随最终结果更新完成时态）

> 我们以服务要求约束下的资源效率评价弹性 Multi-LoRA 服务，而不是将
> 平均延迟与价格合成唯一分数。参考 HydraServe 的 warm 请求标定方法，
> TTFT 和 TPOT 门槛分别取共同 warm 参考的五倍与两倍。针对既有变长输入，
> 我们按输入长度分组，所有系统共享冻结参考。除两项边际达成率外，
> 我们报告同一请求同时满足两项要求的比例，以及实际生命周期 GPU 时间。
> 这允许区分常驻资源换来的低延迟和减少资源后的服务质量。

> 主参考要求所有请求正确完成且至少 95% 满足联合时延约束，再比较
> GPU-s/request；扩容与 adapter churn 另在共同资源预算内比较尾延迟。
> 95% 和参考资源的 75% 分别是本研究的服务档位与节省目标，不是通用 SLA。
> 我们同时检查预定的 90/95/99% 服务档位、50/75/100% 预算及 SLO 倍率，
> 并展示不达标点和原始资源—质量取舍，避免结论只依赖一个阈值。

发表前必须确认全部数值正确性、SLO 倍率、W1/W2 与 3B 等承诺确实完成。
未完成不可使用上述完成式作为实验事实。CE/美元价格仅为补充分析。
