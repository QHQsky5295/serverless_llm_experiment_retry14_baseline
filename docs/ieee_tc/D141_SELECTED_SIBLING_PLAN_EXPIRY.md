# D141：合法请求改变另一准备目标的来源时，结束旧计划

2026-10-01。Prime IEEE Full 正确性检查；不是性能实验或正式消融。
状态：同一 CPU 反例修正前失败、修正后通过；1,071 项相关回归通过。

## 问题与历史证据

D140 的单次 7B 诊断在准备来源检查处抛出 ValueError，随后回放中断。
只有 90 条原生生成契约成功，不能当作完整性能结果。失败瞬间的完整来源
快照没有保存，因此本次反例证明的是一条真实实现缺陷，不能补造历史现场，
也不能声称它唯一解释了 D140。

D109 已处理非目标对象的合法来源变化；D134 已处理旧对象退役后，新计划
有意选择另一来源。此次不同：同一计划选中 a/c，a 尚未由该计划加载时，
合法 demand 从已确认的另一文件副本加载 a；c 尚未提交准备操作。计划注册
不等于已经持有所有目标的文件或 native 对象。旧检查却因 a 也是所选目标，
将这次合法变化当成身份损坏。

[vLLM 0.30.0 官方 worker manager](https://raw.githubusercontent.com/vllm-project/vllm/v0.30.0/vllm/lora/worker_manager.py)
按整数 ID 查找、缺失时加载，并在单线程 core loop 中执行。结合本地多次 RPC
流程可推断：单次操作串行不使整个准备计划原子。这是操作边界依据，不是本次
性能证据，也不证明文件内容相同；内容仍由实际发布记录及冻结 SHA 验证。

## 唯一行为修正与不变项

将“已选中”与“已持有来源”分开：完整、较新的来源观测中，另一所选目标的
物理路径变化也可以构成**旧计划未执行并失效**的证据。v2 检查同时要求传入
目标集合与冻结 GPU 候选集合完全一致，防止用错误目标集合解释冲突。

controller 仍验证逻辑 ID、名称、rank、内容 SHA、owner/clock/epoch，以及
旧/新两份当前文件发布。native 提交点先返回未执行回执，再由 controller
验证；不得先按旧收益定价、驱逐或加载。并发任务沿用既有取消、等待和计划
关闭流程；后续只能由正常控制周期产生新计划，不重试这个失效目标。

没有修改九个公式、预算/admission、需求与准备 profile、容量、并发上限、
生成、超时、工件、负载或远端配置。没有增加 catch-all、sleep、TTL、盲目重试
或兜底加载。实际身份/内容损坏仍失败。residency manager 仅同步修改说明注释。

## 检查与解释

复用 AutomaticGPUReplacement / MixedOwnedPreparation：实际文件管理器发布
同内容 HOST/NVMe，实际 owner 执行 demand，实际 selector/混合执行器选择并
注册多目标计划。native 缓存/模型使用原有 CPU fixture，不执行 CUDA、不新建
论文权重池或工作负载。一个准备任务刻意停在事件边界，检查其在旧计划结束时
能被收回，而不是遗留后台任务。
