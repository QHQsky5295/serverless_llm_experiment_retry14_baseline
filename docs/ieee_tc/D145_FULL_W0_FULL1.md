## 4. 四个失败：已知事实与证据边界

req_03842、req_03843、req_03844、req_03996 的首行一致：

```text
RuntimeError: subprocess_native_rpc_failed_no_retry: TimeoutError:
```

失败分类器记录外层 `RuntimeError`，所以 `timeout=0, returned_error=4`
不等于“没有底层超时”。这不是“new generation withheld”错误；现有日志
也不能证明触发的是外层 1800 s 保护。四条为 `controller_task_exception_v1`，
generation submission 未记录、source admission 缺失、instance_id 为空。
失败默认的零阶段值和空 native timing 对象都不是测得的零耗时，也不证明未 dispatch。

当前 `_rpc` 对原生路径的本地异常只保留类型/文本并附 worker 日志尾部，
没有保留发生异常的 command、operation、connect/send/recv 阶段。
源码中存在 30 s connect 和 300 s send/recv 保护，不能仅凭相同 TimeoutError
文本判断哪一道触发。附带 worker 日志主要是启动/JIT 信息，没有对应失败栈。
请求执行前的选源/保护，以及请求结束的归属释放都可能向外层传播异常；
`controller_task_exception_v1` 不单独定位至 cleanup。

一个可先确认的时间顺序事实：共同到达窗口结束于本机单调时钟
`353241.4238260309`，首次失败终态为 `354366.783730505`，相隔约
18.756 分钟。服务日志在 `done=3731, fail=0` 时已显示 269 个未完成请求。
因此，后期失败不能解释在其之前已经累积的排队；请求错误与服务容量/
控制等待应分别分析。这不是对某个具体 CPU 函数或 GPU 容量的因果归因。
四条异常的外层收集时间晚于各自终态；二者不能交换或当作跨主机时钟。

## 6. 结论和下一问题

1. **完成资格未通过，整体性能改善未得到支持。** 保留完整失败和资源代价，
   不将表中条件延迟作为 M1/M2 达标结果，不宣布相对基线领先。
2. **排队与末尾 RPC 失败是两个相关但不能混同的问题。** 下一步先沿实际
   RPC 操作及资源所有权核查缺失证据；同时利用已有阶段数据定位非推理路径
   的阻塞，不用放大并发或延长超时代替解释。
3. **继续 Prime 优先主线。** 本轮封存和备份后再选择一个可证伪的优化，结合
   既有日志/修改历史和原始文献/官方源码。基线、M1/M2、消融和敏感性尚未恢复。
   3B TPOT 退化、输出 hash 变化、数值身份以及 warm/Resident 标定仍开放。
