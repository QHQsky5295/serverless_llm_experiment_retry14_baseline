## 下一项主线问题：准备是否不必要地占据服务容量

当前源码中 `_ieee_protect_selected_source` 明确在控制器 count reservation
之后执行；`_ieee_prepare_selected_adapter` 对 Remote 调用
`_ensure_local_async`，然后才取得原生可执行引用。`active_requests` 在
reservation 释放时才减少。因此文件准备与控制器服务容量之间确有执行依赖；
这不等于它已被证明是全部违约的根因，也不意味着可直接取消引用/预算检查。

下一项只核查这条具体依赖：**仅对已实际到达的需求，能否让有预算、有所有权
的文件准备与等待推理容量重叠，仍在实际执行前做原有 confirmed routing 和
当前 KV/active-LoRA admission？** 先核对既有 early preparation、movement
coalescing、取消和 pressure 注册路径，避免重复已有机制。D313 中“准备区间
与 admission 分离”主要是计量归属，不能自动证明已取消上述容量依赖。

若已有实现已做到或没有可安全重叠的真实依赖，就排除此方向；若确有缺口，
仅改变这一个调度依赖并复用原队列/预算/传输接口。不得偷看未来 trace、
提前把未发布文件称为 ready、忽略取消后的 IO、重复下载、漏计 GPU/CPU，
或把全部 500 工件预热后称为 cold 运行。冻结评价和初态不变。功能验证
针对改变的执行路径，之后一次完整 W2；不额外重复历史已覆盖的短资格。
本轮尚未实现或测试该候选，也没有预估它能恢复 122 条请求。

本轮重新核查的原始资料：

- [HydraServe §5.1](https://www.usenix.org/system/files/nsdi26-lou.pdf)：
  用实际数据依赖重叠准备与运行时启动，支持检查不必要的串行依赖；不证明
  本项目文件准备的具体收益或引用安全，不移植其多节点流水线性能结论。
- [vLLM 0.30 优化说明](https://docs.vllm.ai/en/v0.30.0/configuration/optimization/)：
  chunked prefill 的预算会影响 TTFT/ITL 取舍，不提供这里的通用最优常数。
- [vLLM 0.30 EngineCore](https://raw.githubusercontent.com/vllm-project/vllm/v0.30.0/vllm/v1/engine/core.py)：
  原生输入处理和模型迭代有明确串行边界；不能将请求包络全部当作 GPU kernel。
