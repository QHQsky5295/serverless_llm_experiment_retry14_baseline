# D720：4,000 请求是否必要——历史前缀与后段变化分析

2026-10-22。回应用户新增问题，只分析，不修改正式工作负载、评价协议、
生产代码或正在执行的 D719；不重新生成数据、重跑历史实验或绘图。
使用 analyze-results 区分原始观测、推断与建议。D719 仍独立按原合同运行。

## 1. 结论与适用范围

**4,000 不是理论必需或行业统一样本数；但本项目现有历史证据不支持把所有
正式主实验直接缩成前 1,000 或 2,000 请求。最有依据的提速方式是区分开发
诊断与完整结论：缩短能在局部回答的问题，保留核心主表的完整生命周期。**

不能承诺一个“看见差异的最早请求数”适用于所有模型、系统和场景。本次
重算覆盖四个已关闭 PrimeLoRA 运行：3B W0/D703、7B W1/D551、7B W2/D554
及其候选 D598。选择范围由已有小型、已核验请求级 CSV 决定，不选胜出片段；
每个源的全部 4,000 条都纳入，并检查所有 500 请求边界。它足以提供早期
判断失真的实际反例，但不是六系统全部排名的最短长度认证。

7B D554/D598 是历史被比较版本，不冒称当前最优版本。3B D703 使用 D714
修正后的真正共同联合 SLO，不使用旧 5,000 ms TTFT 别名。全部数值仍是
单轮固定回放的描述性观测，无 CI；独立数值 adapter 正确性未知仍保持未知。

### 2.1 有的差异早期可见，但不能由此宣布最终排名

- D703 在 500 请求时已显示共同 SLO 不足；1,000 和最终都是 93.60%。
  对发现这一版本存在问题，继续等到 4,000 不是必要条件。但前 100 为 99%，
  不能拿 smoke 推断完整达标。前 1,000 的 P95 TTFT 为 1,562.516 ms，
  最终为 1,784.646 ms，SLO 比例相同也不表示尾部完全稳定。
- D551 的前 1,000/2,000 与最终联合达成相近。这个案例支持短开发回放
  可能有用，但不证明其他场景也如此，不能以此覆盖 W2 的反例。
- D554/D598 前 1,000 的联合达成差为候选高 **0.70 个百分点**，前 2,000
  高 **1.00 个百分点**；到 4,000 变为候选低 **0.50 个百分点**。
  在本次检查的 500 请求网格上，差值从 3,000 的正值变为 3,500 的负值。
  这不是其连续时间轨迹的“精确首次反转点”，也不证明其他运行必在此反转。
- D598 前 2,000 为 95.30%，若据此宣布达标会与最终 89.05%冲突。D554
  的前 1,000 为 96.60%，最终也降至 89.55%。两个版本都有后段退化，不能
  只保留候选最有利阶段。
- D598 最终 P95 TTFT 仍低于 D554（5,644.557 对 5,827.475 ms），但完整
  GPU 时间更高（15,161.688 对 14,641.259 GPU-s，来源 D600）。说明一个
  早期指标或单一尾部指标不能替代约定 G1/G2 的全部条件。

|---|---:|---:|---:|
| 500 | 46 | 86 | 1 |
| 1,000 | 60 | 146 | 2 |
| 2,000 | 83 | 259 | 4 |
| 4,000 | 132 | 497 | 8 |

以上是逻辑 adapter ID，不是独立训练权重数。名义池始终 500，不为缩短
而重新生成或缩池。W2 以 100 请求轮换，1,000/2,000/4,000 分别覆盖
10/20/40 个请求阶段；W0/W1 对应 2/4/8 个阶段，不把阶段数等同自然扩容数。
W2 的后半段仍在引入新的 adapter、替换与驻留竞争，不是简单重复前半段。

原时间轴也非完全均匀：这些 7B trace 的第1,000/2,000/4,000请求到达偏移，
W2 为 1,079.414/1,903.128/3,963.909 秒；W1 为
567.352/1,038.347/2,186.992 秒。它们不是包含启动/drain/收尾的总耗时。
缩到 1,000 确实可能大幅减少开发回放耗时，但不能保证端到端节省恰为75%。

## 3. 为什么不能用长运行前缀补造短运行的资源排名

完整生命周期为：

\[
U_N=U_{pre}+U_{arrival,N}+U_{drain,N}+U_{cleanup,N}.
\]

结束业务的边界变化会影响 drain、资源释放和在线扩缩容。长运行前 N 条
请求完成前还可能到达 N 之后的请求，改变并发和资源状态。因此：

- 长运行前缀的实际时延可以描述，但不等同独立短运行的反事实时延；
- 不能把完整 U 除以4充当 1,000 请求资源，也不能补造提前结束的 release；
- 共同60秒准备不变时，缩短会改变固定成本摊薄，影响弹性/常驻比较；
- 真正改短主协议时，所有系统必须使用相同新输入索引与终止边界，重新取得
  该长度 Resident 的生命周期预算参考，不能照搬 4,000 的75%绝对预算；
- 不能从完整运行前缀同时宣称“节省了实际运行时间”与“已测短协议资源”。

P95 在1,000/2,000/4,000样本中上尾约50/100/200条；P99约10/20/40条。
这是经验分位数的数量直觉，不是独立重复数、置信度或统计充分性的证明。
更多请求仍不能代替多次独立运行；按用户规则，本项目不额外跑 CI。

## 4. 同类原始来源：没有可直接照搬的统一4,000

- [Llumnix，OSDI 2024，§6.1](https://www.usenix.org/system/files/osdi24-sun-biao.pdf)
  对在线服务采用每条10,000请求的合成 trace，并改变速率和变异系数。
  这证明4,000不是该论文的通用设置；不意味着我们必须升至10,000。
- [MLPerf Inference 官方规则](https://raw.githubusercontent.com/mlcommons/inference_policies/master/inference_rules.adoc)
  Server/Interactive 同时考虑600秒运行时长、尾延迟和统计提前停止条件。
  其负载及推断假设与本项目非平稳多LoRA回放不同，不能直接采用它的停止
  算法或把600秒当本项目充分性门槛。可以借鉴“时间与尾部覆盖同时检查”。
- [vLLM 0.30 benchmark 接口](https://docs.vllm.ai/en/v0.30.0/cli/bench/serve/)
  分别提供请求数、速率、burstiness等控制。工具允许指定小请求数，不是
  小请求数能支撑本论文弹性/层级机制结论的证明；提高速率以压缩时间也
  改变排队和争用，不能当作原负载的等价提速。
- 已核查 HydraServe §8.3 的应用/trace生成描述；没有从本次读取的相关段落
  取得足以支持统一最小请求数的明确规定，故不编造“它只跑N条”的论据。

以上为有界来源核查，不声称穷尽所有论文；事实与迁移建议分别陈述。

## 5. 建议：缩短诊断，不在本轮更改正式长度

| 任务 | 建议覆盖 | 边界 |
|---|---|---|
| token/adapter/取消/状态修正的功能 smoke | 现有100请求或定向事件测试 | 不作为500-adapter完整资格或性能结论 |
| 明显等待、重复确认、启动错误的开发筛查 | 既有1,000前缀可优先使用 | 反例可淘汰候选；未发现问题不等于完整通过 |
| 必须观察多次轮换的开发诊断 | 按机制预先说明需要的阶段；2,000可作为候选长度 | 当前仅建议，不新增执行，不伪称八阶段覆盖 |
| 主表、跨场景G1/G2、最终优化验收 | 当前仍保留4,000 | 单键一次、复用已有有效结果、不补CI |
| S1/S2/S3等局部机制微测 | 原计划的事件/样本覆盖，不强制4,000 | 只支持对应机制，不冒充完整生命周期比较 |
| 大规模敏感性中间点 | 可在后续修订时评估缩短 | 先证明覆盖和排名边界；统一合同，关键端点保留全长 |

无需因为一个局部缺陷已修复就无条件启动一次完整性能回放；先问它是否
影响当前主瓶颈、最小验证是否提供新证据。另一方面，也不能因为短前缀
看起来最好就提前宣布优化成功。罕见分支的正确性可以由定向测试证明，
不能要求所有这类分支靠重复完整性能运行偶然出现。

如果用户后续决定减少正式长度，应另建协议身份，固定索引/阶段/时序、
统一系统及参考边界，明确历史4000与新长度分开报告；不按PrimeLoRA胜负
选择截断点。本轮没有批准或实施这个变更，也不为论证能否缩短新增GPU实验。
当前D719按已登记4,000完成，所有尚未完成的主比较/消融/敏感性范围保留。
