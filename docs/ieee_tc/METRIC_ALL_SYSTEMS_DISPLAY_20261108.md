# 全系统统一评价：95% 是服务目标，不是图表准入门槛

日期：2026-11-08。回应最新目标附件
`7503afa5-8c9c-487b-b400-f0e8954e5ff2/goal-objective.md`。

本文件澄清已经批准的 PLAN 2026-11-08 修订，不修改冻结指标、请求阈值、
在线策略、95%/75%主点、工作点选择或当前 D1128 回放。不重新生成输入，
不重算已封存台账，不因此重跑 baseline。不是新协议或独立语义评审通过证明。

## 1. 结论与适用范围

用户指出的展示问题成立：若把“达到95%”误当成进入主图/主表的条件，
确实会排除最需要展示的服务失败及性能差距。正确做法是全部系统共享
连续指标并全部展示，95%只用于解释其中哪一些实测点满足服务目标。

现有 G1/G2 作为两个有约束的研究问题是合理的，但不是覆盖所有点的单一
标量排行榜。必须配合完整资源—服务质量关系，不能仅展示可行子集。

正式比较系统为 PrimeLoRA、vLLM、S-LoRA、ServerlessLLM、HydraServe、
Loquetier；dLoRA 保留既定3B W1/W2的有限覆盖/失败记录。ElasticOnly、
ElasticLocality 等只在消融表出现。不同模型或场景分组，不混成一个平均排名。

## 2. 对所有系统都适用的主表

每一行对应一个真实运行工作点，同一行的资源、时延、达成率不可跨运行拼接。

| 指标 | 含义与适用性 |
|---|---|
| 完成/失败/计划请求数 | 完整保留执行情况，不只报成功子集 |
| 联合TTFT/TPOT达成率 A | 连续的服务质量结果，低于95%仍有意义，不能删除 |
| 生命周期物理GPU-s U、GPU-s/offered-request | 所有完整且资源计量有效的运行均可报告，不预设已达标 |
| P95 TTFT、P95 TPOT | 报原始服务表现及有效样本数；失败不能以删除后低时延掩盖 |
| U/B、是否满足95% | 附加解释列，不代替上述连续结果，也不作为删行规则 |

公式沿用冻结 V1：`A=sum I_r/N_plan`，其中失败为0，单token请求不补造
TPOT；`U=sum_d integral a_d(t)dt`，a_d 表示物理持卡而非利用率；
`R_offered=U/N_plan`。相同完整4000请求场景下 U 和 R_offered 排序一致。

`R_correct=U/N_correct`只在正确性证据满足协议且分母已知时报告。
现有 `n_correct=null` 保留未知；不能把原生输出数量/合同成功直接写成
独立数值正确性已证明。当前台账的联合值和时延是合同及时序观测，正式
正确性资格另列。此限制对所有系统相同，不因此补造缺失值。

未完整执行或未通过资格的系统仍保留一行，列状态、已观察完成/失败、
`U_obs`及可用的条件指标，明确截断；不把不完整资源除以计划请求数后
当成完整服务的低成本优点。未执行不是0，未知不是无穷大。

## 3. 一个图/表中怎样同时展示全部系统

主表采用上面的统一列，各系统一行；若同系统有 resource_opt 与
budget_latency_opt，用明确子行区分，两种工作点不拼接。

主图建议用资源—质量散点：横轴 GPU-s/offered-request（越左越好），
纵轴联合SLO达成率（越上越好），画95%参考线，保留线下所有实测点。
同一图组另列P95 TTFT，或用精确主表承载尾延迟，避免用气泡面积混淆
三个数量。失败/未执行用状态栏或单独符号，不伪造坐标。全部系统必须
可辨认，不能裁掉低达成率或高延迟点；需要log轴时明确标注。

存在多个实际资源工作点时才画各系统的已测边界；仅有一个点就画一个点。
离线改变95%判定不会改变实际GPU占用，也不能从单点制造资源曲线。
最终制图仍遵守既有IEEE单栏、Times New Roman和完整来源规则；本轮
只补解释和数据示例，不为展示中断正在进行的消融实验。

## 4. baseline 达不到95%时怎样判断

1. 主图/主表照常比较其 A、U、尾延迟，报告达成率差值（百分点）。
2. G1的“满足共同95%要求所需资源”列写“已测配置中未观测到可行点”，
   不能写无限资源、100%节省或该系统永远不可能满足要求。
3. G2下，若双方实际点都在共同预算内，可以直接比较其 A 和尾延迟，
   即使某一方低于95%；但只有满足协议的点才支持“达标预算服务”结论。
   一个超预算四卡点不证明该baseline在预算内的全部配置都不可行。
4. PrimeLoRA若同时更省资源、联合达成更高、P95 TTFT更低，可写这些
   明确轴上的已测点优势；不能写双方“实际服务质量相同”或所有指标领先。
5. 如果只省资源而尾延迟更高/达成率更低，保留取舍，不能仅凭超过95%
   升级为系统全面最优。既有主次指标和有界闭口规范仍生效。
6. 完成合理适配、计量和机制解释后，不为了让baseline过95%无限优化。
   仅推进计划内有限的共同预算/资源规模点；有具体复现缺陷才修正重跑。

95%是冻结的本项目主要求，不是行业统一常数。完整保留90/95/99%要求、
预算及请求级阈值敏感性；不能根据哪一条线让PrimeLoRA胜出而换主标准。

补充可报告 `N_good/U`（good requests/GPU-s），所有有有效计量且U>0
的完整点均有定义。但它允许资源与违约比例互相补偿，不能取代达成率、
尾延迟及G1/G2，也不重新引入另一个“只看一个分数”的CE问题。

## 6. 原始论文依据与差异

- DistServe §6.1 以SLO达成率为主要指标，在指定目标下比较每GPU服务能力，
  同时变化负载/延迟要求展示曲线，并补充99%目标。这支持“完整达成率曲线
  加目标线”的组织方式；其最大到达率/GPU不等同于本项目N_good/U。
  [原文](https://arxiv.org/html/2401.09670v3)
- HydraServe §8.3 在严格SLO情形中明确报告所有系统的TTFT达成率不超过63%，
  仍展示其比较。未达到某目标并不使达成率指标失效。其TTFT边际达成率
  不能冒充本项目TTFT/TPOT联合达成率。
  [原文](https://www.usenix.org/system/files/nsdi26-lou.pdf)
- ServerlessLLM Fig.12通过改变每节点GPU数量展示延迟与资源关系。这支持
  用实际资源工作点比较效率，而不是假设所有系统已有一个相同质量点。
  [原文](https://www.usenix.org/system/files/osdi24-fu.pdf)

因此保留G1/G2，并用统一的资源—达成率—尾延迟主表/图覆盖全部系统，
无需回到CE第一，也无需强求所有baseline达到95%。结论边界依据完整数据，
不是靠调整阈值或削弱对照来保证预设排序。
