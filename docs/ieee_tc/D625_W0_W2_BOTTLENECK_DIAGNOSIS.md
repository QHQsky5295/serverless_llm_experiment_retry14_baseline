# D625：复用完整 W0/W2 证据定位残余瓶颈

本轮为离线诊断，不新增性能运行，不改生产实现、九公式、模型参数或指标。
D624补齐同版本W0后，W0/W1/W2联合达成分别95.25/97.275/94.95%；
当前工作点尚未跨场景达标，独立数值正确性仍未知。

问题限定为：W0第501–1500条为何集中148/190条联合违约？其主导墙钟阶段
是否与已完成D623的W2诊断一致？首先区分准备/派发、全局准入、runtime slot、
原生队列与推理阶段，不预设网络、启动或某个控制阈值就是原因。

复用D612的流式请求阶段和物理积分审计器，读取D624已关闭、已备份的源结果；
W2复用D623经归档SHA核验的诊断，不重复解析。W0使用真实rotation500，
W2仍为rotation100，不将不同adapter映射的请求伪作单因素配对。
保留取消的activation及未知ready时间，不补零，不从主结果扣除任何等待。

分析限定4GiB内存、0swap、CPU2/3/26/27，无GPU。核对输入/源SHA、冻结
SLO、时间恒等式、实际释放、147项历史保护及已有汇总一致性。只保存小型
请求投影与结果，不复制工件/负载，不画图，不修改非项目k3s或远端服务。

本轮之后依据实际阶段证据，回看历史优化及原始论文/官方实现，只选择一个
可证伪方向做最小验证；没有证据时不凭95%附近的数值任意调阈值或重跑。
7B目标、数值资格、3B、dLoRA限定比较、A1–A5、S1–S13、成本/审稿文档及
最终图表范围不缩减。

各4000请求；下表是已知工作负载上的单轮描述，不是独立重复、配对处理效应
或新性能运行。W0与W2保持原定不同adapter轮换，不能把两列的差归因于单项机制。

### W0集中违约

- 第501–1500条有148次联合违约，占全部190次的77.895%；其中138次的
  最大首token阶段为全局许可申请→恢复执行。
- 这148条的平均TTFT为10479.516ms，其中上述等待7762.188ms，约74.070%；
  runtime slot为704.129ms，准入→引擎入口941.392ms，原生prefill270.049ms。
  这是实际相邻边界的可加和分解，不是删除等待后的反事实延迟。
- 全部190条违约中，141条由全局许可阶段主导；只有18条由准入→引擎入口
  主导。该141条的平均全局等待8181.994ms，平均TTFT10976.780ms。
- 自然扩容trigger→ready区间与请求到达→首token有交集的521条中，160条
  联合违约；无交集3479条中30条违约。这是条件相关，不证明160条由启动
  单独造成。两个最终取消的activation保留未知ready时间，不补零、不删除。

### W2集中违约

- 202条联合违约中，114条由runtime准入→原生引擎入口主导，62条由全局
  许可阶段主导。前114条的平均前者3621.854ms，平均TTFT4657.490ms。
- 这114条中107条在所选副本上的dispatch快照为remote；其他为GPU 1条、
  HOST 2条、NVMe 4条。remote层级本身不等于全部时间花在线路传输。
- 与自然扩容交集的260条中76条违约，无交集3740条中126条违约；不能仅靠
  启动提速就声称解决了全部W2问题。

## 源码语义与下一步的范围

已核对当前 `scripts/run_all_experiments.py`：

1. `run_one`将`_acquire_dispatch_admission`前后时间保留；该阶段包含等待
   许可和恢复调度，不能把全部墙钟时间称为CPU时间或纯permit饱和。
2. 全局许可数与当前runtime容量相连；许可持有覆盖请求处理及finally清理。
   D625没有记录每次许可实际grant的独立时刻，因此不能由现有两端时间
   区分“尚未grant”与“已grant但尚未恢复”，不直接扩大并发。
3. runtime准入之后，remote路径经`_ensure_local_async`、按adapter合并获取、
   真实传输/本地物化、来源pin和native load，然后才进入原生引擎。
   此包络还包含确认及调度，不能将3621.854ms称为纯网络或纯LoRA加载。

下一主线只聚焦一个可证伪问题：**当前W2远程准备包络中，实际传输/物化、
压力状态确认、native load与剩余调度分别占多少，哪个仍在关键路径上？**
优先复用现有D594/D600的严格transfer/barrier分解读取D621已保存回执，不
新增GPU诊断、不重复完整阶段分析。若原回执不足以细分，明确缺失边界，
不凭包络改代码。先确认具体瓶颈再对照历史和原始实现选择一个新候选。

必须保留的历史反证：D595并行压力确认虽减少局部准备等待，D598完整W2
目标反而退化，已由D601撤销；不能再把相同并行化当作未经尝试的新方向。
D606/D610已优化新鲜文件状态构建，D337/D338/D467已审计或实现启动路径；
不重复声称这些为新改进，也不以queue8→4或放宽阈值作兜底。
