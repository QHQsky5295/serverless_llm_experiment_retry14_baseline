# D1171：7B 当前 PrimeLoRA 候选与基线比较、远端冷层瓶颈诊断

日期：2026-11-09。本文是 D1114、D1115、D1100、D1117、D1118 及已封存
基线结果的离线综合分析。没有重新运行性能实验，也没有改变评价阈值、旧结果、
论文源文件或用户修改。

## 1. 当前比较结论

当前 7B PrimeLoRA 有两种已经结束的工作点：四副本上限的 resource-opt 配置，
以及三副本上限的预算配置。它们不能拼接成一个虚构的“最优运行”。

这组结果已经支持一个明确、可写入实验章节的第一层结论：在已测工作点中，
PrimeLoRA 在共同联合服务要求下显著减少生命周期 GPU 占用；低于 95% 的
对手行仍完整保留，不能被解释成“同质量比较”。

但 W2 仍有一个具体而非抽象的缺口：三副本预算点 D1118 的联合达成率为
97.500%，物理 GPU-s 为 9,873.292，P95 TTFT 为 3,053.004 ms；vLLM 的
同一 W2 工作点为 98.225%、16,115.559 GPU-s、1,751.295 ms。因而 PrimeLoRA
满足预算和联合服务要求，却没有在同预算尾延迟上占优。这是下一轮唯一需要先
验证的主线瓶颈；不能用 CE、GPU-s 单独改善来掩盖它。

## 2. D1100 的逐请求证据

D1100 的 4,000 条请求全部完成，固定输出合同匹配，且远端请求期没有打包。
逐请求分类如下：

| 条件 | 请求数 | 占比 | 平均 TTFT (ms) | P95 TTFT (ms) |
|---|---:|---:|---:|---:|
| 全部请求 | 4,000 | 100.00% | 1,046.15 | 2,815.06 |
| GPU-ready | 2,318 | 57.95% | 751.07 | 1,827.91 |
| selected replica mismatch | 1,682 | 42.05% | 1,452.80 | 3,458.59 |
| remote-cold before dispatch | 503 | 12.58% | 2,337.77 | 4,500.82 |
| scale-up affected | 756 | 18.90% | 1,384.77 | 3,304.54 |

503 个 remote-cold 请求中，496 个是该 adapter 在本轮的首次出现，只有 7 个
是首次出现之后再次回到 remote。这说明 W2 的主要尾部不是一个随机的 remote
标志，而是 500-adapter 轮换下的首次物化：请求到达时，约 497 个实际出现的
adapter 尚未拥有本地文件副本。remote-cold 组的平均 LoRA I/O 为 1,432.59 ms，
而 GPU-ready 组为 0 ms；remote-cold 组的服务 TTFT 平均为 1,959.37 ms，远高于
GPU-ready 组的 387.67 ms。这个方向与请求级时间链一致，不能归因于后处理图表或
统计分母。

因此，直接扩大 NVMe 容量并不能自动解决问题：当前 16 GiB NVMe 主要影响已
发生过的复用和驱逐，不能让一个从未出现过的 adapter 在第一请求前凭空变成本地
副本。另一方面，D947 的全量 500-adapter 初始 NVMe 物化将 W2 P95 TTFT 从
2,997.74 ms 降到 2,464.45 ms、把远端请求期获取降为零，但生命周期 GPU-s/
request 从 2.9290 增加到 3.3241（约 13.5%）。按冻结 G1，这个候选不是主结果；
D946 还证明了物化必须在 replay notice 之前完成，不能把部署阶段操作污染请求时钟。

## 3. 只保留一个可证伪的后续候选

下一候选不是再调 SLO、EWMA、scale interval 或人工等待，而是**预算约束下的
需求加权部署期 NVMe 预物化**：

1. 在 replay notice 之前，依据 manifest 的静态需求先验与已观测历史 hotness，
   用论文既有的“需求加权收益/字节”目标选择候选集合，而不是读取未来请求行；
2. 对候选集合执行同一只读 gzip 交付和现有 owner/epoch/content-SHA 校验，使用
   当前文件预算及 staging 倍数自动决定可容纳数量；不改变 adapter 内容、trace、
   生成合同、后端或九个论文公式；
3. replay 期间仍沿用当前 confirmed routing、handoff、hierarchy、admission
   和 autoscaler。未被预物化的 adapter 继续走原始 remote-cold 路径，不能把失败
   请求隐藏或改写成命中；
4. 预物化 wall time、字节和传输次数作为 deployment accounting 单独记录，
   不计入请求 TTFT/E2E；但由预物化改变的 GPU 生命周期和后续驻留必须完整计入
   G1/G2 的物理 GPU-s。

候选的可证伪预测是：在同一 W2 trace、adapter subset 和资源包络下，预物化应
   减少首次 remote-cold 请求的数量及其 P95 TTFT；若节省的远端等待不能抵消
   额外生命周期占用，或联合达成率下降，则该候选立即退出，不再堆叠第二个策略。
   全量预物化 D947 已经作为资源—尾延迟 trade-off 封存，不重复执行。

候选的通过标准不是“PrimeLoRA 必须在所有原始指标上第一”，而是必须形成一个
   可解释的 G2 改善：在不超过 D1118 W2 预算且联合达成率不低于该点的前提下，
   P95 TTFT 相对 D1118 下降；若未达到，则保留负结果并回到已封存 D1118。只有
   该候选通过，才继续其余 7B 消融；否则不把无效优化扩展到 3B。

## 4. 当前实验闭口与未完成项

- **已闭口**：7B W0/W1/W2 四副本 resource-opt 的可行性记录；7B W1/W2
  三副本预算工作点；HydraServe 与 Loquetier 的既有复现观察。它们的低 SLO、
  适配边界和 n_correct 未知均保留。
- **尚未闭口**：W2 同预算尾延迟比较、严格 confirmed-state 因果消融、7B
  ElasticLocality/累积消融、S1–S13、成本敏感性、最终图表和论文整合。
- **不做**：重跑已完成基线、重跑 D1100/D1114/D1115/D1117/D1118、再次执行
  全量 D947、改变 95% 服务要求、删除低 SLO 基线、或把部署压缩/预物化的外力
  混入请求 TTFT。

本文只登记下一候选及其证伪条件，不宣称该候选已经实现或已经优于 vLLM。
