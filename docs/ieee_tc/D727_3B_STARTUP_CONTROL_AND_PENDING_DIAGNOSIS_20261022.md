# D727：3B 早期扩容与本地命中等待的离线归因

2026-10-22。复用已关闭的 D719/D726 完整 W0；没有新增 GPU 回放、生产修改、
配置选择或远端操作。本记录使用 analyze-results 区分观测、解释和未识别项，
使用 github-sync 保存明确路径的检查点。指标仍为冻结 V1＋单轮 V2／D648。

## 2. 首条请求如何放大为提前持有四卡

| 控制与初始准备观测 | D719 | D726 |
|---|---:|---:|
| 初始 activation trigger 相对业务起点（s） | -48.608095 | -46.634855 |
| 初始 engine ready 相对业务起点（s） | 2.120692 | 8.924465 |
| 初始 trigger→ready（ms） | 50723.854 | 55553.243 |
| 第一请求 TTFT（ms） | 4608.029 | 11244.304 |
| first-ready→第一请求准入（ms） | 1727.064 | 1668.837 |
| 三次扩容决策相对业务起点（s） | 273.784 / 1076.733 / 1078.769 | 14.735 / 16.818 / 18.883 |

D726 三个扩容决策的滚动 P95 都是 11244.303906 ms，与第一请求相同；
样本数为 2/3/3，queue 均为 0，active saturation 为 0.125/0/0，pending
为 0/1/2。唯一超过 1 的归一化分量是 TTFT/5000=2.248861。D719 三次
则由 active 分量超过 1 触发。逐条控制快照的比值、max-score、ready＋pending
和 all-low 谓词均与当时配置一致；不是漏算 pending 的实现错误。

两次共享 queue upper/lower=8/1、active upper/lower=0.875/0.4375、
TTFT upper/lower=5000/219.518056 ms、55 秒窗口、48 秒低负载持续条件和
2 秒控制间隔。这些是在线控制参数，不是离线 D648 服务阈值。
首请求保持 D726 控制 P95 的观测区间为业务后 14.735–59.779 秒。

D726 后三张卡实际于 14.905/16.978/19.046 秒持有，D719 为
273.970/1076.986/1078.987 秒；释放都约在 3975 秒。资源增加主要对应
提前持卡，而不是清理变慢。低 queue/active 且无 pending 时，滚动 P95
均值仍约 1949.519/1987.189 ms（D726/D719），远高于低阈；业务期 all-low
仅 1/0 次，未形成 48 秒区间，因此没有实际缩容。

**解释边界：**初始 ready 晚 6.804 秒同时包含触发晚约 1.973 秒和 activation
长约 4.829 秒；单轮无法将其全归因于图捕获。两轮首 ready 后仍等待约
1.7 秒才准入。不能删首请求、改到达时间、扣启动延迟、延长免费准备窗口，
也不能仅为缩容调高控制低阈；D713 的失败校准仍保留。

## 3. 稳态仍有本地等待，启动不是全部解释

合计 116 条；remote 为 69 条。实际 remote fetch 为 132，而 dispatch
remote 分类为 133，二者定义不同，不强行改成相同计数。

八个既定 500-request phase 的联合通过数：

|---|---:|---:|---:|---:|---:|---:|---:|---:|
| D719 | 483 | 451 | 462 | 466 | 451 | 454 | 445 | 452 |
| D726 | 473 | 477 | 475 | 447 | 463 | 453 | 454 | 464 |

D726 的 294 条联合违约为 TTFT-only 170、TPOT-only 109、both 15。

不利变化都保留；这些是固定已知负载的描述性分组，不是八次独立运行。

## 4. pending 边界揭示计时范围，不能将差额误称网络等待

复用原生 pending ack、GPU acquired、controller admitted 的同钟时间戳，
逐请求检查 4000 条身份、时间顺序和加和误差。routing 已嵌套在下表包络内，
不能重复相加；有重试的请求仍保留完整原始等待。

| D726 selected tier | 数量 | slot 开始→native pending ack（ms） | ack→controller admitted（ms） | 总 slot 包络（ms） |
|---|---:|---:|---:|---:|
| GPU | 1970 | 127.532 | 132.472 | 260.004 |
| HOST | 1325 | 189.248 | 87.678 | 276.926 |
| NVMe | 572 | 120.308 | 108.531 | 228.839 |
| remote | 133 | 59.365 | 65.154 | 124.519 |

GPU-hit 进一步分开：

| GPU-hit 条件均值（ms） | D719 | D726 |
|---|---:|---:|
| native pending ack→GPU acquired | 92.178 | 91.270 |
| GPU acquired→controller admitted | 49.732 | 41.202 |
| receipt 中 `load_and_acquire_ms` | 1.186 | 1.230 |
| receipt 中 completion fence | 0.138 | 0.190 |

**关键计时修正：**`residency_manager.py::demand_load_and_acquire` 先验证
来源、pin/slot 和完整 HOST allocation precheck，之后才设置记录
`load_and_acquire_ms` 的起始时间。因而 1.230 ms 不是完整原生事务耗时，
91.270 ms 也不能减去它后就全部解释为 IPC。后者含前置检查和进入该操作的
时间；D726 未启用逐函数观察器，无法把它准确拆成每个函数的 CPU 时长。
GPU acquired→admitted 同样是返回、调度与发布包络，不是纯网络。

D684 旧诊断曾直接观测完整 HOST 清点均值 74.234 ms、thread CPU/wall
99.24%，且同步控制会与短 decode 交叠；它支持关注这一机制，但早于当前
版本，不能将 74.234 ms 当作本轮已测值或直接从请求中扣除。D691 已证明
忙碌时每轮只处理一个 utility 的交错实际生效，不重做该已解决问题。
