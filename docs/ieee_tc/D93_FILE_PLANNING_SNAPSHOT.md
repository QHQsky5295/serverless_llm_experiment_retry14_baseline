# D93：文件层级规划快照的一致性修正

## 问题与证据边界

D92 原 3B 4000 请求 W0 开发回放在 27 个请求提交后中止：23 成功、4
随整轮取消、3973 尚未提交。首个错误为规划器拒绝不完整的 file-owner
快照；没有 OOM 或预算越界证据。完整失败记录及所有资源释放已保存。
当时没有记录拒绝条件的具体字段，因此不能事后声称已经恢复唯一根因。

历史依据：D90 的 `857fc7e` 区分内容身份与文件分配量。合法的 extent
分配变化会刷新 footprint、推进 source epoch，但不改变已验证内容。
D92 主入口沿用的 preparation_snapshot 先保存 budget epoch，随后
source_snapshot 才刷新源状态；末尾 replacement_capacity 还会再次验证
源。这使得同一把 owner 锁内也能产生前后不一致的版本，不是缺锁问题。

可证伪假设：只改变上一份容量观察、不改当前文件内容及其身份，真实
规划调用仍可能因预算/源版本不一致而拒绝。CPU 反例在未修正代码上
通过真实 runner→owner→selector 路径复现同一 ValueError。第二个测试
证实每个已确认源被重复验证两次。测试使用微小文件和受控旧观察，
不是对 D92 原始文件系统事件的重放，也不是推理性能实验。

## 第一性原则处理

1. 保留既有 owner 锁及内容/路径/引用校验，先完成源状态刷新。
2. 在锁内取得一份容量 inventory，HOST 总预算、文件层预算与替换可回收量
   均由该 inventory 派生；序列化时不再次改变源版本。
3. 已确认源只检查一次，并把这份结果同时交给候选和替换计算。
4. 未结束的文件分配仍按既有保守上界计入，不因 snapshot 就获得物理空间。
   执行时继续检查版本、引用、内容、预算并实际预分配；不增加重试、sleep、
   fsync、忽略异常或 unknown→remote 的兜底路径。
5. 原拒绝条件不变；错误附上当时的 owner/epoch/时间与缺失对象字段，
   下次失败能定位具体条件，不用之后的快照覆盖首次证据。

这是一份协调者管理下的状态视图，不声称文件系统所有 stat 同时发生，
也不声称与另一进程的 GPU/HOST tensor 状态构成跨 owner 原子快照。
Linux 后台分配仍可能变化；保守容量预留及执行重检承担该边界。
IEEE 九式、EWMA、收益/背包目标、路由、admission、预算和 D88/D89
已冻结开发配置没有改变。

## 外部原始资料核查

- Linux 明确区分 extent 已分配但尚未写入等状态，且 FIEMAP 查询与强制
  同步是不同选项；不能为了快照稳定给服务路径添加同步写盘。
  [Linux FIEMAP 文档](https://docs.kernel.org/filesystems/fiemap.html)。
- vLLM 0.30.0 的 BlockPool 在更新/删除本地缓存索引后产生相应缓存事件，
  并将引用与可回收性分开维护。这里借鉴的是从已更新 owner 状态导出
  决策视图的原则，不把 KV 管理代码或其策略移植为 LoRA 算法。
  [固定版本官方源码](https://raw.githubusercontent.com/vllm-project/vllm/v0.30.0/vllm/v1/core/block_pool.py)。

### 失败顺序与下一条主线

1. 原计划到达继续注入，完成率低于到达率，积压跨多个热点阶段增长。
2. 从 04:15 起出现预设超时。超时清理未取得完整原生所有权确认时，副本被
   标记 draining、退出路由，但当时仍持有原生 GPU 上下文。
3. 后续扩容分配被物理 GPU owner 拒绝，原因是目标卡仍有上下文。最终原始
   错误为 `IEEE activation failed; no blind control-loop retry`；外层随后
   出现 external replay failed，不把外层 launcher 标签当原始根因。
4. 只读代码发现 `_select_dedicated_device_id` 从 `get_slots()` 取得占用集合，
   而该接口仅返回 running 成员。`get_all_slots()` 已保存 draining owners。
   因此“可路由副本集合”被误用于“物理占用集合”是下一步优先 CPU 反例；
   不能放松 GPU 分配安全检查、提前伪造 release 或简单吞掉扩容异常。
5. 另一个待验证假设是并发路由重复获取完整源快照、旧视图丢弃再查询造成
   控制开销放大。控制连接本来就与生成连接池分开，不能把该问题写成共池死锁。
   先定位并验证，再优化；本次没有进行性能补丁或新 GPU 重试。
