LoRA I/O、RPC 等其他观测区间也不默认可加和。上述成功请求显示等待主要在

97 条 RuntimeError 分成：96 条父进程返回
`native RPC ownership unresolved; new generation withheld`，
1 条经子进程 RPC 包装返回同类错误；本次生成提交状态均为 `not_submitted`。
这只说明本次新生成未提交，不代表更早原生调用已结束或资源已释放。
全部 999 条 timeout 的 generation/source-admission 阶段证据未保存，
不能把缺失字段或空 instance_id 解释为“从未 dispatch”。

首个 timeout 是 `req_00840`，控制器观察相对业务起点 2,730.165340 秒；
首个返回的 ownership 错误是 `req_01994`，相对起点 3,661.265477 秒。
后者晚于前者，因此不能仅凭后续恢复记录解释最初超时。
231 次控制观测同时出现 ready=0、queue>0；它们是事件数，不是独立请求数。

安全保护的作用是防止原生调用状态未知时盲目重复提交、错用 adapter 或提前
释放引用；它不是可接受低完成率的理由。后续应减少造成状态未解决的控制开销、
完善实际完成/取消协调，而不是删除校验或延长时限掩盖问题。

2026-09-28 再次核对的原始资料：

- [Python 3.12 asyncio 文档](https://docs.python.org/3.12/library/asyncio-dev.html)：
  同一事件循环线程中的同步 CPU 工作会延迟其他任务。这支持检查同步解析，
  不证明本轮全部超时由它引起，也不自动支持线程池方案。
- [vLLM 0.30.0 LoRA worker 源码](https://raw.githubusercontent.com/vllm-project/vllm/v0.30.0/vllm/lora/worker_manager.py)：
  LRU 操作由核心引擎串行调用，动态加载/激活仍会改变状态。
  因此即使复用解析结果，也不能省略 owner、epoch、内容与新鲜度检查，
  不能把多次 RPC 间的状态当作一个原子快照。

这些只界定后续最小验证的边界；本轮尚未修改生产解析或通信逻辑。
