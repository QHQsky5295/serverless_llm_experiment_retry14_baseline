# D668：3B当前HOST清点与核心等待的单次定位回放

2026-10-18。承接D667，3B W0优化主线。此前完整D665的联合延迟达成88.75%，
尚未达到冻结要求；这次是详细观测，不是新性能候选或G1/G2结果。

## 唯一问题和停止边界

当前完整HOST物理图清点究竟在原生核心线程占用了多少时间，分别发生于哪些
控制操作？将函数内部wall/thread-CPU与其外部排队分开，避免把pending到
acquired一整段等待都归因于清点。D667已完整记录历史失败候选、官方vLLM/
PyTorch源码和仪器设计，本轮再次核对原始源码，不引入新的调度策略。

只做一次原W0前1000条诊断，不按SLO胜负重跑，不从时延中扣除观察器开销，
不以prefix成本外推4000请求。若HOST清点不是主要开销，转向已测其他段；
若是，再验证保持物理状态正确性的新设计，不能用epoch/TTL缓存跳过检查。

## 完成：实测开销与解释边界

本次唯一回放于2026-10-18完成，实际源码提交为
`e760eadb040c74f284fa345859db7bd482d0a138`。原生绑定、输出数量与计时合同
1000/1000完整，共122510输出tokens；独立数值正确性仍未知，n_correct不补造。
联合时延达成901/1000，TTFT949、TPOT945。平均TTFT821.399ms、P95
2159.547ms；平均TPOT18.317ms、P9535.392ms；平均E2E2918.553ms。
物理占用4369.905970 GPU-s只描述这次带仪器的前缀，不外推完整W0、不作排名。

四个原生核心的287670个span全部正常关闭，无截断、未完成span或缺失decode
窗口；1000/1000请求窗口可分析。16329次新增观测中，9233次为库存清点，
7096次为allocator计数查询。下表均为本次实际调用，不是RPC等待的推算值。

| 测量对象 | 次数 | 平均wall / P95（ms） | thread CPU / wall |
|---|---:|---:|---:|
| HOST库存清点，全部scope | 9233 | 69.830 / 100.034 | 99.21% |
| 完整32-adapter registered库存 | 6419 | 79.415 / 101.932 | 99.15% |
| allocator计数查询 | 7096 | 0.0719 / 0.0943 | 98.15% |

已有未完成工作时，client控制操作累计245.179s，其中清点嵌套162.223s。
这表明清点本身占用核心CPU，而不能把该时间解释为仅等待另一进程的RPC。
全部清点644.741s跨四个进程累计，不能作为用户时延串行总和。

49条2–32 token且TPOT违约的请求，平均decode窗口538.305ms，其中与清点
交叠216.372ms、与全部client控制交叠334.158ms。263条同长度未违约请求
对应219.716/30.157/45.017ms。这是描述性关联，不是匹配反事实；多个请求
窗口可能重叠，不能逐请求相加为总CPU时间，也不能把216.372ms直接当作可
消除的延迟。GPU kernel/异步执行并未由此被单独测量。

观察器总时间60.368s，写入49.175s包含在其中；四进程观察包络累计4169.059s。
这些数值保留而不从TTFT/TPOT中扣除。结论限于当前3B、32项native HOST容量、
这1000条原序请求和本次观测；不能以旧7B profile替代当前测量。

决策：下一候选优先审计新鲜物理图清点的重复工作及查询范围，allocator查询
不是本次优先瓶颈。不引入owner/epoch/TTL跨请求缓存，不绕过实时容量/别名/
引用检查；先对照D329/D333/D610/D635及官方实现证明语义，再选择单一可证伪
改动。D665完整W0联合88.75%的缺口仍未关闭，本次不接受任何生产性能候选。
