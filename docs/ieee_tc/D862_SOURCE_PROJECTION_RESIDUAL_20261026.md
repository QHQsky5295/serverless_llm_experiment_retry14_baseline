## 2. GPU 时间差的实际来源

| 同钟时间/事件 | D858 | D861 |
|---|---:|---:|
| 初始实例 ready，相对业务开始 s | 2.797530 | 3.700517 |
| 首条请求 TTFT，ms | 4864.030117 | 5641.947306 |
| 两次扩容决策，相对业务开始 s | 322.321149 / 324.411760 | 8.640847 / 10.659175 |
| 触发超过 1 的分量 | active，1.142857 | TTFT，1.128389 |
| 第一扩容决策的 TTFT 样本数 | 41 | 1 |
| 业务到达窗口 GPU-s | 11244.543499 | 11872.086873 |
| 终态后收尾 GPU-s | 31.781257 | 29.155578 |

控制事件逐条复算 queue/active/TTFT 比值、max score、ready+pending 和 all-low，
均符合当时冻结配置。D861 首条请求越过 5000ms **在线扩容阈值**；这不是共同
SLO 的离线阈值。两次早期扩容时 queue=0、active=0，P95 等于该首条请求。
D858 首条没有越过此线，后续由真实 active saturation 触发。业务窗口多持卡
627.543373 GPU-s，收尾反而少 2.625679 GPU-s；总差 624.654006 GPU-s。
物理区间积分和四个互斥窗口均核对，不能把成本增加归因于清理延迟。

两轮均无 all-low 时刻，未发生缩容。低 queue/active 且无 pending 的采样分别
1582/1736 个，其 P95 TTFT 均值 2089.079/1935.728ms，仍高于在线缩容线。
这是现有规则的实际行为，不是改变阈值、扣除首请求、延后业务或给予免费
准备的理由。D712/D713、D737/D744 的既有否决证据继续有效。
首 500 请求联合通过从 479 增至 492，但后七段合计少 24 条；不能把全部 SLO
差异归为启动。没有构造反事实 GPU 节省量，也未证明 0.9s 初始 ready 差由
D860 引起。完整闭环轨迹不同，局部代码作用与运行变异在单轮中不可分离。

## 4. 单一下一问题与停止重复方向

本节点关闭“再减少一次来源 stat 就能改善完整目标”的候选，不继续在该
局部堆叠优化。D851–D854 全 owner 异步化、D844/D856 ctypes、D850 提前通知、
D628/D631 SHA 移锁、D822 压力共享、D839/D840 解码选择不重新测试。
D857 已接受的一次读引用观察保留，不撤掉已完成的 HOST 融合和图重放优化。

下一问题限定为：**当前短输出 decode 窗口中的慢迭代，主要处于原生模型执行、
原生控制调用，还是输出交付等待？** 先核对既有 native observer 和当前调用
边界；只有无法由现存记录回答时，才登记一次有界诊断，不先改 batch/token/
线程数。D722 复用 D684 的旧迭代记录；D723 只有前 100 请求，早于 D724/D725
图覆盖及 D747/D751 HOST 融合；D843 是完整 W2 的 controller 栈，不是当前
原生迭代分解。因此旧材料不能作为当前后端停顿份额的证明。

[vLLM 0.30.0 core](https://raw.githubusercontent.com/vllm-project/vllm/v0.30.0/vllm/v1/engine/core.py)
的 batch queue 优先提交新批次，再取已完成输出；单个 step 可包含前批结果
等待，分配形状不能直接标作纯 prefill/decode 核函数时间。
[同版本 profiling 文档](https://docs.vllm.ai/en/v0.30.0/contributing/profiling/)
明确观测会扰动性能。后续如需诊断必须单独标识、不进入主排名，沿用既有
观察器及资源上限，不连续追加剖析代替有证据的候选和完整评估。
