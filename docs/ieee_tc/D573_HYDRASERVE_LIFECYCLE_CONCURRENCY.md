# D573：先排除 HydraServe 复现路径的额外阻塞

2026-10-16。此次不改 PrimeLoRA、IEEE 九公式、共同输入/指标、原生 HydraServe
调度算法，不访问其他项目 k3s。D572 的原生日志审查之后，最小事件屏障测试
确认本机适配中的全局锁会让一个副本关闭阻塞其他副本的寻址/创建。

已改为每副本生命周期互斥和短注册临界区，并保留真实释放、同副本顺序、
失败/取消所有权、依赖关闭和原生 GPU 资源归还语义。测试前恰好两个目标
并发断言失败；修正后 71 项 CPU 检查通过。测试峰值 51,798,016 B，内存
high/max/OOM/OOM-kill/swap 均为零；实际测试资源域已经递归空并关闭。

首次加载错误测试包和首次扩展回归缺依赖的失败保留，不伪作系统性能失败。
详细改动、原始来源、前后源码和测试记录位于 baseline 仓库同名文档及
`paper_results/ieee_tc/hydraserve/d573_lifecycle_concurrency/`；本仓库保存同一
资格证据和跨仓库备份身份。发布后 checkpoint.json 记录 baseline 提交。

**证据边界：CPU 资格通过，不是实际 TTFT/SLO 改善。** 仍需复用原 100 请求
进行实际路径资格，再用新执行键补受影响的完整对照。不能把估计锁等待从旧
D510/W0、D546/W1 时延中扣除；不能把所有差距归因于适配层。原生控制器在
启动期间暂停新的调度检查这一行为没有修改。
