## 选择的新执行边界

当前 `LocalSourceReferences` 与主调度器处于同一解释器；HTTP线程也通过
该对象执行预算、清点和发布。D851–D854曾把完整文件事务交给线程，但仍
共享解释器与状态锁，D855已记录负向结果并回退。因此本次选择**独立进程
中的单一文件状态权威**，不是重新包装旧线程方案或缓存旧快照。

这是一项需要实测的架构假设：文件状态CPU工作不再与请求控制共享解释器，
可能减少相互阻塞；新增IPC、序列化和排队可能抵消收益。现有数据不能判定
净效应。用户已明确要求推进有潜力的优化，不因架构不同而放弃。

| 现有依赖 | 进程化处理 |
|---|---|
| owner内字典、RLock与物理清点 | 仅子进程拥有；复用原owner检查，不复制账本 |
| snapshot→选来源→acquire的复合锁段 | 一个原子命令，不拆成存在空窗的多个RPC |
| materialization/workspace/interest上下文 | 子进程保存上下文；父进程只持不透明ID；不跨IPC持锁 |
| publication闭包调用manager | 在子进程内复用mutation与publish_directory，不序列化闭包 |
| native HOST退出证明 | 传递真实pidfd，而非另一进程无意义的整数fd |
| 文件变化回调 | 命令回执携带有序变化事件；集成时统一投递既有wake机制 |
| 取消时引用/空间的实际归属 | 命令继续可join；不丢弃已完成突变的回执、不提前释放 |
| 进程/IPC异常 | 暴露失败，不重建空owner、不退回旧账目或无约束路径 |

D888首先实现这个边界及真实CPU组件检查，不切换正式runner、不新增GPU
性能点。随后须迁移所有实际调用，特别是异步规划/路由、HTTP同步worker、
文件复制与publication、通知、停止顺序，且所有子进程在原服务资源域内。
不将组件通过或进程存在称为整系统收益；完整迁移后按同一指标运行一次W2。

## 外部依据与适用边界

- [vLLM官方CPU路径说明](https://vllm.ai/blog/2024-09-05-perf-update)：
  API与engine分进程用于隔离CPU/GIL竞争。这里借鉴分离执行边界，不移用
  其H100上的改善比例，也不声称已经证明本机GIL占比。
- [vLLM 0.30.0 core_client](https://raw.githubusercontent.com/vllm-project/vllm/v0.30.0/vllm/v1/engine/core_client.py)：
  区分进程内、同步跨进程和异步跨进程调用。现有后端版本不升级。
- [Python 3.12进程文档](https://docs.python.org/3.12/library/multiprocessing.html)：
  使用spawn避免继承多线程/CUDA状态；对象跨进程须显式传递，不能把复制后
  的本地字典当作共享权威。复用本项目IEEEPlanningCPU已有单worker做法。
