## 2. 观察与解释的边界

1. **不是固定八请求总入口。** 当前 open-loop 的总容量按 runtime 数乘模型容量；
   四副本时为 4×8=32。记录恢复的入口后占用峰值也是32。
2. **占用入口不等于在原生引擎内生成。** 全窗口平均入口后占用29.3039，
   native dispatch→末 token 占用3.1804。后者仍含原生队列和 prefill，
   不是“恰好3.18张卡在计算”。不能用29.30证明引擎批处理已经饱和。
3. **GPU 活动的交叉证据。** 4412个窗口内资源采样中，4071次有入口前积压；
   3625次入口到终态占用为32。持卡GPU在每个采样点先求均值，再跨采样求均值，
   为22.5641%。它不是严格时间加权利用率，也不能单独证明CPU是唯一瓶颈，
   但不支持将长排队直接归因于3090算力饱和。
4. **生成后的2.55秒不能混作decode。** 源码的请求结果在生成返回时构建，
   之后 `_finish_runtime_request_reservation` 等待 pending关闭、GPU引用释放、
   HOST引用释放，最后外层入口名额释放并记录终态。测得的是这一整段外层差值，
   不是其中某个RPC的独占耗时。入口释放略早于终态，因此占用是保守上包络。
5. **E2E边界待一致性核查。** D112原报告止于controller完成；外层终态比该边界
   平均晚2.550083秒。两列均保留，不覆盖旧数、不把后者称为已经测得的客户端
   socket响应时刻。正式比较前要核对冻结协议中的完成通知 `c_r` 对应哪一观察点。
   本次不改变TTFT/TPOT或物理GPU生命周期；也不据此宣称正式计量已合格。

每副本 native 区间计数为1056、961、989、994；峰值均8。
source-admission之前14.02秒包括观察、选择、冲突重试和来源保护等，不能凭区间
名字将其全部归因于路由公式。准备段9.54秒可能包含合法加载/竞争，不应全部删除。

## 3. 历史、源码与外部依据

- D110有独立详细CPU profiling；其采样不是D112的测量，也不能作配对因果对照。
- D111只共享当前进行中的不可变native解析；D112已有4000请求完整成功，
  但仍有8507次陈旧集合拒绝。该计数不是失败请求数，不能据此关闭新鲜度保护。
- 当前 `_rpc` 在线程中等socket，但响应JSON在控制事件循环中解码；原生progress
  回调等待事件循环确认；释放路径有多个顺序控制RPC。这些是下一步待检验机制，
  并非本次已证明的唯一根因。
- Python说明同一事件循环的任务共享线程，阻塞计算会延迟其他任务；这是检查
  控制面串行占用的机制依据，不能据此直接量化本系统收益。
  [Python 3.12 asyncio 文档](https://docs.python.org/3.12/library/asyncio-dev.html)
- vLLM 0.30的LoRA管理源码说明其修改由单线程engine core调用。不能简单将
  native状态修改放到任意并行线程，破坏其线程安全前提。
  [固定版本源码](https://raw.githubusercontent.com/vllm-project/vllm/v0.30.0/vllm/lora/worker_manager.py)
- dLoRA联合处理请求与adapter编排，是相关背景；它的结论不能替代本系统的
  测量，也未证明这里的RPC路径快慢。
  [dLoRA官方论文入口](https://www.usenix.org/conference/osdi24/presentation/wu-bingyang)
