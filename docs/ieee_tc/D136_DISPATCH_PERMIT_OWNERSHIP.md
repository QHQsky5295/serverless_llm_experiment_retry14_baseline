# D136：入口排队的空位归属与先到先服务

## 问题与证据边界

主线仍是 PrimeLoRA IEEE Full 的完整资格。D135 的 4,000 请求均已终态，
其中 3,999 个符合原生生成合同，1 个超时；不是正式 G1/G2 合格结果。
本项不重跑 D135，也不重建一次性交付缓存。

| 已有观测 | 解释范围 |
|---|---|
| 成功请求平均 TTFT 534.819472 s，原生 TTFT 0.315762 s | 排队/控制路径值得优先检查，不直接证明某个函数是全部瓶颈 |
| 平均 arrival→入口准入 530.910913 s | 是已有成功请求的阶段测量，不是 GPU 内核耗时 |
| 每副本原生并发峰值 2，全局峰值 8 | 排除“后端始终完全串行”；不能证明持续饱和 |
| req_03061 进入服务接收队列仅比计划到达晚约 3 ms | 不能把它的整个超时归因于客户端未送达 |
| 该失败请求未保留后续准入/原生事件 | 不能据默认零字段推断它从未 dispatch；确切超时位置仍未知 |

这些数值复用 [D135 完整结果](D135_FULL_W0_FULL1.md)，无新增 GPU 测量。
D135 原生合同验证不等于数值 adapter 区分性验证；共同 warm SLO 仍待标定。

## 历史实现与原始资料

旧入口以 `Condition` 等待 `_dispatch_admitted_requests < capacity`。
release 先减计数，再 notify 一个等待者；被通知者恢复前，新到任务仍能
获取这个空位。旧任务醒来发现已满后重新排到条件队列尾部。
这不是 IEEE 的副本选择公式，而是公式路由之前的控制器入口实现。

Python 的 Condition 只承诺通知后重新获取锁，不把资源授予被通知者。
Python 3.12.12 的 Semaphore 源码则在唤醒等待者前扣除可用计数，并对
已授予但被取消的等待者返还额度。本项借鉴这种资源归属原则，但保留
Prime 原有动态容量函数；不固定成另一套并发配置。
[Condition 文档](https://docs.python.org/3.12/library/asyncio-sync.html#asyncio.Condition)、
[Python 3.12.12 源码](https://github.com/python/cpython/blob/v3.12.12/Lib/asyncio/locks.py)。

vLLM 0.30.0 的入口未完成请求限制与 scheduler 的运行序列/token 限制分别
存在。这里仅以它区分入口资源与原生调度资源的做法检查语义，不移植其
默认数值，也不借用其性能结果。
[AsyncLLM](https://github.com/vllm-project/vllm/blob/v0.30.0/vllm/v1/engine/async_llm.py)、
[Scheduler](https://github.com/vllm-project/vllm/blob/v0.30.0/vllm/v1/core/sched/scheduler.py)。

## 可证伪假设与唯一候选

假设：旧入口存在可复现的空位抢占，违反已排队请求的先到先服务；使释放
与授予成为同一个无 await 的事务可消除这一条乱序路径。
这不等于假设 D135 的唯一超时已经被定位，也不承诺消除总体排队。

改动限定为现有 runner 的入口 permit 队列：

1. 请求按进入入口的顺序持有 FIFO ticket。
2. 按原容量函数，把实际空位计入最早等待者的所有权，再唤醒它。
3. 已授予但未恢复的等待者仍占计数，后来者不能抢占。
4. 排队期间取消只撤回 ticket；授予后取消返还一次 permit。
5. 扩容只授予新增可用空间；缩容不撤销既有持有者，等计数下降再授予。
6. runtime slot 通知、选中副本后的 source/LoRA/KV 引用与释放均保留。

没有提高容量、延长 deadline、添加轮询 sleep、提前假报释放、改变 trace、
增加 warmup 或绕过物理保护。仍使用完整 4,000 请求和相同模型配置验证。

## 最小测试与当前结论

| 检查 | 结果 | 能支持什么 |
|---|---|---|
| 旧方法：older 已排队，newcomer 已可运行，再释放 permit | RED：实际 `[newcomer, older]` | 真实 runner 方法存在空位抢占反例 |
| 同一交错、相同容量下的新方法 | GREEN：`[older, newcomer]` | 这一条抢占路径被消除 |
| 排队取消、授予后取消、取消后先发生容量通知 | 通过 | 无丢失/重复返还，取消后后续请求仍进展 |
| 动态扩容与缩容、仅 slot 通知 | 通过 | 入口计数与原容量边界一致 |
| 64 个 CPU 测试任务、容量 2 | 通过，FIFO，峰值 2，最终计数 0 | 控制器队列功能；不是推理吞吐实验 |
| 无所有者 release | 显式拒绝下溢 | 不再静默掩盖错误释放 |
| 扩展回归与旧结果保护 | 1,068 项通过；147 个受保护条目未变 | 支持 CPU 功能与回归验证，不替代 Full |
| 普通 7B W0 Full | 未开始 | 尚无端到端改进或完整资格结论 |

CPU 测试 9 项通过（0.005 s）；初始 RED 1 项失败（0.002 s）是预期的
缺陷复现证据，保留原日志。二者均在实际 3/4 GiB、swap 0、CPU
`2,3,26,27` 的限制内完成，内存 high/max/OOM 事件均为 0。

扩展回归用时 134.480 s；完整命令 2:24.10，峰值 RSS 1,176,684 KiB。
另核验 166 条未改变的冻结来源引用与计划/指标 SHA。全部实际资源域在
测试后为空并按身份关闭。没有进行 GPU 推理或远端服务调整。
