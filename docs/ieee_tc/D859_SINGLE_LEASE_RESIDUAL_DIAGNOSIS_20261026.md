sent，无请求内打包。复用D848/D855同钟连续六段，完整CSV保留。

总span下降15.498ms；发布缩短但接收/预留和发布后span增加，不能称交付各段
均改善。当前服务端对象读取均值1.917ms、socket write累计248.131ms、发送
包络250.078ms；与客户端区间重叠，不跨主机相减、不相加为总延迟。客户端
headers后先reserve_files再读body，接收段不是纯网络。505次传输也不自动
等于510条Remote请求，更不等于145条Remote TTFT违约请求。

[Linux TCP文档](https://man7.org/linux/man-pages/man7/tcp.7.html)区分接收窗口、
应用缓冲和调度延迟，支持不将socket write包络当链路带宽；不能据此证明
本机背压份额，不更改全局网络参数。

## 4. 取舍和下一主线

本次数据不支持重开全owner线程异步化D851–D854、通知提前D850、stat局部/
ctypes边界D844/D856、解压搜索D839/D840、压力ACK D595/D598、共享压力D822、
SHA移锁D628/D631或控制时序D737/D744。D857一次读租约减少重复观察继续保留，
不将它换名重复测试。D172已使用msgspec解码，D192带递归验证的新编码无收益；
仅凭D843解码采样多，不能重跑同一编码候选。

当前不能从这些包络选定一个新的生产补丁。下一只在准入→来源的现有调用
依赖和当前实际工作量中寻找**明确可删除的重复工作或可保持所有权的执行
边界**；先对照上述历史。不同边界若要重开，必须写明改变了哪个前提、如何
保留实时身份/容量、取消与最终结算。没有具体依据就不追加GPU回放，也不
用一串小参数或局部stat微测代替主线。新候选仍需最小相关验证和唯一完整W2。

本轮重新核查[vLLM官方CPU路径分析](https://vllm.ai/blog/2024-09-05-perf-update)
和[Python asyncio](https://docs.python.org/3.12/library/asyncio-dev.html#running-blocking-code)：
前者区分CPU工作、同步及进程隔离，后者说明同步任务阻塞同循环。它们没有
给出本机GIL/锁的因果比例，不能将vLLM的进程结果当线程方案成功证据。
