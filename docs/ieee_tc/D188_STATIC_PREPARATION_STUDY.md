## 问题与历史

D187当前版本观察到，控制器536个业务期主线程样本中，95个包含
`preparation_snapshot`。其中93个来自稳态准备入口、2个来自初始化。
这只定位值得检查的同步路径，不给出CPU时间占比或全部等待的因果解释。
当前源码的工件内容清单已经被冻结，但每个准备快照仍逐adapter校验文件名、
计算同一内容SHA、求逻辑字节、生成相同目标描述。

- D151已裁掉路由不消费的staging观测，本轮不重复该改动。
- D153已合并同一次文件owner清单扫描；本轮保留这一完整实时扫描，不改成TTL。
- D159已将纯选择/目标构造合入既有CPU worker；本轮不增设另一规划进程。
- D163已消除计划成员查询的冗余解码；D172/D173未确认净收益，不重复解码优化。

[vLLM官方性能分析](https://vllm.ai/blog/2024-09-05-perf-update)将CPU数据准备、
对象构造及同步依赖列为值得剖析的服务开销；[Python异步文档](https://docs.python.org/3.12/library/asyncio-dev.html#running-blocking-code)

## 本轮具体测量

复用D153已有fixture、交替次序和输出比较方法。分析原型从当前函数AST
只替换三个纯表达式：canonical ID校验、内容摘要、静态目标描述生成。
动态清单、来源重验证、epoch、预算、预留、replacement和返回时间戳原样保留。
静态输入脱离原可变字典，以只读嵌套映射保存；每个返回值仍脱离模板。
原型只存在于本轮分析脚本，不被服务导入。

三种条件各三对交替组件调用，共18个结果逐字段相同，仅忽略原本不同的
capture时间戳。500-name fixture只扩展既有测试元数据，不生成LoRA或trace。
另直接读取既有7B的500-adapter内容索引，配空文件owner，既不下载也不复制工件。
最后故意改动实时文件/插入未确认目录，原型分别拒绝；不能把静态描述当成命中。

## 裁决：支持一个实现候选，不代表已优化成功

证据支持将**不可变工件描述单独编译、动态物理状态继续逐次确认**。
下一步直接实现并验证这一候选，不再重复同一组件研究或D187诊断回放：

1. 从同一已冻结内容索引建立不可变描述；记录文件名、大小、内容SHA和
   逻辑字节，不读取未来请求，不存储tier/readiness/budget等动态状态。
2. 目标文件占用仍按实际目的地分配粒度逐文件上取整。描述须绑定准确的
   owner根目录和实测粒度；绑定改变必须重新编译或显式失效，不能沿用旧值。
3. 保留当前一次新鲜文件清单、二次stat变更检测、来源withdrawal、共享inode/
   pending allocation/实际余量、执行前重检查。全局预算不能由目标描述替代。
4. 可变/外部输入仍需完整验证；只允许真正不可变且有明确生命周期的内部
   对象走预编译路径，不加“已验证=true”兜底，不根据字典对象地址猜其未改变。
5. 验证输入别名与返回值隔离、同内容重复配置、拒绝不同内容、subset身份、
   根目录/粒度绑定、真实源变化与未确认副本，以及既有预算/取消/退役回归。
6. CPU资格通过并备份后，按相同cap4/D157配置做一次普通7B完整4000回放，
   与D185比较全部阶段、TTFT/TPOT、实际GPU-s及相同临时候选SLO，保留退化。

没有修改九个公式或控制规律，也没有接受性能收益。7B数值身份、共同warm/
Resident标定、新指标旧Prime对照、G1/G2仍开放；7B实际达标前不推进3B或基线。
主比较、消融及敏感性矩阵全部保留。按计划§11与学术绘图规则，本阶段交付
精确组件表，不将微测画成系统优势图。
