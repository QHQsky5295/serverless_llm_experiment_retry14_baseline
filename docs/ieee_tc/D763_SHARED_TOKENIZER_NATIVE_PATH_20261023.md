# D763：共同分词器适配的原生路径验证

## 问题与边界

D760 完整 W0 的 4000 个请求中，2522 个返回原生响应、1478 个失败；
D761 已隔离出相同 tokenizer 的重复构造及延迟回收。D762 依据已发布工件
内容一致性复用共同分词器，不改变 LoRA 权重绑定、RR、store、扩缩容、
生成合同或资源限制。本次只验证这一改变在真实原生服务中生效。

复用原 3B trace 的前 100 请求（29 个 adapter、17369 个目标 token）、
原生 vLLM 0.10.2、既有 32 GiB store 和四 GPU 上限；min=1、max=4、
target=8、keep_alive=10、1800 秒请求保护不变。真实远端交付使用已经
发布的只读对象，没有请求期间打包，也没有新增权重或负载。

全部因果归于共同分词器，更不能从启动主导的前 100 请求推算完整 W0。

## 结论与下一步

本次证明改变后的原生服务路径可执行、共同分词器实际生效，且所测前缀没有
出现内存节流。它尚未证明 D760 的完整负载停顿已解决，也不是最终性能点。
独立 LoRA 数值正确性仍未知，`n_correct=null`；HTTP 成功和长度符合不
替代该证明。低短前缀 SLO 不触发基线配置搜索。

下一 D764 保持相同配置与本次适配，直接执行原 4000 请求完整 W0；复用
已经通过的 500-ID/1000 请求资格，不再增加重复短检查。保留 D760 失败。
随后依据实际完整结果继续同配置 W1/W2 和剩余基线，而非无限优化基线。
