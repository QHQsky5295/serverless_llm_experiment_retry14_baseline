# D459：D458 完整运行的阶段与资源反馈诊断

2026-10-12。离线分析，不新增性能运行、配置候选或图表。

## 问题与边界

D458 相比 D371 减少 17.3049% 生命周期 GPU 时间，联合 SLO 为 96.45%；
但资源仍高于 ElasticLocality 21.0622%，P95 TTFT 高 17.6310%。继续主线需要
识别剩余业务期持卡和请求延迟的实际来源，不先修改控制阈值或增加兜底路径。

复用 D454/D455 分析器，增加显式 `--include-d458`，保留默认旧路径与旧结果。
核验 D458 matched_comparison 的固定 SHA、六条旧行、公共参考和输入合同；
同一原生单调时钟做 12 段可加和分解，再统计 8 个固定 500 请求阶段。
物理 GPU 用已经闭合的区间并集，四个互斥生命周期窗口，控制事件仅报告样本数。
原生加载与路由是嵌套阶段，不再额外相加；样本数不是持续时间；条件分组不是因果对照。

输入为 D371/D453/D458 原始结果，旧结果不改写。输出到独占 D459 原始目录和
`paper_results/ieee_tc/main_comparison/d459_d458_diagnosis/`。运行前先做分析器
回归测试；CPU 独立限额 high3/max4 GiB、swap0、CPU2,3,26,27，隐藏 GPU。
不启动远端服务，不重放负载，不做置信区间，不更改公式或在线配置。

磁盘低于 150 GiB 时不得开始下一重型实验。只对明确闭合且无人使用的已有
日志采用既有无损压缩工具，校验两次解压 SHA 并保存原路径→归档回执；唯一
权重/trace/测量内容、旧投稿保护目录及用户修改不删除。空间回收不与性能运行并行。

结果出来后只提出有直接证据支持的下一假设；任何实际优化仍须核查代码历史和
原始文献/官方实现，验证 IEEE 等价性、最小正确性及完整回放。不能从本次观察
直接宣称孤立因果效应或 G1/G2 已完成。W1/W2、3B、HydraServe 隔离资格、所有
消融/机制/敏感性和最终文档图表均保留。

## 实际结果：三条相同 W0 的完整请求时间线

三系统身份为 D371 旧 PrimeLoRA、D453 ElasticLocality、D458 新 PrimeLoRA；
各 4,000 请求。40 个 CPU 回归测试通过，12,000 条请求的 12 段恒等式误差
最大 0 ms。旧两行的阶段、控制和规划分析与已封存 D454/D455 逐字段完全一致。

| 平均阶段 / ms | 旧 PrimeLoRA | ElasticLocality | 新 PrimeLoRA |
|---|---:|---:|---:|
| 到达→控制器接入 | 207.674 | 6.136 | 69.582 |
| 接入→申请入口许可 | 56.340 | 14.925 | 26.876 |
| 入口许可等待/恢复 | 0.380 | 356.170 | 167.528 |
| 等待副本接纳位置 | 281.050 | 151.597 | 249.701 |
| 接纳→原生引擎入口 | 291.174 | 173.306 | 281.610 |
| 原生入口→队列 | 105.608 | 104.004 | 136.062 |
| 原生队列等待 | 6.974 | 4.166 | 9.120 |
| 原生 prefill | 201.598 | 193.393 | 205.273 |
| 原生 decode | 3336.563 | 3102.616 | 3636.602 |
| 原生末 token→worker 完成 | 82.747 | 92.415 | 114.058 |
| worker 完成→控制器回收 | 255.562 | 4.157 | 90.735 |
| E2E | 4825.670 | 4202.886 | 4987.147 |

另一个接纳转换阶段在三者均为零，保留于 JSON 中。路由、LoRA I/O 等嵌套
计时在完整 JSON 另报，不加进上述时间和；阶段分位数不能相加。

观察与解释分开：

1. D458 相对 D371 的接入延迟减少 138.092 ms、完成回收减少 164.827 ms，
   支持文件视图优化后控制路径阻塞变小的观察；单轮不能给孤立因果效应或置信度。
2. 平均 TTFT 仅降低 5.046 ms。许可等待增加 167.148 ms，解码增加 300.039 ms，
   因而 E2E 增加 161.478 ms。保留这些退化，不将资源下降写成全面更快。
3. 相对 ElasticLocality，新 PrimeLoRA 平均 E2E 多 784.261 ms，其中 decode
   多 533.986 ms，约占差值 68.09%。原生 token 工作量一致，但实际并发、路由和
   准备活动不同；尚不能把这 534 ms 全部归于加载争用或控制器。
4. 新 PrimeLoRA 第 0→7 阶段的接入为 36.160→86.396 ms，完成回收为
   32.349→122.027 ms；第 6 阶段还有 147.749/181.368 ms 的较高值。旧版末阶段
   为 406.651/456.315 ms。增长有所减轻但仍未消失，不能宣称 CPU 路径已无瓶颈。

相对旧版，业务窗口少 2668.997 GPU-s，但清理窗口多 165.604 GPU-s。
相对 ElasticLocality，总差 2083.623 GPU-s，业务窗口贡献 2048.857，约 98.33%。
主要差距仍在业务期，不能先靠缩减收尾或免费预热消解。控制条件有重叠，样本
数不是时间长度，更不是可独立相加的“造成资源浪费比例”。

原规划进程已分离：旧/新完整规划事件 2859/2988，worker CPU 总量
631.339/623.641 s；父进程冻结序列化均值 10.038/8.970 ms，规划结果回收
146.898/41.181 ms。生成 RPC 响应回收 254.727/89.878 ms，通道等待仅
0.026/0.036 ms。不能把规划 worker 总 CPU 时间视为每请求阻塞，也不重复做
“把规划移出主线程”这个已经完成的改动。

## 下一条主线与文献核查

先复用 D458 实际准备、原生事务和请求阶段日志，关联**同一个 GPU/owner**
上的准备活动与 decode 区间，分别检查实际并发、控制事务和请求驱动加载。
同时保留剩余控制回收延迟。关联不是反事实效应；字段不足时明确缺口，仅在
必要时登记最小诊断，不先改变评价阈值、盲改并发或执行下一轮同键性能回放。

本轮重新核查 [vLLM 官方 CPU/异步执行分析](https://vllm.ai/blog/2024-09-05-perf-update)：
其证据说明 CPU 调度和输出处理可影响 GPU 执行，支持检查真实跨进程边界；
不能将其 H100 数字或旧版本改动直接套到我们的 vLLM 0.30.0 上。
也核查 [PEP 471](https://peps.python.org/pep-0471/) 与
[Python 3.12 的 scandir 说明](https://docs.python.org/3.12/library/os.html#os.scandir)：
在 POSIX 上获取完整 stat 仍需系统调用，DirEntry 会缓存结果。因此不因
“scandir 更快”就跳过必须的第二次 fresh-stat，或假定单纯换 API 会减少一半
确认开销。任何后续候选仍须当前代码/历史证据、等价性和实测，而非补丁堆叠。
