# D101：用同一库存的归属索引消除同步容量计算的重复扫描

2026-09-28。基础证据版本 `ae8a5caffaadadad6b45a9750b26cf1ccb9b3a3c`；
其运行实现与 D100 Full7 的 `6815bee` 相同。本次只有一个优化假设。

## 问题、历史与依据

D100 Full7 成功2445/4000，成功子集平均 native TTFT 0.389秒，但 service
TTFT 16.420秒、dispatch/admission等待812.435秒。这个差距是定位控制/准备
开销的线索，不能把成功子集当完整性能，也不能仅据此断言某函数是全部根因。

追踪 `17bb348` 的文件 owner 快照改动及当前调用路径，发现
`_plan_ieee_preparation_for_slot` 在异步控制线程中同步构造文件规划状态。
`_file_replacement_capacity_from_inventory` 对每个来源重新遍历整个文件库存，
对每个文件重新 stat 来源的父目录、创建并逐项比较祖先路径。检查的是同一份
库存，并没有获取更鲜的文件状态；重复次数随来源数×分配数增长。

参考 [Python asyncio 阻塞代码说明](https://docs.python.org/3.13/library/asyncio-dev.html)
以及 [vLLM 官方 CPU profiling 文档](https://docs.vllm.ai/en/latest/contributing/profiling/)，
先用 cProfile 定位计算，再修改数据表示，不先把共享状态盲目转移到线程池。
[vLLM 0.30 block pool 源码](https://raw.githubusercontent.com/vllm-project/vllm/v0.30.0/vllm/v1/core/block_pool.py)
把缓存查询索引与实体引用/释放条件分开；这里借鉴这种区分，不移植 KV 算法，
不声称索引本身是论文新贡献。

## 第一性原则：相同谓词，换遍历方向

一个库存 inode 只能贡献给同时满足以下条件的来源树：

1. 是普通文件，与来源父目录属于同一设备；
2. 没有库存之外的硬链接，没有尚待增长的预留字节；
3. 此 inode 的**全部**已知路径都在该来源树下。

旧方法为每个来源分别检查这组条件。新方法对每个 inode 一次性取所有路径的
祖先集合交集，再与同设备来源集合求交，累计其真实分配字节。父目录设备号在
本次 owner 锁内按父目录读取一次。空集合、嵌套路径和原有排序行为保留。

最终 `eligible` 条件仍为：可回收量非零、等于该已确认来源全部分配字节，且
不被计划、读引用或移动任务保护。跨来源/跨层硬链接不虚构可回收空间。
索引仅在本次函数调用存在，不跨 epoch 缓存，不发布 GPU-ready，不预约或释放
物理资源。执行阶段的重新检查完全保留。九个 IEEE 公式、需求窗口、背包目标、
admission、冻结配置、工作负载、deadline、所有权确认和远端交付方式均未改变。

## 定点剖析：真实保存的库存，明确重建的来源

复用 D100 清理前1199条分配记录（1064个文件 inode），按既有500-ID清单和
路径重建133个来源。原缓存已安全删除，所以 Path.stat 只返回原记录设备号；
保护集合为空。这里不是重放真实活跃 epoch，也未测文件系统 I/O、传输或 GPU。
没有生成任何权重、负载或第二套工件池。

| 同一元数据计算 | 原方法 | 索引方法 |
|---|---:|---:|
| 三次非 profiler 耗时（秒） | 5.917741 / 5.810550 / 5.857327 | 0.059045 / 0.051430 / 0.049904 |
| 每次目录设备查询 | 141512 | 2 |
| profiler 函数调用数 | 47086736 | 352815 |
| profiler 自身测得耗时（秒） | 23.185 | 0.176 |
| 输出全部行的 SHA | 两者完全相同 | 两者完全相同 |

输出 SHA `c0a48e9ecfbfde97167b92359e46a069f08361ad5331c068664d1aca4343085c`。
未加 profiler 的均值比109.65，仅表示这个函数在这个元数据样本上的缩减，
没有置信区间，不等于端到端加速109倍。profiler显著增大耗时，不能混入均值。

## 正确性与结论边界

新增三个检查已通过：设备/硬链接/预留/保护组合、100组随机元数据与旧谓词
逐行一致、目录查询次数不再随来源×inode增长。输入和 owner 状态不被修改。
既有完整 CPU 回归1186项通过（55.068秒），覆盖真实小文件的所有权、驱逐和
准备流程；系统解释器另有47项 OS 护栏检查通过（0.216秒）。合计1233项不同
检查，不把先前的3项子集重复计数。

本次接受的是语义等价的数据结构优化，不是“服务已合格”。只有完整回放才能
检查等待、取消、恢复频率及完成率是否改善；它们也可能暴露新的主要瓶颈。

路径，不加超时、不关保护、不重做 profile。结束后先清理、校验、表格，再决定
后续动作。7B、warm SLO/Resident、基线主比较、消融和敏感性仍未完成。
