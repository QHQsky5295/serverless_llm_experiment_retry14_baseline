# D936：3B W2 当前 PrimeLoRA 与已完成基线的同合同再接入

日期：2026-10-30  
目的：在 D935 通过服务可行性门槛后，重新核对已有 3B W2 基线，决定哪些结果
可以用于下一轮 PrimeLoRA 优化，哪些仍受资格限制。此文不重跑基线、不生成新
负载、不覆盖旧结果。

## 1. 共同输入和资格边界

D935 PrimeLoRA、ServerlessLLM D766、vLLM D656、S-LoRA D773、HydraServe D809
和 Loquetier D802 均使用既有 3B W2 工作负载、500-adapter 集合、固定长度贪心
生成契约和请求级目标长度；对应 trace、adapter map 和原生 token/时序审计均从
封存结果读取。D935 使用当前 PrimeLoRA 代码和已就绪的真实远端发布对象，其他
系统保留各自官方实现、适配和编译初态。

所有系统的 `n_correct`/独立 LoRA 数值正确性字段仍为未知或未通过资格。因此，
下表是完整请求、原生 token/adapter 绑定和共同 TTFT/TPOT 字段下的描述性观测；
不能把 token 数等于目标长度写成独立数值正确性证明，也不能把低资源占用直接
写成已经完成 G1 的“每个正确请求”结果。

## 3. 当前结果支持的判断

1. 在已知 W2 观测中，PrimeLoRA 的 U 最低，并且 3B W2 的 75% Resident 参考为
   12,083.064 GPU-s；D935 为 11,936.550 GPU-s，低于该参考约 1.21%。因此它是
   当前唯一同时满足共同服务门槛和该预算参考的已测点之一（严格的 G1 仍需独立
   正确性字段）。
2. PrimeLoRA 的联合 SLO 为 99.875%，高于 ServerlessLLM 的 98.125%，但 P95
   TTFT 为 2,302.041 ms，明显高于 ServerlessLLM 的 480.724 ms 和 vLLM 的
   441.635 ms。因而当前 PrimeLoRA 在“资源—服务可行性”上具有可用的 Pareto
   位置，却尚未在 W2 尾延迟上最优；不能把 CE 或较低 U 当作尾延迟优势。
3. vLLM 和 ServerlessLLM 的 U 均高于 75% Resident 参考，HydraServe 虽然 U
   较低但联合 SLO 为 0；因此不能用不满足共同服务要求的低 U 行替代预算内的
   服务质量比较。后续应同时报告预算可行域和未达标点，不能删掉后者。
4. D934 的 3B 失败由远端服务未启动造成，D935 是恢复服务后的唯一新执行键；
   不能把 D934 的失败归因于 PrimeLoRA 算法，也不能把 D935 与历史 D886 文档中
   不同联合口径的 93.750% 直接混排。D935/D886 口径冲突已在 D935 文档中封存。

## 4. ServerlessLLM 历史问题的处理

ServerlessLLM 历史 7B/3B 诊断已经定位出官方 round-robin 分配器在无 ready
实例或队列满时固定 1 秒轮询的问题；D72/D73/D74 保留为机制归因证据。当前
3B W2 主观测 D766 使用已审计的共享分词器和修复后路径，仍保留 ServerlessLLM
原生 RR、autoscaler、store loader 和队列语义，不把 ready-only 诊断包装成
PrimeLoRA 的收益。历史四分钟 dispatch 结果不能作为当前 D766 的直接 TTFT，
也不能未经生成契约说明与 D935 排名。

## 5. PrimeLoRA 下一轮优化假设

D935 请求级字段显示，P95 TTFT 的主要结构性来源不是固定输出合同：

- 511/4,000 请求在 dispatch 前观察到 `adapter_remote_cold_before_dispatch`；
  这些请求平均 TTFT 约 2,090 ms，P95 约 3,722 ms，而非 remote-cold 请求平均
 约 615 ms；
- 运行器记录的全体请求平均 LoRA I/O 为 257.342 ms；remote tier 请求包含真实
  读取、传输和本地物化，不能从 TTFT 中事后扣除；
- scale-up 影响请求的平均 TTFT 约 1,057 ms，P95 约 2,922 ms；runtime slot
  wait 的 P95 约 651 ms，dispatch/admission wait 的 P95 约 1,038 ms；
- 两次扩容发生在回放初期，实例初始化约 35 s；本轮没有 scale-down，因此不能
  把尾部简单归因为缩容抖动。

这形成一个可证伪假设：在不改变九个公式、请求到达和 GPU 预算的前提下，当前
3B Full 的 16-GiB NVMe 文件预算不足以覆盖 500-adapter W2 的实际工作集，导致
高频轮换时重复出现 remote cold；以观测到的 adapter 字节总量驱动的 NVMe
容量/驻留候选选择，若能减少 remote-cold 次数而不增加物理 GPU 生命周期时间，
应同时降低 P95 TTFT 并保持预算可行性。若验证显示增加文件驻留只把等待转移到
扩容前准备、或超过磁盘/内存安全包络，则该方向撤回，不继续堆叠缓存规则。

该假设不是结论，也不授权直接把 `nvme_capacity_mb` 改成有利常数。下一实验需
先从 D935 的实际 adapter 内容字节、请求级 miss/churn 和当前磁盘余量计算一个
可审计的候选容量，再以唯一新执行键完成小范围机制验证和完整回放；所有旧结果
保持不变。

## 6. 交接决定

- ServerlessLLM、vLLM、S-LoRA、HydraServe 和 Loquetier 的既有 3B W2 结果先复用，
  不因低 SLO 盲目重跑或为对手临时调参。
- 当前 PrimeLoRA 3B 进入下一轮有证据优化，目标是保持 D935 的预算内服务可行性，
  同时缩小 remote-cold/扩容尾延迟；优化后再按同一矩阵重新比较。
- 由于当前 PrimeLoRA 尚未在 P95 TTFT 上最优，本轮不绘制最终排名图；只保留该
  结果矩阵和阶段证据，待下一候选完成后统一作图。
