# D610：将实时 extent 核验纳入同一次文件观察

2026-10-17，待验证开发候选，不是性能采纳。完整 PLAN、冻结 V1 和单轮 V2
保持不变；D607 W2 联合94.05%、U15078.910657仍未满足 G1/G2。

## 假设与来源

D608 的剩余违约集中在本地准备阶段，但其跨度不能直接归因为某个函数。
进一步复用 D603 已保存的调用者摘要：末区段141次包含 `_file_inventory`
的主线程样本中，41次直接调用者为 `_settle_file_allocations`（39+1+1），
其余100次为 `inventory`。这是采样出现次数，不是耗时比例；该诊断早于
D606，但当前两个遍历的调用结构仍存在。

D153 已在没有 closed/unsettled writer 时省去前置扫描，并把来源与容量合并；
D457/D606 已减少路径对象构造。不能重复实施这些旧优化。D329 的反例禁止
以 owner/epoch 代替实时物理事实；D365 说明内容身份与物理分配不同。

新假设：需要 extent 核实时，让同一次库存遍历在首次见到该 inode 时完成
原有 closed-writer FIEMAP 检查，随后读取新的 stat，再执行完整第二遍变更
检测，可消除专为寻找这些 inode 而进行的前置全树遍历。
不改变公式、预算、保守预留、调度、采样周期、并发或任何服务配置。

## 原始资料与适用边界

- [vLLM CPU 开销分析](https://vllm.ai/blog/2024-09-05-perf-update)：减少同步
  Python 管理工作值得以本系统数据验证，不照搬其性能数字。
- [vLLM 0.30 block pool](https://raw.githubusercontent.com/vllm-project/vllm/v0.30.0/vllm/v1/core/block_pool.py)：
  其 BlockHashToBlockMap 明确通过表示设计减少内部对象管理成本；它管理的
  是自身原生 block，不能作为缓存外部文件系统动态状态的依据。
- [Linux FIEMAP](https://docs.kernel.org/filesystems/fiemap.html)：FIEMAP 调用间
  文件仍可能变化；SYNC 会触发同步。本候选保留无 SYNC 的现有 extent 判据，
  未初始化仍全额保留原 allocation envelope，不等待、不 fsync、不轮询。
- [PEP 471](https://peps.python.org/pep-0471/)：DirEntry 会缓存元数据；仍使用
  两遍显式实时 stat，不以 DirEntry 缓存满足第二遍检测。

按 research-lookup 作有界官方来源核查；Parallel 未认证，使用网页工具，
未安装依赖、配置新凭据或上传私有数据。

## 必须保持的合同

1. 同一 owner 锁、原文件/写入者生命周期；没有跨调用观察缓存或新 locator。
2. 只有 writer_closed 且未 settled 的已预留 inode 可作现有 extent 检查。
3. 修改分配上界前检查原 envelope；成功后重新绑定路径、inode、内容签名及
   新 envelope。全树第二遍仍在所有 extent 操作之后执行。
4. 保留硬链接计量、特殊文件拒绝、缺失/变化检测、未知来源拒绝、私有传输
   的容量收费、取消和原子发布。错误不能产生成功快照或 ready 状态。
5. 不减少内容 SHA 验证，也不改变 publication lock；本轮不叠加另一个候选。

## 验证与停止条件

复用既有微型发布和 extent 测试，核查 settled/unsettled/active-writer、
初始化成功/未完成、rename、第二遍变化与越界。比较父版本与候选的完整
预算/来源/footprint输出，忽略原有 capture timestamp；统计实际全树遍历。
已有小型组件入口作有界开销验证，不生成模型工件池或负载。
使用现有 CPU 回归环境及3/4GiB、swap0、CPU2,3,26,27；不重用 D606 的环境错误。
最多两轮有理由的最小验证，若语义不等价或没有可解释收益则归档，不开 GPU。
通过后备份，再按既定同配置、新执行键完成一次普通 W2；不重复 D607。
当前不声称任何端到端收益，不作图，完整7B/3B、dLoRA、A1–A5、S1–S13及
最终成本/审稿证据交付继续开放。

## CPU 资格与组件结果

16项聚焦测试及215/178/13项分模块回归全部通过，共422项；真实微型发布、
重命名、写入未完成的保守收费、已确认来源、取消及文件变化拒绝均在内。
辅助内存峰值516440064/1662357504B，high/max/OOM/kill/swap全部0。
不将这些CPU检查称为模型数值正确性或完整推理资格。

第一次组件比较在完整快照等价断言处失败，尚未开始计时，原操作数未落盘，
不猜测它的具体差异。第二次增加状态重置及逐字段记录：未初始化分配精确
一致，初始化场景的分配预算不同。检查发现 AST 提取的父版函数使用独立
globals，而测试仅替换候选所在模块的 FIEMAP；父版仍查询真实文件。
这是不同测试条件，不是候选性能结果。两次失败、脚本与实际关闭记录保留。

第三次只修正测试：两版绑定同一个 extent 查询函数并断言函数身份相同。
生产候选自16项聚焦检查开始未再改变。两个微型完整快照及分配账目完全一致；
再复用D557已关闭目录的999普通元数据文件/1003路径，受控设定一个inode的
分配状态，**不写目录、不复制工件、不声称测量了真实kernel转换耗时**。

全部组件调用如下（毫秒，三次交替；不是正式性能重复或置信区间）：

| 状态 | 父版三次 | 候选三次 |
|---|---|---|
| 已 settled | 10.238 / 9.634 / 9.804 | 9.882 / 10.440 / 9.508 |
| 尚未初始化 | 19.945 / 19.388 / 19.923 | 10.038 / 10.266 / 9.835 |
| 本次可完成 settlement | 18.796 / 18.363 / 20.081 | 9.497 / 9.288 / 9.799 |

未 settled 两种路径的全树观察从两次减为一次：普通路径stat由4次减为2次；
成功settle的那个路径额外进行一次绑定重查，为3次。已settled路径仍为每路径
2次。8组等价/调用次数断言通过，没有减少最终全树的第二遍检查。
组件均值约19.75→10.05ms、19.08→9.53ms；这不是TTFT改善约50%的证据。
已settled的小差异不作性能归因。所有调用值和失败保留，不筛选。

决定：CPU语义/组件资格通过，候选可进入新键的完整普通W2验证；尚未采纳
为最终性能版本，不宣布G1/G2达标。先备份，再检查新增日志空间及启动门槛。
