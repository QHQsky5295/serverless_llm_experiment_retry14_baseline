# D618：准备设备域与放置设备域一致性修正

本轮先封存D617失败（01c36f6），再修复已重现的实现缺陷。不改九公式、
SLO、三副本模型配置、输入或远端交付；不是新性能调参或已经达标的结果。

## 依据、假设与取舍

D617首次遇到GPU1尚在退役、同时新扩容需要空闲GPU3的时序。历史D469
（68aef59）把CPU准备域截成`available[:max_instances]`，放置却考虑全部
合法设备。D615/W2虽完成，未证明该交叠边界正确；不能借其结果否认故障。
D614已经明确ready+pending上限和物理持有不是同一量，退出期间的重叠要计费。

不变量为：所有可被放置器选择的TP=1物理设备，都有对应的固定UUID准备路径；
正在退出、pending或失败未归还的设备不可重用；CPU准备不等于GPU-ready。
可证伪假设：去除错误的副本数量切片后，同一重叠状态能够领取GPU3的现有
CPU准备进程，且不提前复用GPU1、不改控制器上限、不启动隐藏替代worker。

选择覆盖完整合法设备域，而不在运行中换UUID、捕获异常后重试或强制串行
等待全部退役。限制放置域为前三张卡虽然也可避免异常，但改变了已冻结四卡
资源环境的可用性；本轮没有性能或算法依据采用这一限制。
完整覆盖可多保留一个CPU前端，CPU/内存开销纳入共同服务包络；可能暂时
持有四张GPU（两ready、一启动、一退出），照实计入U，不称三卡物理硬上限。
没有新自由参数、场景分支或未来负载信息。TP=1资格仍由原入口强制验证。

## 验证与主线

先在未修改生产代码上运行新增集成测试，保留失败见证，再作单处语义修正。
覆盖不同max值、完整设备域、非连续ID、draining与pending/failed所有权、
资格前置及禁用策略。复用原生命周期、激活许可、真实归还顺序和控制器测试。
CPU fixture不冒充原生CUDA正确性或性能。原生机制先按下面的D611内容证据
复用，三副本上限与退役交叠的集成资格由新版本完整W1核验一次；不另造较短、
较易负载冒充性能验证。完整W2/W0同工作点按影响核查，不将旧源码W2拼成新主表。

失败、额外CPU准备量、瞬态物理占用和未用准备进程都保留。新性能启动前先
核查并恢复磁盘150GiB门槛；当前无GPU运行。完整3B/dLoRA/A1–A5/S1–S13/
成本与审稿证据不删减；在目标未达前不画图。

## 实际检查结果与证据复用

- 首次测试启动被150GiB磁盘门槛拒绝，未执行测试。保留该门槛回执；复用
  原有压缩器对D617两份已封存日志进行两次解压SHA核验，回收224239616 B。
  14项归档测试通过，失败身份不变，原证据以gzip及恢复映射保留。
- 原生产版本运行12项factory测试：四个设备域subtest失败、一项重叠claim
  错误，与D617因果见证一致。未修改失败日志或删除不通过测试。
- 单处生产修正后，60项针对性测试和464项原有相关回归全部通过；无跳过、
  无high/max/OOM/swap事件。回归内存峰值1929834496 B。
- AST比较确认全脚本仅一处语义变化：移除设备列表的副本数切片。CPU前端、
  原放置器、物理分配/归还和autoscaler均未修改，配置与九公式不变。
- 对已封存D611原生完整运行流式核查：准备域[0,1,2,3]、四个真实UUID、
  五个激活前端全部退出；每个准备记录为CPU-only、engine_ready=false。
  D611生产源SHA与修正前一致。复用的是“四设备固定UUID准备/激活/退出”
  机制证据，不复用其max=4性能来宣称新max=3达标。
