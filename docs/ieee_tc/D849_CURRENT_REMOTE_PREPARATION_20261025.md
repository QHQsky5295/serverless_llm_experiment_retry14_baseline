## 4. 有界的下一项依赖核查，而非直接上生产补丁

唯一后续问题：**在文件已完整校验和确认发布、真实读租约保护成立之后，
是否仍必须等私有workspace退役和线程返回，才能通知消费者？**

这一步先核对依赖，不重做D827清理微测、不新GPU profiling、不改解码器。
如果可行，候选只改变有所有权的就绪交接点，全部清理仍在原任务/服务预算
内执行；临时归档和实际物理占用在真实释放前继续收费，原pressure保留到
IO及清理确实join，成功请求仍等完整结算，任何晚到错误仍传播为失败。
文件就绪不能标成GPU就绪；原生单线程加载/准入继续检查当前状态。

必须先检查的具体阻碍：transfer_workspace清理与消费者source_snapshot/
acquire_confirmed/demand_witness共享owner锁。仅在rename后发callback可能
只是把等待移到消费者，甚至阻塞事件循环，不能作为优化实现。需要证明
同一次确认发布可安全交接实际读租约，覆盖取消、重复订阅、失败、驱逐和
epoch变化；做不到就拒绝，不用陈旧容量、未知→ready或后台遗失任务绕过。
不减少最终内容SHA、不改变可观察状态定义，不提前免计cleanup资源。

与历史的区别：D827否决“单独优化/删除清理即可解决差距”；本问题不减少
清理工作，而检查消费者是否真正依赖该工作完成。D831当时限定IO完整join
后交接，未证明更早的租约交接；当前505条精确发布—通知边界给出了待检验
范围。D628移SHA锁、D733单次to_thread、D844批量stat和D845已实施的身份
查询不重做。D329只靠owner epoch缓存物理事实的反例继续有效。
