## 原因、推导与范围

D1067 的 2139 次完整规划中，900 次最终无文件/GPU目标，对应 39.03%
规划 CPU 时间。这不是提前可判定比例，也不是请求时延可直接扣除的比例。
本次唯一假设：其中一部分满足“当前正需求全部已有本副本确认 GPU 来源”，
可在相同收到的状态上证明没有正收益，避免构造完整可执行计划和空注册。
实际触发比例未知；不能把 900 当作预期节省次数。

证明：若 h_a>0，则最快确认来源已是 GPU，没有更快目标层；若 h_a=0，
Eq.(4) 的所有准备收益均为零。Eq.(6–7) 的插入/替换因而没有正收益候选。
不改变选择规则、预算、需求窗口、成本公式、路由或物理准入，也不按场景调参。

实现放在既有 CPU 规划 worker 中，在全量 native/file 身份、图、预算和所有
adapter 来源检查之后，完整 source-view JSON 冻结之前。仍读取当前真实
native 图、当前共享文件观察，仍在原入口冻结需求；没有额外 RPC、陈旧结果
复用、TTL、阈值或未来请求。节省范围不包括前面的文件观察/native RPC。

只由稳态 residency 调用启用。Handoff、pre-init、显式诊断及未满足条件的
规划保持完整路径。零需求仍由 D1066 的控制轮判断处理，本候选要求非零需求。
不取消在途准备，取消/失败仍按既有 worker join 与 owner 规则处理。

无收益返回独立的不可执行证明对象，不伪造 plan SHA、已验证执行计划或容量
预留。保留需求、native/file owner、epoch、原始采样时间、正需求 GPU 身份
与确认时间、witness SHA。仍发布同一已验证 native 来源，并执行既有当前
engine/owner 发布检查。下一个控制轮重新观察，不缓存本证明。
