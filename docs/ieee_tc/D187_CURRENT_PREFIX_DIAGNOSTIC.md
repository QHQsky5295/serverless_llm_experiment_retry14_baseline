把瓶颈归因于某个RPC。D162的CPU栈观察早于多项实现变更，不能直接
当作当前热点。因此先在当前版本观察调用链，不继续猜测性优化。

## 解释与下一步

观察支持继续检查**当前控制路径的同步状态构造**，并不证明某一函数
独自造成全部2.388秒的引擎前等待：

1. controller的95次preparation_snapshot观察中，93次由
   `_plan_ieee_preparation_for_slot`直接调用，2次来自初始化路径。
   当前源码在协程中同步取得文件owner快照；其内部包含实盘清单、来源
   验证及整个静态工件集合的目标描述构造。它们与请求接收/路由共用
   控制器主线程，是需要优先审查的结构性干扰路径。
2. GPU core中仍可见HOST物理清单遍历；它还服务加载前预算核查，不能
   因为“查询昂贵”就删除全局占用检查，或拿单adapter占用替代全局预算。
3. RPC解码与执行描述复制依然存在，但D172/D173已没有确认净收益；
   不重复旧解码方案，也不凭采样再做一次相同Full寻找更好的数值。

下一个有界问题是：在保留fresh owner/epoch、实际空间、失效、并发预留
和执行重检查的前提下，能否把不可变工件描述与动态物理状态分开，减少
主请求事件循环中的重复构造？先对照历史D151/D153/D159/D163及官方
异步控制实现，做依赖与不变量研究；尚未接受或实现新优化。不使用TTL
假装confirmed，不放松预算、不改公式/配置/SLO，也不立即重跑Full。

当前结论仅是“已获得当前版本定位证据”，不是“瓶颈已完全证明”或
“优化已达标”。详细观察不进入正式性能排名。7B全部未决验收继续保留。
