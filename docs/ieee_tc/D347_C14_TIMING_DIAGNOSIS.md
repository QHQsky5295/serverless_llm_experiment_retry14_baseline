# D347：C14 工作点退化的保留数据诊断

2026-10-08；7B 主线，离线分析，不重跑 GPU，不修改服务实现或评价协议。
前置完整结果 D346 已备份为 `33def6fbbdc0c5f2e0c9173f7a0f910514ff960b`。

## 要回答的问题

D346 的物理 GPU 时间比 D336 少7.95%，但暂定共同阈值下的时间条件联合
达成由95.925%降至91.375%，TPOT未通过数80→241。不能接受为达标节省。
本诊断检验退化与并发服务、扩容启动和加载重叠的对应关系，不从相关性推出
因果，不继续无依据提高并发或重复完整运行。

- 固定八个500请求阶段，保留每阶段全部请求及同一共同阈值；没有挑尾部
  后重新计算主成绩。已测同输入、原生数量和物理资源结果原样保留。
- 复用 D304–D306 的 decode/加载/调度区间方法及 D319 的配对共同到达集合。
  D336 已有 D337 完整区间投影，按旧 manifest/SHA 直接复用，避免再次生成。
- `mean_other_native_requests` 是同副本其他请求 dispatch→last-token 区间
  在本请求 decode 期间的平均重叠数，不是每次 GPU kernel 的 batch size。
- interval overlap 不是测得的 kernel 停顿时间，不能从 TPOT/E2E 中减去。
  单次开发运行不提供 CI、显著性或正式 G1/G2 资格。

## 历史与原始资料

D343 同一 C14 runtime 的8/14请求短波：吞吐约增加17.90%，共同8请求 TPOT
约增加43.32%。它预示吞吐/延迟取舍，但不是完整回放比较。D336 将历史容量
规则用于 C8，D346 将同规则用于 C14：queue_upper=C、active_upper=(C−1)/C，
active_lower=active_upper×m/(m+1)。物理容量和延迟可接受的工作点并非同义。

核查代码历史：`00199eb` 中 D88 初始规则、`0175a04` 的容量目标提取；
现有 `IEEEReplicaController.evaluate` 以实际在途/ready_capacity 的饱和率、
queue 和 TTFT 最大比率决策，低负载三个条件持续满足才回收。当前不修改该
控制律、九个公式、共同阈值或参考 batch8。

- [vLLM 0.30 优化文档](https://raw.githubusercontent.com/vllm-project/vllm/v0.30.0/docs/configuration/optimization.md)：
  并发、token预算、KV和prefill/decode存在不同取舍，不能将可容纳请求数等同
  满足尾延迟的吞吐；不照搬数据中心 GPU 的默认大 batch。
- [vLLM 同版调度实现](https://raw.githubusercontent.com/vllm-project/vllm/v0.30.0/vllm/v1/core/sched/scheduler.py)：
  序列、token、KV与 LoRA 约束是不同限制。只改外层排队并不增加原生吞吐。
- [Ray 2.59 autoscaling 文档](https://raw.githubusercontent.com/ray-project/ray/ray-2.59.0/doc/source/serve/advanced-guides/advanced-autoscaling.md)：
  目标在途数与最大在途数分别定义，目标应结合端到端延迟；最大值过高可能
  让扩容就绪前请求集中于旧副本。不采用其经验百分比作为本系统常数。
- [Knative concurrency 文档](https://knative.dev/docs/serving/autoscaling/concurrency/)：
  软目标与硬上限不同。该原则只支持下一假设方向，不证明 Prime 当前根因。

## 未就绪扩容必须保留

analysis1 的95项CPU测试通过，随后旧分析器因一个实际记录缺少
`engine_ready_at` 停止。原失败日志/代码版本归档保留；这不是 D346 请求失败。

该记录为自然扩容 `ieee-activation-108e10506aec4cfc82faf4401273da79`，
状态 cancelled，未发布 ready；trigger=950435.854732591，业务起点
946477.560737699，即业务后3958.293994892s。preparation_terminal_at
950442.988157501 只是文件准备任务结束，不等于引擎ready或GPU释放。

源码取消路径会等待仍由其拥有的 startup 任务并释放资源；不将 preparation
时间冒充启动结束。当前离线分析把有实际 ready 的闭合启动区间与未就绪
记录分开，要求全部服务请求只能绑定实际 ready epoch。未就绪原记录完整
输出，不伪造终点；其物理 GPU 占用仍已计入 D346 总 U。

因此启动重叠分组只描述已测 trigger→ready 区间，不宣称覆盖全部启动暴露。
取消记录不从工作量/资源统计删除；所有4000请求仍进入整体和八阶段统计。
若某请求绑定未ready副本，或者缺状态无法解释，则分析拒绝通过。

新增边界测试验证 cancelled 不变成 ready、错误时钟/缺状态/伪造时间被拒绝、
4000请求完整性、阶段分母、Type-1统计以及不覆盖已有目录。analysis2 与
analysis1 使用不同输出目录；没有 GPU 或共同阈值重测。

主线仍为7B优化，然后3B、暂停基线、M1/M2、消融和敏感性。数值正确性、
共同最终参考和正式 G1/G2 均 OPEN；未达标前不画图。

其他竞争解释也有证据，不能省略：

- 与peer prefill区间重叠的请求数2288→2763，其中TPOT未通过76→233；
  无此重叠的对应数4→8。prefill区间不是isolated kernel stall。
- 与实际加载区间重叠的请求数1348→1718，其中TPOT未通过54→188；
  无此重叠的对应数26→53。加载区间与prefill/启动/并发有交集，不能相加
  充当各自“解释了多少退化”。也不能以减少加载次数预先保证改善。

**当前支持的判断：C14工作点让更多请求同时占用旧副本，在更频繁的扩缩容
和prefill/加载重叠下出现更差的TPOT；物理slot数量不能直接充当性能容量。**
尚不能唯一归因为软目标、kernel batch、prefill还是加载。不得将相关分组
用于推造反事实 TTFT 或GPU节省。

下一项只复用 D343/D344 的 C14 已测请求/长度/服务曲线，核查能否推导
延迟约束下的软目标，而让物理C14与IEEE控制算式保持不变。需要先验证
校准样本是否覆盖实际短输出和并发范围；不足就明确边界，不填造中间档。
不重开C15/C14容量扫描，不改共同warm batch8，不直接把C8配置叫最优，
不同时改prefill预算/加载策略。先形成一个有数据来源、可证伪的开发候选，
再最小验证及完整回放；本诊断不是已完成该优化。
