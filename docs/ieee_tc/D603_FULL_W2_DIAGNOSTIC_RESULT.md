## 能支持与不能支持的解释

1. 后段增长同时出现在到达接收和完成回传，而原生队列/prefill均值没有同样
   增长。结合当前controller采样，优先检查同步控制/状态维护，比直接将
   整体增长归因于GPU计算或远端链路更有依据；仍不是独占原因的因果证明。
2. `_local_file_inventory`在四窗最近项目帧中分别出现38/534、52/403、
   63/376、141/601次。最后一窗包含该函数的142个样本中，130次直接调用者
   是`_file_inventory`，10次是`_source_observation`，2次是`acquire`。
   这提供具体路径和调用位置，不是该函数消耗了23.6% CPU或请求延迟的证明。
3. 当前源码`residency_manager.py`的该函数确实遍历受管roots，逐路径lstat，
   构造inode/path清单，再进行第二次lstat核验；这些操作在owner保护下执行。
   本轮没有测得每次完整遍历的耗时或文件数曲线，不能仅由栈认定复杂度增长
   已量化，也不能据此删除新鲜性、变更检测、预留或硬链接容量核验。
4. D457已优化单次新鲜视图中的路径投影和祖先对象构造，但明确没有改变
   两次lstat或跨调用遍历。当前证据不是“旧优化丢失”，不能重复宣称同一改动
   为新贡献。D329过期状态捷径与D529元数据候选的反证继续有效。

帧计数包含等待，inclusive计数重叠；GIL可能隐藏忙区间，C/CUDA内部不可见。
没有无观察器A/A，不能声称诊断零扰动或用本轮与旧普通运行之差定量归因。
