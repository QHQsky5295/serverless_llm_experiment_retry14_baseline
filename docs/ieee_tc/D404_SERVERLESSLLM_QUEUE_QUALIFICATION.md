## 2. 假设检验：修复的是正确性，不是置换算法

D403 只把 storage-aware scheduler 的旧下标删除换为待分配申请身份删除，
source SHA 为 `7f42b0cce82f970392b3d484767a13563fb2d29f6c6e870aa8f29b86fb972b91`。
本轮实际 actor 读回与此一致，位于规定服务资源域、使用规定 CPU 集合。
回放结束时 running=true、loop_done=false、loop_exception=null，待分配队列
total=done=0；四个不同 GPU 上的 backend-ready 原始回执与请求观测吻合。
因此，本次受影响扩容路径通过，不能再把 D402 缺第四实例当作基线正常表现。

原 D402 为三后端、平均 TTFT 138.039 秒；本轮为四后端、82.941 秒。
请求合同逐项相同，但启动/分配事件的实际时序不同（到达前持卡时间也不同），
而且每个版本仅一次短前缀。只报告这些观察，**不把全部延迟变化因果归给队列
修复，不宣称统计显著性，不与 PrimeLoRA 的 4,000 请求结果计算提升比例**。
真正证据是原错误的确定性 CPU 复现、最小修复边界，以及 live 四后端/循环存活。

仍存在 82.333 秒路由等待；成功运行不能代替共同 SLO 可行性或配置最优。
target=2、max_num_seqs=4 仍是机械诊断点。下一步须核查启动积压及原生公开
容量配置，不能将未合理配置的点直接放入最终比较，也不继续扩写无新假设的
局部修补。评价仍按冻结 V1＋单轮 V2，CE 不决定主排名。
