# D356：控制交错策略的受影响 profile 重测

D355 的 Full100 入口在实际模型初始化前拒绝了旧 profile：新增
`ieee_control_interleave` 会改变 ready 后控制与模型推进的先后顺序，
不能从精确配置身份中删除它以强行复用旧时延。原失败、零终态、零观察
持卡时间和完整清理证据保留；这不是低成本性能结果。候选仍只有 D355
这一条主线，不新增容量或扩缩容参数扫描。

按照 D344 已完成的测量方法，复用原请求、静态工件及五种真实来源，
包括已知短输出/高接纳计数的补充案例，共 125 waves、1569 次调用，
其中 24 次保留的预热、1545 次测量。实际 admission 决定覆盖情况，
不按预计 wave 大小填值。旧案例只是测量设计，不转移任何旧时延。
只使用既有 collector、preparer/exporter 和资源限制；不生成新 trace、
新权重或整池副本。新目录与 D344、D355 隔离。

唯一可复用的统计是同固定输出合同下已经完成的原生输出长度。
新增明确的 length-only transfer 身份，保留候选的完整配置与新 SHA；
验证源原生计数、prompt/target、后端、输入和声明差异。既有 C8→C14
容量差异及本次交错策略均明确记录，所有其他差异拒绝。旧 timing
loader 不修改，不能加载旧 service/preparation profile。

新 Full 继续使用 D353 的 C14/软目标8、初始化分组、EWMA、存储预算、
生成及共同60秒通知。只换候选执行策略及该策略下重新测得的初始化。
因此最终与 D353 的对照包含合法 profile 刷新，不能声称完全排除了
初始化测量变异；控制触发和直接 TTFT/TPOT 仍需完整结果验证。

依据为 D354 实测输入轮次及
[vLLM 0.30 原生核心循环](https://raw.githubusercontent.com/vllm-project/vllm/v0.30.0/vllm/v1/engine/core.py)：
输入处理与模型步骤交替执行的边界会影响服务时间。本次重测不改变
论文九式、冻结 V1、D170 暂定开发阈值或正式 warm/Resident 定义。

验收顺序：CPU 合同检查 → 单卡真实原生 source 测量 → GPU/远端释放
与原生输出、来源、200服务类/24准备类覆盖检查 → 合法 profile 导出
→ 新独立 Full100 → 原4000 W0。若覆盖不足，只补实际缺项；若实际
机制/正确性失败，保留失败并诊断，不循环盲跑。数值正确性、正式
G1/G2、3B 和暂停的 baseline 工作仍未完成。优化期不作图。

准备阶段127项CPU回归通过，原案例、配置、长度初始化及正式控制绑定
核验通过；两个严格 timing loader 保持原样。此阶段没有GPU测量，
后续实测仍需确认交错机制触发、真实类别覆盖和释放。
