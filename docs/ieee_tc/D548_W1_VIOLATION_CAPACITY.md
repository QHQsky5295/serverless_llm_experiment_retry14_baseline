## 4. 一个明确的下一项假设，而不是继续拆分同一日志

已核对当前 `scripts/run_all_experiments.py`：

1. 主入口先 `await runner.preload()`。
2. IEEE preload等待 `_start_ieee_initial_deployment()`；该函数等待首个initial
   activation完成后才返回。外置到达记录仍继续，不平移业务原点。
3. 周期性 `_evaluate_ieee_live_control` 在后续连续回放路径中执行。本轮首个
   控制事件在initial ready之后，与该启动依赖一致。
4. 纯 `IEEEReplicaControl.evaluate` 本身允许 ready=0/capacity=0，queue压力
   不要求已有TTFT样本；缺TTFT不会支持缩容。初始任务已纳入pending集合。

IEEE稿件§3.1要求排队请求形成扩容压力、每控制周期按三项max-score判断，
没有规定必须等第一个引擎ready才开始观察已到达请求。因此下一项可证伪假设是：
**初始runtime等待不应阻塞同一部署内的已到达队列控制；保持原公式、上限和
采样周期，让在线队列在initial仍pending时驱动合法扩容，可能更早提供容量。**

这尚未实施、尚无收益证明，也不能解释第二阶段与后续全部违约。先用既有
initial lifecycle测试验证真实到达与控制任务的所有权：不读未来trace、不
新增固定副本数、不把pending作为ready、不双计初始任务、失败/取消全部可收尾，
首次ready身份明确，且不在 `run()` 重置已产生的控制/接纳状态。若原调用图
无法满足这些条件，则不采用该路径；禁止绕过资格直接启动大回放。

该候选只解开控制任务与引擎初始化的串行依赖，不移植其他系统算法，也不改
九式/服务阈值/cooldown/生成/资源计量。后续最小原生验证和完整新版本评价
均需独立新键；同模型跨W0/W1/W2规律一致，所有旧失败保留。

官方来源核查（2026-10-15）：

- [Llumnix OSDI 2024，§4.3–4.4、§6.5](https://www.usenix.org/system/files/osdi24-sun-biao.pdf)
  使用在线负载协调调度与扩缩容，强调新实例利用与回收效率。其KV迁移机制和
  freeness策略不同，本次不移植，也不能由该论文证明本候选有效。
- [vLLM 0.30.0 scheduler配置源码](https://raw.githubusercontent.com/vllm-project/vllm/v0.30.0/vllm/config/scheduler.py)
  的async scheduling旨在减少执行空隙；本机已显式使用原生异步scheduler，
  不能把“开启异步调度”再次包装成新优化。
- [vLLM 0.30.0优化文档](https://docs.vllm.ai/en/v0.30.0/configuration/optimization/)
  将批量、KV空间、prefill/decode权衡分开。当前证据不支持把增大batch/token
  预算当作无需验证的解法。D386加激进queue触发的退化也不重做参数扫描。
