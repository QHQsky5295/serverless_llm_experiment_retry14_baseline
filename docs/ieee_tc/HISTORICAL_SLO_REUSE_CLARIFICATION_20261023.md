## 2. 为什么曾经报告 3B 为 99.875%

D703 旧 `audit.json` 的 3995/4000=99.875% 来自运行时
`scenario["slo_attainment"]`，实际仅为开发条件 `TTFT <= 5000 ms`。
旧分析器将其误写为 `joint_slo_fraction_observed`，没有检查 TPOT，也没有
使用 D648 已冻结的按输入长度分组阈值。此前“3B 联合 SLO 已达标”的汇报
因此错误；用户记忆有明确的历史记录来源，不能归咎于用户记错。

冻结共同规则并非事后提高：D648 在 2026-10-17 已冻结，早于 D703。
prompt 长度不超过 506 的 TTFT/TPOT 阈值为
1466.050801101725/29.92187236665917 ms；更长请求为
2539.648668190845/36.21551519318005 ms。引用 manifest 的完整精度，
不使用显示值舍入、两个边际比例的平均或旧 5 秒比例替代联合事件。

D714 在 2026-10-22 已复用 D703 原请求离线重算：

- 共同 TTFT：3851/4000 = 96.275%。
- 共同 TPOT：3884/4000 = 97.100%。
- 同时满足：3744/4000 = 93.600%。
- 违约构成：仅 TTFT 140，仅 TPOT 107，两者均超限 9。
- 原生时钟重算 TTFT/TPOT/E2E 与保存值的最大误差均为 0 ms。

这不是系统从真实的 99.875% 退化到 93.600%，而是纠正了指标标签。
D703 本身没有为这项统计更正重跑；旧错误回执与新更正均保留。
本次只回读小型封存产物及原统计代码，不在 D752 性能测量中重读/哈希
大日志或重复执行 D714。既有来源绑定：
