# D600：局部确认变快，没有转化为完整 W2 目标改善

2026-10-17。只复用已封存 D554/D598，未运行新推理、改变服务、调参或生成
负载。沿用 D594 的请求阶段、双端 transfer、压力确认分析及原物理积分函数。
两个版本各4000请求，仍是已知回放的单轮开发观测；无运行间 CI、独立数值
正确性证明或严格因果效应。冻结 V1/单轮 V2、九公式和完整实验范围不变。

## 1. 完整目标与局部效果分开

| 指标 | D554 原串行确认 | D598 并行确认 |
|---|---:|---:|
| 联合 SLO | 3582/4000，89.55% | 3562/4000，89.05% |
| 平均 TTFT（ms） | 1757.588 | 1809.513 |
| P95 TTFT（ms） | 5827.475 | 5644.557 |
| 生命周期 GPU-s | 14641.259 | 15161.688 |
| 共同 W2 GPU-s 预算 | 12086.669 | 12086.669 |

局部：严格关联到自有远程交付且最终实际调用 native load 的请求分别490/494条。
准备包络均值从4246.488降至3827.021ms（−419.468ms），其中开始确认
493.998→337.145ms，结束确认758.819→591.267ms，合计−324.405ms。
最终 native load 51.001→50.831ms，基本未变。两组是执行中实际形成的条件
子集，不是相同样本的随机干预。RPC并行span相互重叠，累计RPC时间不能
与屏障墙钟时间相加，也不能从最终TTFT中事后减去。

全体4000请求：互斥阶段的平均变化为到达→释放+51.372ms、释放→许可申请
+16.365ms、runtime slot等待+33.286ms，admission→engine dispatch
−43.098ms。总体service TTFT下降49.101ms，而前置queue增加101.026ms。
因此局部准备改善不足以抵消整体等待；不以P95小幅降低宣布G1/G2成功。

## 2. 不是所有命中层级同时受益

| 实际选中 tier | D554请求数 / 联合违约数 | D598请求数 / 联合违约数 |
|---|---:|---:|
| GPU | 2473 / 46 | 2495 / 68 |
| HOST | 169 / 11 | 162 / 19 |
| NVMe | 842 / 48 | 829 / 59 |
| remote | 516 / 313 | 514 / 292 |

远程组少21次违约，其他组多41次，净多20次。tier由各次运行的真实路由决定，
不能把上述组当作完全匹配的因果样本。按请求ID、adapter、arrival和source
index匹配全部4000条后，159条由达标转为违约，139条由违约转为达标；
3186条保持同tier，其中102/105条分别发生上述转变；814条改变tier，57/34条
分别转变。它说明闭环状态与选择不同，不证明改变tier本身造成退化。

四个连续1000请求的联合达标数：D554为966/920/850/846，D598为973/933/
838/818。后段到达→释放均值分别591.617/712.296ms。不能把前段的改善
当作完整工作负载收益，也不能仅凭时序趋势断言某个CPU函数是原因。

## 3. GPU占用增加发生在业务期间，不是启动次数或清理

| 互斥 GPU-s 窗口 | D554 | D598 | D598−D554 |
|---|---:|---:|---:|
| 到达前 | 34.077 | 34.855 | +0.777 |
| 到达窗口 | 14547.356 | 15075.985 | +528.629 |
| drain | 14.990 | 9.743 | −5.247 |
| 清理 | 44.835 | 41.105 | −3.730 |
| 总计 | 14641.259 | 15161.688 | +520.429 |

共同到达窗口3963.909秒。四卡同时持有从3078.022秒升至3601.482秒；
三卡持有从526.752秒降至5.755秒。D554共8个实际ready epoch（1初始、
7自然扩容），D598只有4个（1初始、3自然扩容），但D598更早持续持有四卡。
所以“启动次数少”并不等于生命周期GPU占用低。每个epoch的第一条实际
dispatch已关联，未用initial替代natural或改写first-service定义。

这些由实际物理分配区间并集严格恢复；不能把成本增加归因于收尾、网络打包
或GPU利用率。为什么在线控制选择不同尚需针对控制与等待路径核查；不得
仅凭两条闭环轨迹断言并行确认是全部变化的唯一原因。

## 4. 方向决定与停止条件

D595的CPU/原生安全合同成立，局部等待改善也有观测支持，但D598未满足
约定95%联合SLO及75%参考预算，并且较D554整体目标退化。本候选不提升为
主配置，不继续推广W0/W1，不重复相同W2寻优。保留全部代码、测试、诊断
和失败历史；下一步先撤销这一孤立候选回到既有语义，再定位全局等待/
控制反馈瓶颈，不能在未接受候选上叠加另一项改动。

下一假设须从真实可观测量出发。重点核查等待增长与在线控制、状态采集、
CPU执行的对应关系，避免重复D514/D516、D520–D529已否决的捷径。
本次只读核查发现`_current_coord_metrics()`的全历史deepcopy调用位于
运行结束聚合/关闭处，不能凭其代码看起来昂贵，就认定它是在线请求变慢
的原因。新改动仍须历史/源码/原始资料→可证伪假设→最小测试→完整新键。

已重新核对[官方vLLM 0.30多进程执行器](https://raw.githubusercontent.com/vllm-project/vllm/v0.30.0/vllm/v1/executor/multiproc_executor.py)
和[Python 3.12任务语义](https://docs.python.org/3.12/library/asyncio-task.html)：
分发/确认可以并行且必须保留取消后的所有权，但它们没有承诺本系统的完整
资源/SLO收益。不能以通用并发实践替代本次负面完整结果。
