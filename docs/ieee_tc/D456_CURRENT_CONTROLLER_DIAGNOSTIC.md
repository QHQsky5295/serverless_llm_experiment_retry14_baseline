# D456：当前 7B 控制延迟的一次函数级诊断

2026-10-12。预登记：不是新性能候选，不改变论文公式、控制阈值或基线。

## 问题与历史证据

D454 同合同 W0 比较不能支持 PrimeLoRA 最优；其物理 GPU 时间高于
ElasticLocality，联合 SLO 较高但尾延迟也较高。D455 对保留的 8,000 条
请求离线分解，发现 PrimeLoRA 的到达接收和完成通知延迟随运行增长，
而 native entry 到首 token 的均值差仅约 12.6 ms。不能由此推断具体函数
的因果贡献，也不从用户时延中扣除这些等待。

D455 已排除“Full 全局 permit 长等待”和“实时导出整个协调器历史”
作为当前已证实原因。纯规划已经在独立进程执行；D93/D188/D193–D204
已改过静态描述、快照与表示，D329 不支持用 epoch/TTL 代替实际状态。
D328 的 Python 栈来自旧 C8 配置，不能直接当作当前 D371 的函数归因。

本轮可证伪假设：当前主控制循环中的同步状态构建/读取或消息处理，
仍占据可观测的活跃路径，延迟及时接收请求及 native 完成事件。
同时保留反证：若主要样本位于等待或其他路径，不先修改文件库存。

  同配置寻找更好数字，也不将 1,000 请求线性外推 4,000 请求。

## 原始依据与解释限制

已重新核对 [Python 3.12 frame API](https://docs.python.org/3.12/library/sys.html#sys._current_frames)：
它提供观察瞬间线程帧，读取时活动可能已改变。栈计数不是 CPU 时间比例，
GIL 延迟会漏采，不能把样本频率直接换算成 TTFT 的因果份额。
[vLLM 官方 CPU/调度分析](https://vllm.ai/blog/2024-09-05-perf-update)
表明 CPU 调度与输出路径值得分开测量；这里借鉴诊断方法，不借用其
硬件、版本或加速比例，也不移植会改变论文语义的策略。

前缀可能不足以重现完整回放后段的增长。若未定位，明确其证据不足；
先结合既有全量阶段记录，不盲目重复短测试。下一步只允许一个证据支持、
公式兼容的新候选，经过最小验证和普通完整回放评价净收益。
