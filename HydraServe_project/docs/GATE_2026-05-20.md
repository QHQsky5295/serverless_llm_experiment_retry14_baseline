# HydraServe Gate: 2026-05-20

## Source

- Upstream repository: `https://github.com/LLMServe/hydraserve`
- Upstream commit: `8ae605de354ccfa2e9095514cdb4a9e9c56aa56b`
- Paper: `HydraServe: Minimizing Cold Start Latency for Serverless LLM Serving
  in Public Clouds`, NSDI 2026.
- Local source: `vendor_new_baselines/HydraServe_main_20260520`

The upstream README describes HydraServe as a serverless LLM serving system
based on a modified vLLM 0.4.2. Its official run path starts storage-server
and inference endpoints through Kubernetes and requires at least one GPU server
plus at least one remote-storage server.

## Local Checks

- Created isolated control-plane environment `hydraserve_py_20260520`.
- Installed the upstream control dependencies with user-site disabled for gate
  execution.
- Imported the HydraServe control modules:
  `main`, `scheduler`, `resource_manager`, `engine`, `ModelInfo`, and
  `ImageInfo`.
- Verified the upstream embedded vLLM 0.4.2 source still parses static LoRA
  arguments such as `--enable-lora` and `--lora-modules`.

## Blockers

Full HydraServe is not runnable from the current user account:

- Docker daemon access is denied, so the official Docker image build path
  cannot be used.
- `/usr/local/bin/kubectl` and `/usr/local/bin/helm` are root-only.
- No usable kubeconfig is present; the official `src/main.py` and
  `src/start_storage_server.py` entry points fail before launching services.
- `kind` and `minikube` are absent, and passwordless sudo is unavailable.

These are platform/runtime blockers rather than simple missing Python libraries.

## LoRA Workload Audit

HydraServe's embedded vLLM source retains LoRA classes and static
`--lora-modules` support. However, the K8s worker app used by HydraServe does
not wire LoRA arguments into `AsyncEngineArgs`, and the scheduler path
`Request -> Instance -> ChatEngine` sends a fixed base model name to the worker
instead of preserving per-request adapter identity.

Therefore, replaying PrimeLoRA's closed LoRA workload would require changing
HydraServe's scheduler/request semantics, not merely adapting model paths or
installing local libraries. Merging each adapter into a full model would also
change the workload and would not be a fair LoRA comparison.

## Decision

HydraServe remains appendix/gate evidence only on this machine. Do not promote
it to a formal row unless a real GPU Kubernetes deployment can run the
unchanged true-remote Llama-2 7B and Llama-3.2 3B LoRA workloads and emit
`e2e_v3` metrics without replacing HydraServe's control plane.
