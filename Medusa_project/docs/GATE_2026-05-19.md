## Hardware And Runtime Blockers

Even if the CUDA Graph compile issue were patched, the official build and run
path is still not runnable on this machine without changing the system:

- README requires CUDA `12.4`, driver `550.54.14`, and 4 Optane P5800X SSDs.
- Current machine exposes `/usr/local/cuda -> /usr/local/cuda-13.0` and driver
  `580.105.08`; the conda env is a mixed CUDA 12.1/13.x package state.
- `setup.py` hard-codes `-I/home/zsx/spdk/build/include`.
- `setup.py` links `/home/zsx/spdk/build/lib/libspdk_env_dpdk.so`,
  `/home/zsx/spdk/dpdk/build/lib/librte_*.so`, `/usr/local/lib/libgdrapi.so`,
  and SPDK libraries.
- The machine has no `/home/zsx/spdk`, no SPDK/DPDK libs, and no GDRCopy lib.
- The official scripts hard-code model paths under
  `/home/zsx/raidfs-back/home/zsx/.cache/huggingface/hub/`.
- Official model choices are OpenLLaMA/Qwen/Yi/Falcon names; the requested
  Llama-2 7B and Llama-3.2 3B true-remote LoRA workloads would require a
  nontrivial model-path and workload adapter.

## LoRA And e2e_v3 Gate

The fork retains vLLM LoRA request classes and tests, so LoRA is present in the
inherited codebase. However, because the official Medusa runtime cannot be
built, we cannot truthfully run the closed true-remote shared trace/subset
through Medusa or emit a valid `e2e_v3` summary.

## Decision

Do not enter Medusa into the formal comparison table or figures on this
machine. It can be discussed as related work or as a non-reproducible appendix
gate unless the testbed is changed to provide the official CUDA/SPDK/GDRCopy
stack and a clean adaptation for the Llama-2 7B and Llama-3.2 3B LoRA workload.
